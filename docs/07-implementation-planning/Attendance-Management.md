# Attendance Management — Implementation Plan

Feature: Attendance Management
Version: 2.1
Status: **Implemented.** All 16 phases complete — see Change History v1.4 for Phase 11's own verification, v1.6 for Phase 12's (amended from its original "Correct" design — see that entry), v1.7 for Phase 13's (self check-in, replacing Phase 11's Manager/Admin-recorded "Come"), v1.8 for the additional test coverage locking in Phase 13's date/timestamp guarantee (no new phase — Phase 13's own scope already covered this), v1.9 for Phase 14's (the Excuse action's own date restriction), v2.0 for Phase 15's (a narrower Manager-recorded arrival path for Teacher/Accountant, added alongside — not replacing — Phase 13's self check-in), and v2.1 for Phase 16's (the Africa/Mogadishu business-time fix).

Source documents: `docs/03-business/Attendance-Management.md` (v2.1, Approved), `docs/06-technical-design/Attendance-Management.md` (v2.1, Implemented).

**Super Admin has zero Attendance access (Business Rule #34).** Phase 2 and Phase 8 each carry an explicit task and test for this; Testing Strategy's Permission Tests treat it as a mandatory, per-route negative case, not an incidental one.

**Staff attendance status is system-determined, not manually chosen (Business Rules #35–39, v1.2 Business Specification).** Phase 11 replaces Phase 5's and Phase 6's manual `POST .../records` endpoints with per-account "Come" and "Excuse" actions.

---

# Scope

This plan sequences the implementation of Attendance Management into ten phases, from database foundation through frontend/mobile surfaces, automated tests, and final validation. Implementation was subsequently authorized by the Product Owner and Phases 1-10 are now complete — see Change History for the exact scope of what was verified.

**Out of scope for every phase below:** any change to timetable generation logic, TSA business logic, or WSA business logic — Attendance Management only ever reads from these, per the Technical Design's Dependencies section; any Reports/Notifications feature; any biometric/RFID/QR capture method; any parent/guardian-facing surface; any multi-school attendance concept.

## Phase 1 — Database / domain foundation (Implemented)

**Scope:** Add `StudentAttendance`, `StaffAttendance`, `SchoolNonWorkingDay`, `AttendanceSettings` models; `AttendanceStatus` and `AttendanceSource` enums; the two raw-SQL partial unique indexes for `StudentAttendance`. Seed `AttendanceSettings` with one row per existing school (all window fields null, i.e. "use system default," until the Open Questions are resolved). No School-Admin-facing UI for `SchoolNonWorkingDay` yet — a minimal seed/manual-entry path only, sufficient for Phase 3+ testing.

**Files/modules likely affected:** `backend/prisma/schema.prisma`, a new migration under `backend/prisma/migrations/`, `backend/src/features/attendance/attendance.repository.js` (new).

**Dependencies:** None — this phase has no dependency on any other phase.

**Business rules covered:** #21 (source), #22 (who-marked vs. who-recorded as distinct fields), #23 (configurable, not hardcoded, opening time), #29 (no cascade delete), #31 (no session on non-working days — data foundation only, enforcement is Phase 3+).

**Tests required:** migration applies cleanly against a copy of the current schema; both partial unique indexes reject a genuine duplicate insert and accept a legitimate non-duplicate insert (raw SQL/integration-level check, mirroring how `Shift.isDefault`'s own partial index is tested); `AttendanceSettings` row is created for every existing school after seeding.

**Validation criteria:** `npx prisma migrate diff`/`validate` reports no drift; a manual `INSERT` attempting to violate either partial unique index fails as expected in a local Postgres instance.

**Rollback considerations:** purely additive (new tables/enums, no existing table touched) — rollback is a plain down-migration dropping the four new tables and two enums; no data-loss risk to any existing feature.

**Dependencies:** Phase 1 (schema must already have migrated cleanly before adding a second migration).

## Phase 11 — Staff Attendance Arrival-Based Redesign (Implemented)

**Scope:** Replace Phase 5's and Phase 6's manual-status staff-attendance write paths entirely, per Business Specification v1.2 (Business Lifecycle §11, Business Rules #35–39) and Technical Design v1.3 (Section H).

1. **Schema:** add three nullable `@db.Time()` fields to `AttendanceSettings` — `staffAttendanceStartTime`, `staffAttendanceLateThreshold`, `staffAttendanceAbsenceCutoff` — replacing the existing, never-enforced `staffAttendanceOpeningOffsetMinutes` stub (Technical Design Section D). A new migration; no data loss, since the old field was never read by any code path.
2. **Service layer:** `recordStaffArrival(schoolId, accountId, actingUser)` (the "Come" action — server-captured timestamp, derives `PRESENT`/`LATE` via a new pure `deriveStaffAttendanceStatus(arrivalTime, settings)` helper, creates the `StaffAttendance` row); `markStaffExcused(schoolId, accountId, date, actingUser)` (create-or-correct to `EXCUSED`); `getStaffAttendanceRoster(schoolId, staffAccountIds, date, actingUser)` (the read-time `ABSENT`/`NOT_RECORDED` derivation, shared by both the Manager and Admin staff-attendance views). `recordManagerStaffAttendance`/`recordAdminManagerAttendance`'s old bulk-array-of-statuses logic is removed, not deprecated-and-kept — there is no valid caller left for it once the routes below change.
3. **API:** remove `POST /attendance/manager/staff/records` and `POST /attendance/admin/managers/records`; add `POST /attendance/manager/staff/:accountId/come`, `PATCH /attendance/manager/staff/:accountId/excuse`, `POST /attendance/admin/managers/:accountId/come`, `PATCH /attendance/admin/managers/:accountId/excuse`. `GET /attendance/manager/staff` and `GET /attendance/admin/managers` gain the read-time derivation and a `time` field in their response shape (Technical Design Section R).
4. **Frontend:** `ManagerStaffAttendancePage.jsx` and `AdminManagerAttendancePage.jsx` replace their per-row status `<Select>` with a single "Come" button (disabled once a status already exists for that person/day) and, once a row is `ABSENT` or already has a status, an "Excuse" action instead of a general status editor — matching the Business Specification's own "Manager does NOT manually choose PRESENT/LATE" instruction at the UI layer, not just the API layer. New School-Admin-facing settings UI to configure the three `AttendanceSettings` time fields (no such screen exists yet — this phase's own gap, per Technical Design Risks).
5. **Migration/compatibility:** existing `StaffAttendance` rows created under the old manual-status system (Phase 5/6) remain valid, unmodified historical data — `source`, `status`, and every audit field they already carry are still meaningful and correct; this phase never rewrites past rows, only changes how *new* ones are created going forward.

**Files/modules likely affected:** `backend/prisma/schema.prisma` (new migration), `backend/src/features/attendance/{attendance.service.js, attendance.controller.js, attendance.routes.js, attendance.validation.js}`, `web/src/features/attendance/{services/attendance.service.js, pages/ManagerStaffAttendancePage.jsx, pages/AdminManagerAttendancePage.jsx}`, a new School-Admin settings page (not yet named — scoped here, designed at implementation time).

**Dependencies:** Phase 1 (schema), Phase 2 (RBAC), Phase 5 and Phase 6 (this phase replaces their write paths but reuses their read endpoints' shape and their `getManagerStaffAttendanceView`/`getAdminManagerAttendanceView`-equivalent roster resolution, extended rather than rewritten from scratch).

**Business rules covered:** #14, #15, #17, #18 (amended), #23 (amended), #26 (amended — Student-scoped), #35, #36, #37, #38, #39 (new).

**Tests required:** "Come" derives `PRESENT` at/before the late threshold and `LATE` after it, for both Manager→Teacher/Accountant and Admin→Manager; a second "Come" for the same person/day is rejected (409); "Come" before the configured start time is rejected (422); "Come" when Staff Attendance Timing Settings are entirely unconfigured is rejected (422), never silently defaulted; no `PRESENT`/`LATE`/`ABSENT` value is ever accepted from the client on `.../come` (the endpoint takes no such field at all); a "Come" recorded after the absence cutoff still produces `LATE`, not `ABSENT` (the non-obvious consequence flagged in Technical Design Section H.1); `GET` staff rosters report `ABSENT` with `time: null` once the absence cutoff passes with no "Come," and `NOT_RECORDED` before it; this derivation is re-verified against a **past** date, not just "now," so historical queries don't silently misreport (Technical Design's own flagged Risk); `.../excuse` creates a fresh `EXCUSED` row when none exists (the derived-`ABSENT` case) and corrects an existing one (preserving `recordedBy*`) when one does; `.../excuse` is rejected for any status value other than `EXCUSED`; Manager can excuse/come for Teacher/Accountant but not another Manager; Admin can excuse/come for Manager only.

## Phase 12 — Staff Attendance "Unexcuse" Action (Implemented; amended — see below)

**Scope:** Fix a real gap surfaced by live usage of Phase 11: "Excuse" was the only correction path, so a mistaken `EXCUSED` click had no way back. Per Business Specification v1.4 (re-amended Business Rule #37) and Technical Design v1.6 (Section H.2's Unexcuse action). No schema change.

**Amendment note:** this phase originally shipped a generic "Correct" action accepting any of the four statuses from the client (documented in an earlier draft of this section). The Product Owner flagged that as unfair — it let a Manager/Admin manually choose a staff member's status, defeating the entire point of the arrival-based model. That version never reached real users; it is not recorded as a separate phase, only as this note, and the scope below describes the corrected design actually implemented.

1. **Service layer:** `unexcuseStaffAttendanceByAccount(schoolId, accountId, date, actingUser)` and its `unexcuseManagerStaff(...)`/`unexcuseAdminManager(...)` role-specific wrappers — looks up the existing `StaffAttendance` row for `(accountId, date)` (404 if none, 422 if not currently `EXCUSED`). If the row's `correctedByAccountId` is set (a genuine "Come" arrival was excused), recomputes `PRESENT`/`LATE` from the row's own untouched `recordedAt` via `deriveStaffAttendanceStatus` and clears `correctedBy*` (delegating the write to the pre-existing `correctStaffAttendance`, unmodified since Phase 7/v1.2). If `correctedByAccountId` is null (Excuse created the row fresh), deletes the row outright. Never accepts a client-supplied status. "Come" and "Excuse" are entirely unchanged.
2. **API:** add `PATCH /attendance/manager/staff/:accountId/unexcuse` (body: `{ date? }` only, Role: `MANAGER`) and `PATCH /attendance/admin/managers/:accountId/unexcuse` (same shape, Role: `SCHOOL_ADMIN`). Reuses the existing optional-date validation already used by `.../excuse` — no status field exists on this endpoint at all.
3. **Frontend:** `ManagerStaffAttendancePage.jsx` and `AdminManagerAttendancePage.jsx` show an "Unexcuse" button in place of "Excuse" whenever a row's current status is `EXCUSED`, so a mistaken click is always one click to undo. No status-picking UI of any kind is exposed for staff attendance.

**Files/modules affected:** `backend/src/features/attendance/{attendance.service.js, attendance.repository.js, attendance.controller.js, attendance.routes.js, attendance.validation.js}`, `web/src/features/attendance/{services/attendance.service.js, pages/ManagerStaffAttendancePage.jsx, pages/AdminManagerAttendancePage.jsx}`.

**Dependencies:** Phase 11 (this phase adds to its routes/pages, replaces nothing).

**Business rules covered:** #37 (re-amended).

**Tests required:** unexcusing a row that had a genuine prior arrival recomputes the correct `PRESENT`/`LATE` from that arrival's real timestamp and clears `correctedBy*`; unexcusing a row Excuse created fresh deletes it entirely (verified both via the `GET` roster reporting the correct derived state afterward and via a direct DB check that no row remains); unexcusing a non-`EXCUSED` row is rejected (422); unexcusing a non-existent record is rejected (404); a Manager cannot unexcuse an Admin-recorded Manager row and vice versa (reusing `correctStaffAttendance`'s existing source-check defense-in-depth); the SUPER_ADMIN-exclusion route list uses the two `/unexcuse` routes, not `/correct`.

**Validation criteria:** full Attendance suite plus every test above passes; full backend suite passes with zero regressions; `npm run build` succeeds; manual browser walkthrough confirms a mistakenly-Excused row can be undone via "Unexcuse" and that no UI path lets a Manager/Admin pick an arbitrary status.

**Rollback considerations:** purely additive relative to Phase 11 (two new routes, two new service functions, one new UI affordance per page) — safe to roll back independently without affecting Phase 11's "Come"/"Excuse" behavior at all.

## Phase 13 — Staff Attendance Self Check-In (Implemented)

**Scope:** Replace the Manager-clicks-Come-for-every-staff-member / Admin-clicks-Come-for-every-Manager model (Phase 11) with genuine self-check-in — each Teacher, Accountant, and Manager records their own arrival. Per Business Specification v1.5 (re-amended Business Rules #14, #15, #17, #18) and Technical Design v1.7 (Section H.1). No schema change — purely a recording-authority change, not a data-model change.

**Why this phase exists:** the Product Owner identified that Phase 11's "Manager clicks Come for each staff member" design (approved and shipped earlier in this same project) was itself an anti-pattern — operationally, a Manager clicking through 20–60 people one at a time every morning does not scale, and architecturally, a third party recording someone else's arrival is a weaker, less accountable signal than the person recording their own. This phase does not touch `EXCUSED`/`Unexcuse` (Phase 12) at all — Manager/Admin correction authority over someone else's record is unchanged; only who triggers the underlying arrival write changes.

1. **Service layer:** `recordSelfArrival(schoolId, actingUser)` — replaces `recordStaffArrival`/`recordManagerStaffArrival`/`recordAdminManagerArrival` with one function for all three self-checking-in roles. Captures server time, derives `PRESENT`/`LATE` exactly as before (`deriveStaffAttendanceStatus`, unchanged); determines `source`/`staffRole` from `actingUser.role` alone (`TEACHER`/`ACCOUNTANT` → `MANAGER_STAFF_ATTENDANCE`; `MANAGER` → `ADMIN_MANAGER_ATTENDANCE`); writes `recordedByAccountId = actingUser.id` (always the subject). No target-account lookup, since there is no target — the acting user is the subject.
2. **API:** add `POST /attendance/staff/me/come` — no path parameter, no body, Role: `TEACHER`, `ACCOUNTANT`, `MANAGER`. **Remove** `POST /attendance/manager/staff/:accountId/come` and `POST /attendance/admin/managers/:accountId/come` entirely — a breaking change, not additive (the second breaking change this feature has made, after Phase 11's own bulk-endpoint removal). `GET /attendance/manager/staff`, `GET /attendance/admin/managers`, and both `.../excuse`/`.../unexcuse` route pairs are completely unchanged.
3. **Frontend:** `ManagerStaffAttendancePage.jsx` and `AdminManagerAttendancePage.jsx` drop the "Come" button entirely — a Manager/Admin never sees a per-row "Come" action again. The roster becomes a live, read-only-except-`EXCUSED` list: Staff Member, Role, Arrival Time, Status, with "Excuse"/"Unexcuse" as the only actions (Phase 12, unchanged). ## Phase 14 — Staff Attendance Excuse Date Restriction (Implemented)

**Scope:** Fix a real, live-tested gap: the normal Excuse action (Phase 12) accepted any client-supplied date with no legality check — `PATCH .../excuse` with `{"date":"2020-01-01"}` or `{"date":"2099-12-31"}` both succeeded. Restrict the normal action to today; add a separate, explicitly-authorized historical-correction action for a genuine past date; never allow a future date through either. Per Business Specification v1.7 (new Business Rule #41) and Technical Design v1.9.

**Investigation before implementation, per the ticket's own instruction:** confirmed via a live `curl` test against the running server (not just a code read) that both a 2020 and a 2099 date succeeded through `PATCH /attendance/manager/staff/:accountId/excuse`. Root cause: `markStaffExcused` took `dateStr` straight through to `toDateOnly` with only ISO-syntax validation (`validateOptionalDateBody`); the frontend compounded it by feeding the roster page's own unrestricted date-filter picker directly into the Excuse call. This is unrelated to Phase 13's self "Come" restriction (Business Rule #40) — Excuse was never touched by that fix, since Excuse and Come are different actions with different (and, until now, differently-enforced) date rules.

1. **Service layer:** `markStaffExcused` gained a `historical` flag (default `false`). When `false`, `assertTodayOnly(dateStr)` runs first — reject (422) unless `dateStr` equals today. When `true`, `assertPastDateOnly(dateStr)` runs instead — reject (422) unless `dateStr` is strictly before today. The create-or-correct-to-`EXCUSED` mutation itself is unchanged and unduplicated between the two callers. New wrappers `excuseManagerStaffHistorical`/`excuseAdminManagerHistorical` call `markStaffExcused` with `historical: true`; the existing `excuseManagerStaff`/`excuseAdminManager` are otherwise unchanged (they now simply run through the new `assertTodayOnly` gate before reaching the same mutation they always had).
2. **API:** add `PATCH /attendance/manager/staff/:accountId/excuse-historical` and `PATCH /attendance/admin/managers/:accountId/excuse-historical` (same role gates as their non-historical counterparts). Body: `{ date }` — required, via a new `validateRequiredDateBody` (distinct from the existing `validateOptionalDateBody` the normal action keeps using). `PATCH .../excuse` and `.../excuse-historical` are otherwise unchanged in shape (no new fields beyond the date-legality gate).
3. **Audit:** the create-or-correct write via a `historical: true` call additionally records a distinct `attendance.staff.historical_excuse` audit event (on top of, never instead of, the generic action the underlying write already produces) — a historical correction is unambiguous in the audit trail, not merely inferable by comparing the record's `date` against `createdAt`.
4. **Frontend:** `ManagerStaffAttendancePage.jsx`/`AdminManagerAttendancePage.jsx` keep their existing date-filter picker exactly as-is (viewing any date is still allowed) but now branch the Excuse action on it: today calls the normal action, unchanged; a past date calls the new historical action through a visibly relabeled `StaffExcuseModal` (new `historical`/`targetDateLabel` props, additive — this component is used only by these two pages, not shared with Student Attendance); a future date disables the Excuse control entirely, with an explanatory label and a page-level banner. `Unexcuse` is completely untouched.

**Files/modules affected:** `backend/src/features/attendance/{attendance.service.js, attendance.controller.js, attendance.routes.js, attendance.validation.js}`, `web/src/features/attendance/{services/attendance.service.js, pages/ManagerStaffAttendancePage.jsx, pages/AdminManagerAttendancePage.jsx, components/StaffExcuseModal.jsx}`.

**Dependencies:** Phase 12 (this phase restricts and extends its Excuse action; Unexcuse is untouched). Independent of Phase 13 (self "Come") — different action, different gap, different fix.

**Business rules covered:** #37 (amended — date-scope split), #41 (new).

**Tests required:** today succeeds via both an omitted and an explicit `date`; yesterday and tomorrow are both rejected (422) through the normal action, each verified against a direct DB read confirming no row was created for the rejected date; the historical action succeeds for a genuine past date; the historical action rejects a missing `date`, today, and a future date (422 in all three cases); `Unexcuse` against a record created via the historical action still works, unchanged; the two Excuse audit actions (`attendance.staff.excused` vs. `attendance.staff.historical_excuse`) are distinct and independently queryable.

**Validation criteria:** full Attendance suite plus every test above passes; full backend suite passes with zero regressions; `npm run build` succeeds; manual browser walkthrough confirms today's Excuse popup is unchanged, a past date's popup is visibly labeled as a historical correction, and a future date's Excuse control is disabled.

**Rollback considerations:** additive for the historical path (two new routes, two new service functions, one new validation function) but the normal `.../excuse` route's own behavior changed (it now rejects non-today dates it previously accepted) — rolling back the `assertTodayOnly` gate alone would silently reopen the original gap, so this phase should be rolled back as one unit, not split into "keep the restriction, drop the historical route" or vice versa.

## Phase 15 — Manager-Recorded Staff Arrival for Teacher/Accountant (Implemented)

**Scope:** Add a narrower, explicit Manager-recorded "Come" path for Teacher/Accountant staff attendance, alongside (never replacing) Phase 13's self check-in. Per Business Specification v2.0 (new Business Rule #42, amended #14/#15/#16) and Technical Design v2.0 (Section H.1b). No schema change — `StaffAttendance` already had every field this action needs; this is a recording-authority addition, not a data-model change.

**Why this phase exists:** the Manager Staff Attendance roster's `NOT_RECORDED` control had no recording action at all — clicking it opened the `EXCUSED` popup, a correction mechanism never intended to record a first arrival (Business Rule #37 explicitly forbids `EXCUSED` being used to fabricate `PRESENT`/`LATE`). The Product Owner directed a dedicated fix: reintroduce a Manager-initiated recording action, but scoped no wider than the Manager's existing `EXCUSED` authority (Teacher/Accountant only, never another Manager, never an Admin) — deliberately narrower than Phase 11's original Manager-clicks-Come-for-everyone design, which remains reverted. This phase does not touch `EXCUSED`/`Unexcuse` (Phase 12/14) at all, and does not touch self check-in (Phase 13) — both continue to work exactly as before, on records created by either path indistinguishably (aside from the audit trail).

1. **Service layer:** `recordManagerStaffArrival(schoolId, accountId, actingUser)` in `attendance.service.js` — resolves `accountId` against `authService.listAccountsByRole(schoolId, ['TEACHER', 'ACCOUNTANT'])` (422 `ValidationError`, same shape `markStaffExcused` already returns, if not found — this is what makes "never a Manager, never an Admin, never cross-school" structural rather than a policy note); shares `assertStaffAttendanceTimingConfigured` and `deriveStaffAttendanceStatus` with `recordSelfArrival` unduplicated; creates the row with `staffAccountId` = the target, `staffRole` = the target's role, `source = 'MANAGER_STAFF_ATTENDANCE'`, `recordedByAccountId` = the acting Manager, `recordedByRole = 'MANAGER'`, `recordedAt` = the captured instant. Catches the existing `@@unique([staffAccountId, date])` violation and translates it to the same 409 self "Come" already produces. Records a new, distinct audit action, `STAFF_ATTENDANCE_MANAGER_ARRIVAL_RECORDED`, with `metadata.staffAccountId` = the target and the audit row's own `userId` = the acting Manager — the two-distinct-facts guarantee (Business Rule #22) applied to a "Come"-family write for the first time.
2. **API:** add `POST /attendance/manager/staff/:accountId/come`, role `MANAGER`, no body. Every other Manager staff-attendance route (`GET .../staff`, `.../excuse`, `.../excuse-historical`, `.../unexcuse`) is completely unchanged. `POST /attendance/staff/me/come` (Phase 13) and `POST /attendance/admin/managers/:accountId/come` (removed in Phase 13, still removed) are both unaffected — this phase does not touch the Admin↔Manager relationship at all.
3. **Frontend:** `ManagerStaffAttendancePage.jsx`'s per-row control branches on status for the first time: while `NOT_RECORDED`, clicking the (already-existing, already-unfilled) status dot calls the new arrival action directly instead of opening `StaffExcuseModal`; for every other status (`PRESENT`/`LATE`/`ABSENT`), the click still opens the Excuse popup exactly as before — no visual redesign, no new component. `AdminManagerAttendancePage.jsx` is explicitly **not** touched by this phase (Admin↔Manager relationship out of scope); its own `NOT_RECORDED` row still opens the Excuse popup, unchanged — a known, deliberate asymmetry, not an oversight, flagged in Risk Assessment below.

**Files/modules affected:** `backend/src/features/attendance/{attendance.service.js, attendance.controller.js, attendance.routes.js}`, `web/src/features/attendance/{services/attendance.service.js, pages/ManagerStaffAttendancePage.jsx}`.

**Dependencies:** Phase 11 (shares `deriveStaffAttendanceStatus`/timing settings), Phase 13 (coexists with, does not replace, self check-in — both write to the same table under the same uniqueness constraint), Phase 12/14 (`EXCUSED`/`Unexcuse`/historical correction, unaffected and reused as-is since the new action shares `source = MANAGER_STAFF_ATTENDANCE`).

**Business rules covered:** #14, #15, #16 (all amended), #42 (new).

**Tests required:** a Manager can record arrival for a Teacher and receive the correct derived `PRESENT`/`LATE`; a Manager can record arrival for an Accountant; a Manager attempting to record arrival for another Manager is rejected (422); a Manager attempting to record arrival for a School Admin account is rejected (422); the arrival timestamp is server-captured (never accepted from the request, which has no body); a spoofed `date`/`recordedAt`/`status` in the request body is ignored identically to self "Come"'s own Phase 13/v1.8 guarantee; `PRESENT`/`LATE` is derived automatically from the captured time against the configured late threshold, never client-supplied; a Manager attempting to record arrival for a Teacher/Accountant who has not yet had any attendance today succeeds and produces a `NOT_RECORDED` → recorded transition; a second recording attempt for the same staff member/day is rejected (409), whether the first was self- or Manager-recorded; `EXCUSED` and `Unexcuse` continue to work identically on a Manager-recorded row, proving Phase 12/14's correction authority was not regressed; the audit row for a Manager-recorded arrival carries both the target staff member's id and the acting Manager's id as the recording user, distinguishable from a self-recorded arrival's audit row; a Manager attempting to record arrival for a Teacher/Accountant at a different school is rejected (422, cross-tenant); the existing self "Come" route and its own full Phase 13 test suite continue to pass unmodified.

**Validation criteria:** full Attendance suite plus every test above passes; full backend suite passes with zero regressions; `npm run build` succeeds; manual browser walkthrough confirms clicking a `NOT_RECORDED` row's ○ on the Manager roster records that staff member's arrival and updates the row immediately without ever opening the Excuse popup, while every other status's row still opens the Excuse popup exactly as before.

**Rollback considerations:** additive — one new route, one new service function, one new audit action, one new frontend branch in an existing click handler. Rolling back removes the new route/function/branch cleanly; self check-in (Phase 13) and `EXCUSED`/`Unexcuse` (Phase 12/14) are entirely unaffected either way, since neither this phase nor its rollback touches their code paths.

## Phase 16 — Staff Attendance Africa/Mogadishu Business-Time Fix (Implemented)

**Scope:** Fix a real, live-reported bug: every Staff Attendance business-time computation ("has the window opened," `PRESENT`/`LATE` derivation, read-time `ABSENT` derivation, self check-in, Manager-recorded arrival, and the Excuse action's "today") read `Date#toISOString()` — always UTC — instead of the application's actual, fixed operating timezone, Africa/Mogadishu (UTC+3, no DST). Per Business Specification v2.1 (new Business Rule #43) and Technical Design v2.1 (Section H.4).

**Investigation before implementation, per the ticket's own instruction:** a read-only diagnostic was run first, no code changed. Confirmed via a live Node script against the real dev database: the server's own OS timezone is `Africa/Mogadishu` (confirmed via `Intl.DateTimeFormat().resolvedOptions().timeZone`), current server time was `07:40` local / `04:40` UTC, and the school's configured `staffAttendanceStartTime` was `06:00`. `recordManagerStaffArrival`'s actual gate — `timeStr < startTime` where `timeStr = new Date().toISOString().slice(11,16)` — evaluated `'04:40' < '06:00'` → `true` → rejected, even though the School Admin's evident intent (6:00 AM meaning Mogadishu wall-clock) had already passed by more than an hour and a half of real local time. A parallel check confirmed the reporter's Working-Days edit (adding Thursday to `SchoolCalendar`) was correctly applied and completely unrelated — Staff Attendance's "Come" actions never call `assertSchoolDay`/`isSchoolDay` at all (verified by grep — those calls exist only in the Teacher/Manager **Student**-attendance code paths, Phase 3/4), so the working-day change could not have affected this error in either direction.

1. **Service layer:** four new `Intl`-only helpers in `attendance.service.js` (Section H.4) — `mogadishuTimeString(date)`, `mogadishuDateStr(date)`, `mogadishuOffsetMinutes(date)`, `mogadishuWallClockToInstant(dateStr, timeStr)` — added alongside, not replacing, the pre-existing UTC-based `toDateOnly`/`dayOfWeekFor`/`nowTimeString`/`todayDateStr`, which remain completely unchanged and continue to back Teacher/Manager Student attendance. Rewired every Staff Attendance business-time comparison to use the new helpers: `recordSelfArrival` and `recordManagerStaffArrival` now derive `timeStr`/`dateStr` via `mogadishuTimeString`/`mogadishuDateStr` (the real absolute `arrivalNow` instant is still what gets stored in `recordedAt` — only the comparison strings changed); `assertTodayOnly`/`assertPastDateOnly` (the Excuse date-scope gates, Phase 14) now compute "today" via `mogadishuDateStr(new Date())` instead of `todayDateStr()`, so a record's "today" is consistent across Come, Excuse, and Unexcuse, never split by the UTC/Mogadishu day-boundary gap (21:00–23:59 UTC is already the next calendar day in Mogadishu); `unexcuseStaffAttendanceByAccount`'s recompute branch now reads the original arrival's time-of-day via `mogadishuTimeString(existing.recordedAt)` instead of `formatTimeField` (which is UTC-literal); `deriveStaffRosterEntry`'s `ABSENT` derivation now converts the configured absence cutoff via `mogadishuWallClockToInstant(dateStr, absenceCutoff)` before comparing against `new Date()`, instead of naively constructing `new Date(`${dateStr}T${absenceCutoff}:00.000Z`)` (which wrongly treated the Mogadishu-intended cutoff as if it were itself UTC).
2. **No API change.** No route, controller, or validation file changed — every edit is inside `attendance.service.js`'s existing functions. No schema change — no new column, no new table.
3. **No new dependency.** All four helpers use only the built-in `Intl.DateTimeFormat` API (Node's ICU is complete by default) — no `moment-timezone`, `luxon`, or `date-fns-tz` package was added, and none was already present in `package.json`.
4. **Frontend:** untouched. The bug and its fix are entirely server-side business-time interpretation; the reported symptom (the toast message "Could not record arrival" / "Staff attendance has not opened yet for today") simply stops appearing at the wrong wall-clock moment once the server-side comparison is corrected.

**Files/modules affected:** `backend/src/features/attendance/attendance.service.js` only, plus its test file `attendance.routes.test.js`.

**Dependencies:** Phase 11 (shares the timing-settings/derivation functions this phase corrects), Phase 13 (self check-in), Phase 14 (Excuse date-scope gates), Phase 15 (Manager-recorded arrival) — all four had the same underlying UTC-literal bug; this phase fixes all of them in one pass since they shared the same root cause and the same new helpers.

**Business rules covered:** #43 (new). Business Rules #35–37, #39–42 are unchanged in *what* they require — only *which clock* "now" is read from changed.

**Tests required:** a scenario where raw UTC time-of-day is still before the configured start time but Mogadishu time-of-day is already past it succeeds for self "Come" (the literal reported bug, reproduced and proven fixed); the identical scenario succeeds for Manager-recorded arrival; the read-time roster derives `ABSENT` for a cutoff that a naive UTC-literal comparison would say hasn't passed yet, but has genuinely passed in Mogadishu time; `Unexcuse` recomputes `LATE` (not `PRESENT`) from an arrival's Mogadishu time-of-day, not its raw UTC time-of-day, for a late threshold that sits between the two readings; every pre-existing Staff Attendance test continues to pass (two pre-existing tests needed their fixture values adjusted from raw-UTC-relative to Mogadishu-relative, since they were unknowingly asserting the old bug's behavior — not a new regression, a correction of test expectations that encoded the bug).

**Validation criteria:** full Attendance suite (87 tests, up from 83) passes; full backend suite (1145 tests) passes with zero regressions; `npm run build` (frontend) succeeds, since no frontend file changed. No manual browser walkthrough was performed for this phase — the fix is a pure server-side business-time interpretation change, fully covered by the integration test suite against the real Express app and dev database.

**Rollback considerations:** low-risk, single-file, purely internal to `attendance.service.js` — no API shape changed, no schema changed, no frontend changed. Rolling back restores the UTC-literal comparison (and therefore the reported bug) with no other side effects, since nothing outside this one file depends on the new helpers.

# Risk Assessment

- **Assumption Requiring Approval #1 blocks Phase 4 specifically** (see Phase 4's own hard-prerequisite note) — the highest-severity open risk, since it affects real school data shapes that may not be known until implementation time.
- **The four Open Questions (time windows) affect Phases 3, 5, 6, 7** — mitigated by the "null means system default, never a hardcoded guess" design (Technical Design Section K), but the actual default values still need Product Owner input before Phase 3 can be considered functionally complete for a real school, not just structurally correct.
- **`MANAGER` role and Manager account-management (Phase 2) is new, security-sensitive surface** — bundled into this feature rather than delivered independently; requires careful review given it's a net-new RBAC role, not a permission tweak to an existing one.
- **`SchoolNonWorkingDay` has no management UI in Phase 1–7** — a real school cannot actually populate holidays before Phase 8, or before an ad hoc admin data-entry path is agreed; flagged so Phase 8 planning doesn't discover this gap late.
- **The Teacher-lock mechanism (Phase 4) modifies already-shipped Phase 3 code** — the single highest regression-risk change in this plan; Phase 4's own tests must include full re-verification of Phase 3's existing test suite, not just new-behavior tests.
- **(Phase 11) No School-Admin-facing UI exists yet to configure Staff Attendance Timing Settings** — until built, "Come" is rejected for every staff member at every school, per Business Rule #38's deliberate "no default, ever" design. This makes Phase 11 functionally incomplete for a real school without its own settings screen, not just structurally correct — the same class of gap `SchoolNonWorkingDay` already has.
- **(Phase 11) The read-time `ABSENT` derivation must be correct for past dates, not just "now"** — the single highest correctness risk in this phase; a naive "is it currently past the cutoff" check (ignoring which date is being queried) would silently misreport all historical un-recorded staff-days as `NOT_RECORDED` forever. Requires a dedicated test against a genuinely past date, not just today's.
- **(Phase 11) Removes Phase 5's/Phase 6's bulk `POST .../records` endpoints entirely, not additively** — any external caller (a future mobile client, an internal script) built against the v1.2 bulk-status API breaks. None is known to exist yet (Phase 8's own web frontend is the only consumer, and this plan updates it in the same phase), but this is a genuine breaking change, not a purely additive one like every other phase in this plan.
- **(Phase 13) Removes `POST .../manager/staff/:accountId/come` and `POST .../admin/managers/:accountId/come` entirely, not additively** — the same class of breaking change as Phase 11's bulk-endpoint removal above, and the reason Phase 11's own approved design has to be revisited so soon after shipping: it approved the Manager/Admin-clicks-Come model that this phase now reverses. None of Phase 11's own consumers are external (same web frontend, updated in the same phase), so the actual blast radius is limited to this repository, but this is the second breaking change in this feature's history and worth flagging as a pattern — staff-attendance recording-authority decisions should get more scrutiny before shipping than they received in Phase 11, precisely because reversing them after the fact is disruptive.
- **(Phase 13) A new self-service frontend surface is required for Teacher/Accountant/Manager to self-check-in** — no such page existed before (Teacher/Accountant/Manager previously had no attendance-recording UI of their own at all for staff attendance). This is new frontend surface area, not a re-skin of an existing page, and needs its own design/placement decision (e.g. a dashboard widget vs. a dedicated page) at implementation time.
- **(Phase 15) Deliberate asymmetry: `ManagerStaffAttendancePage.jsx` gains a Manager-recorded arrival action, `AdminManagerAttendancePage.jsx` does not.** The Admin↔Manager relationship was explicitly out of scope for this phase's directive — an Admin still cannot record a Manager's arrival, and that page's `NOT_RECORDED` row still opens the Excuse popup, unchanged. This is a known, intentional inconsistency between the two otherwise-structurally-identical roster pages, not an oversight; if Admin-side parity is ever wanted, it is a new, separately-scoped phase, not an extension of this one.
- **(Phase 14) `.../excuse` gains a real, non-additive behavior change** — unlike every other Phase 14 addition, restricting the normal Excuse action to today is not backward-compatible: any caller (a script, a future mobile client) that previously relied on supplying a non-today date to `.../excuse` now gets 422 and must switch to `.../excuse-historical`. None is known to exist yet (the web frontend is the only consumer, updated in the same phase), but this is the third behavior-narrowing change in this feature's history (after Phase 11's bulk-endpoint removal and Phase 13's Come-route removal) — flagged so a future reader doesn't assume every Phase 14 change is purely additive just because two of its three changes are.

- **(Phase 11) Status-derivation Tests** — a new category this phase introduces: `deriveStaffAttendanceStatus` exercised directly as a pure function across the late-threshold boundary (exactly at, one minute before, one minute after) independent of any HTTP/DB layer, plus the full "Come" → derived status → `GET` roster round trip through the real API for both the at-threshold and after-threshold cases.
- **(Phase 12) Unexcuse Tests** — the `.../unexcuse` routes exercised for both outcomes (recompute-from-real-arrival vs. delete-the-fresh-row), the 404-when-no-row and 422-when-not-currently-EXCUSED cases, and the same Manager/Admin source-check defense-in-depth already covered for Student attendance, now re-verified for staff attendance's own two sources. Deliberately does NOT test "correct to an arbitrary status," since no such capability exists.
- **(Phase 13) Self Check-In Tests** — `POST /attendance/staff/me/come` exercised for all three self-checking-in roles (`TEACHER`, `ACCOUNTANT`, `MANAGER`), confirming `source`/`staffRole`/`recordedByAccountId` are all derived correctly per role with no client input; the removed `.../accountId/come` routes return 404 (route no longer registered); a `SCHOOL_ADMIN` token is rejected on the self-check-in route (Business Rule #33). Deliberately does NOT test "Manager records a Teacher's arrival," since no such capability exists any more.
- **(v1.8) Self Check-In Date/Timestamp Integrity Tests** — a dedicated group proving Business Rule #40: a normal today self "Come" succeeds and is dated today; a client-supplied `date` of yesterday or tomorrow is ignored (the record still lands on the real today, and no row is ever created under the spoofed date — verified with a direct DB read, not just the response body); a client-supplied `recordedAt` is ignored (the response's `recordedAt` equals the real, fake-timer-pinned "now," never the spoofed value); a client-supplied `status` is ignored; all three spoofed together in one request are ignored simultaneously. Paired with two **Historical Correction Tests** proving the opposite guarantee for the *other* action: a Manager's `EXCUSED`/`Unexcuse` against an explicit past date still succeeds — this fix must narrow only self "Come," never the Manager/Admin correction workflow.
- **(Phase 14 / v1.9) Excuse Date Restriction Tests** — proving Business Rule #41: today succeeds via both an omitted and an explicit `date` through the normal Excuse action; yesterday and tomorrow are both rejected (422) through the normal action, each verified against a direct DB read confirming no row was created for the rejected date (not just the HTTP status); the separate historical action succeeds for a genuine past date; the historical action rejects a missing `date`, today, and a future date; `Unexcuse` against a record created via the historical action is unaffected; the two Excuse audit actions are distinct and independently queryable via `AuditLog`. Deliberately does NOT retest self "Come" (Phase 13/v1.8's own test group already covers it) — this category is specifically about the Excuse action's own, separate gap.
