Version: 1.0

Status: Draft — feature sequence pending Product Owner approval

# Purpose

This document defines the order in which the project moves from initialization to completion: which global phase comes first, and in what sequence business features are implemented.

This document defines **what order** features are delivered in.

Development-Lifecycle.md defines **how** each individual feature moves through its own phases (Business Discovery → Business Specification → Business Review → Technical Design → Implementation Planning → Implementation → Validation → Documentation → Feature Acceptance → Maintenance).

Read both documents together. This one should never restate the per-feature lifecycle — only the sequence.

---

# Global Project Phases

These are one-time, project-wide phases. They are distinct from the per-feature lifecycle in Development-Lifecycle.md.

## Phase 0 — Foundation

Status: Completed

Governance, architecture, and standards documentation established. Repository initialized.

## Phase 1 and onward — Feature Delivery

Every phase from here on is the delivery of exactly one business feature, taken through the full Development-Lifecycle.md process before the next one begins, per the Constitution's "one feature at a time" rule (§4).

There is no separate "final phase" beyond feature delivery. The project reaches completion when every feature in the sequence below has reached Feature Acceptance. From that point, Development-Lifecycle.md's Phase 10 (Maintenance) governs the project going forward.

# Feature Delivery Sequence

The order below follows business dependency — each feature is placed after the features its data or workflow relies on — not arbitrary preference. It is a proposal for approval, not a final decision.

| Order | Feature | Reason for this position |
|---|---|---|
| 1 | School & Platform Management | A school must exist before any user of that school — including its first School Admin — can be created or log in. This is the true starting point of the tenant lifecycle. **Accepted**; see Status Tracking below. |
| 2 | Authentication & Authorization | Every other feature depends on knowing who is acting and what they may do, but it operates on schools and accounts that School & Platform Management brings into existence. **Accepted**; see Status Tracking below. |
| 3 | Class Management | **Re-sequenced ahead of Student Management** (was #5) — Student Management's Technical Design (docs/06-technical-design/Student-Management.md) identified that Enrollment, Promotion, and Graduation-eligibility all require a Class entity and a "final Class" designation. This is an implementation dependency, not a business-logic change: Academic placement belongs to the academic structure Class Management owns, and Student Management must not invent a placeholder Class model to work around the gap. Foundational academic structure also referenced by Timetable, Attendance, and Exams. **Accepted**; see Status Tracking below. |
| 4 | Student Management | Attendance, Exams, Fees, and Passcard all reference a Student record. Depends on Class Management (#3 above) for Enrollment, Promotion, and Graduation. **Accepted**; see Status Tracking below. |
| 5 | Teacher Management | Required before Class/Subject assignment and Attendance can reference a teacher. Class Management's own records (e.g. a Class's existence) do not require a Teacher to exist first; only the later assignment of a Teacher to a Class/Subject does, which remains after Teacher Management here. |
| 6 | Subject Management | Same reason as Class Management; typically defined alongside it. |
| 7 | Academic Year Management | **Added mid-sequence** (not in the original proposal) — a Product Owner architectural requirement identified while reviewing Student Management's free-text `Enrollment.academicYear` field: Academic Year needed to become a first-class, school-scoped entity multiple unbuilt features (Attendance, Timetable, Exam Management, Fees Management, Report Cards) already implicitly depend on, the same reasoning that produced Subject Management. Sequenced after Subject Management since both are foundational academic-structure features; Student Management's own consumption of it is a separate future ACR, not part of this feature's own delivery. **Accepted**; see Status Tracking below. |
| 8 | School Schedule Management | **Added mid-sequence** (not in the original proposal), per the Product Owner's approved architecture position: `School Management → Academic Year Management → School Schedule Management → {Subject, Teacher, Student, Class Management, Teacher Subject Assignment}`. Establishes a school's Working Days, Weekend Days, and Shifts as the authoritative operating-schedule foundation Timetable and other future time-aware features would otherwise each invent independently. **Retroactive insertion under four already-Accepted features and one Approved-through-Implementation-Planning feature** — Class Management, Subject Management, Teacher Management, and Student Management are already built with no Shift concept, and Teacher Subject Assignment is awaiting Phase 6; none are reopened by this insertion, but Class Management requires a small additive change (a required `shiftId` reference, with existing Classes backfilled to the school's Default Shift), the same category of change already used for Teacher Management's own `getTeacherById` addition. See `docs/03-business/School-Schedule-Management.md` and Status Tracking below. |
| 9 | Teacher Subject Assignment | **Added mid-sequence** (not in the original proposal) — connects Teacher, Subject, Class/Section, and Academic Year (all now Accepted) into a school-owned teaching-responsibility record. Placed directly ahead of Timetable, which depends on it: Timetable cannot schedule teaching periods without first knowing who teaches what, to whom, and in which Academic Year. See Status Tracking below. |
| 10 | Timetable | Depends on Class, Subject, Teacher, Academic Year, School Schedule Management, and now Teacher Subject Assignment already existing. |
| 11 | Attendance Management | Depends on Student, Class, and Timetable. |
| 12 | Exam Management | Depends on Student, Class, and Subject. |
| 13 | Fees Management | Depends on Student and school enrollment; independent of the academic features above. |
| 14 | Online Passcard | Depends on Student identity being established. |
| 15 | Reports | Aggregates data from every feature above; must come after what it reports on. |
| 16 | Audit Logs (review/search capability) | Audit *event capture* is part of every feature's own Audit Requirements from Phase 1 onward. This entry is specifically about building the audit review/search feature itself, which depends on other features already producing audit data. |

# Backlog (not yet sequenced)

Features identified as needed, but not yet placed into the Feature Delivery Sequence above. They require a Product Owner decision on priority/position before Business Discovery begins, per the Change Policy below.

| Feature | Reason it exists | Motivating gap |
|---|---|---|
| Administrative Corrections | Cross-cutting feature to correct administrative mistakes (e.g., a mis-clicked Transfer or Graduation) across features that model permanent, one-way lifecycle events — without each feature inventing its own bespoke undo logic. Placeholder Business Specification started: `docs/03-business/Administrative-Corrections.md`. | Student Management's Transfer and Graduation are correctly implemented as permanent (Business Rules #6, #15), but the "separate, controlled administrative correction process" those rules anticipate does not exist yet. Until this feature is designed and built, there is intentionally no in-application recovery path for a mistaken Transfer or Graduation — recorded as a known limitation in `docs/06-technical-design/Student-Management.md`'s Risks section. |
| Platform Configuration | Platform-wide shared configuration: system settings, reference data (countries, currencies, languages), and other platform-level configuration not scoped to any single school. | School & Platform Management's Business Specification (v1.0) and Implementation Plan originally included this as in-scope, but it was never built, and nothing in the codebase needs it today. Phase 7 Validation found the gap; Product Owner decision (School-Management.md v1.1) consciously descoped it as speculative (YAGNI) rather than building it now, and tracked it here instead. |
