# Overview

This document designs the technical approach for the Business Specification approved in `docs/03-business/Weekly-Subject-Allocation.md` (v1.0).

It applies the already-approved architecture (`System-Architecture.md`, `Folder-Structure.md`), technology stack (`Technology-Decisions.md`), and standards (`Database-Standards.md`, `API-Standards.md`, `Security-Standards.md`, `Naming-Conventions.md`) to this specific feature. No new business rule is introduced anywhere below; every design decision either directly implements an already-approved Business Rule or is a pure implementation-mechanism choice the Business Specification deliberately left open (e.g. the exact shape of the "Needs Review" mechanism, since the Business Specification states the *behavior* — automatic detection, school-wide generation block — without prescribing *how* a downstream schema change is detected without an event system).

This feature is **nested under Timetable Management's own navigation, but is its own feature module and its own Technical Design document** — the same treatment already given to Teacher Subject Assignment (menu-adjacent to Timetable, but its own module, its own lifecycle, its own Accepted status independent of Timetable's own). "Nested in the menu" is a Frontend/navigation-position decision (see Frontend Design); it has no bearing on backend module boundaries, which follow Feature Ownership exactly as every other feature in this project already does.

# Architecture

- Implemented as a feature module: `backend/src/features/weekly-subject-allocations/` — plural, kebab-case, matching `teacher-subject-assignments`/`academic-years`/`classes`/`subjects`, the dominant convention for a feature whose own entity is a *collection of many rows per school* (one allocation per Grade/Form per Academic Year), as opposed to `school-schedule`'s singular naming (a school has exactly one schedule configuration, not many).
- **Two entities, a header-plus-lines shape** — `WeeklySubjectAllocation` (one row per school + Academic Year + Grade/Form) and `WeeklySubjectAllocationSubject` (one row per Subject within that allocation, carrying its own weekly period count and Double Period flag). This mirrors `Shift`/`Period`'s own header-plus-child shape and `TimetableVersion`/`Lesson`'s own shape more closely than a single flat table would: the "total must exactly equal available periods" validation (Business Rule #6/#7) is naturally a property of the *whole* allocation (the header + all its lines together), not any single line, and Needs-Review detection (below) is likewise a property of the header alone.
- **"Needs Review" is a derived comparison, never a persisted flag.** The Business Specification describes *behavior* ("automatically marked Needs Review"), but this project has no event/pub-sub mechanism (System-Architecture.md's Modular Monolith style is direct, synchronous, in-process function calls only) — there is no way for School Schedule Management or Class Management to *push* a notification the moment a Working Day, Shift, or GradeLevel-Shift-membership change occurs. Rather than inventing a first event mechanism for this one feature, or persisting a boolean that could only ever be refreshed at the same touchpoints a pure comparison would already need to run at anyway, this design stores only `availablePeriodsAtSave Int` on the `WeeklySubjectAllocation` header (a snapshot of the calculated total at the moment of last save) and derives "is this Needs Review right now" by re-running the same calculation live and comparing — the identical "derived, never stored" judgment call already applied to Assignment status (Teacher Subject Assignment) and Weekend Days (School Schedule Management). See Backend Design's `isAllocationCurrent` helper and Risks for the one real consequence of this choice (there is no proactive, standing "Needs Review" list independent of a read or a generation attempt touching it).
- **Available weekly teaching periods is never stored as a live, continuously-synced value** — it is computed fresh, every time it is needed (at save-time validation, at Needs-Review comparison, and by Timetable Management's own future generation pre-check), via `classesService.getGradeLevelShift(schoolId, gradeLevelId)` (Class Management's new narrow interface, `docs/06-technical-design/Class-Management.md` v1.7) followed by `schoolScheduleService.getWorkingDays(schoolId)` and `schoolScheduleService.getShiftPeriods(schoolId, shiftId, { status: 'ACTIVE' })` (School Schedule Management's existing, unchanged interface), counting only `TEACHING`-type Periods. This feature never stores a second copy of any Working Day, Shift, or Period data, per its own Business Rule #14.
- **This feature depends on, but does not modify, School Schedule Management** — no schema or interface change is required there; every function this design calls already exists and is already Accepted.
- **This feature depends on Class Management's own not-yet-Implemented "Architecture Update (Grade/Form)"** (`GradeLevel`, `getGradeLevelShift`, `listGradeLevels`, `validateGradeLevel`) — this is a hard, blocking dependency (see Dependencies): this feature's own Implementation cannot begin before that Architecture Update is Implemented, since every `WeeklySubjectAllocation` row references a `gradeLevelId` that does not exist as a real column anywhere in the schema until then.
- This feature exposes a small, narrow public interface for Teacher Subject Assignment and Timetable Management to call, rather than either querying this feature's own tables directly, per Decision-Making-Principles' Feature Ownership and Loose Coupling — see Stable Public Service Interface below.
- **This feature has no responsibility for Lesson creation, Timetable generation, or Teacher assignment of any kind** — its own schema has no reference to `Lesson`, `TimetableVersion`, or `TeacherSubjectAssignment` anywhere; the dependency runs in one direction only (Teacher Subject Assignment and Timetable Management depend on this feature, never the reverse), the same one-directional shape Class Management already established relative to Student Management.

# Database Impact

Conceptual data shape only — field-level schema is a separate Database Design exercise if the Product Owner wants one produced.

## `WeeklySubjectAllocation`

- `id`, `schoolId` (required), `academicYearId` (FK, required), `gradeLevelId` (FK to Class Management's `GradeLevel`, required), `availablePeriodsAtSave Int` (the calculated available-weekly-teaching-periods figure at the moment of last save — a snapshot used only for Needs-Review comparison, never treated as a second source of truth for "what the available figure is right now"), timestamps.
- **`@@unique([schoolId, academicYearId, gradeLevelId])`** — an ordinary unique constraint, not a partial one: unlike `Shift.isDefault`/`Class.isFinal` ("exactly one flagged row"), this is simply "at most one allocation per natural key," which Prisma's schema DSL already expresses directly, no raw SQL needed.
- No `status`/lifecycle column — an allocation is never archived independently; it exists for exactly as long as its owning Academic Year is relevant, and is simply superseded by a fresh allocation when a new Academic Year begins (Business Rule #2's own per-year scoping). There is no "delete an allocation" action in the Business Specification's own Lifecycle.
- Indexing: `@@index([schoolId, academicYearId])` (the most common list/filter query, mirroring Teacher Subject Assignment's own identical index), `@@index([gradeLevelId])`.

## `WeeklySubjectAllocationSubject`

- `id`, `weeklySubjectAllocationId` (FK, required), `subjectId` (FK to Subject Management's platform-wide catalog entity, required — validity of "is this Subject actually assigned to this school" is checked at write time via `subjectsService.isSubjectAssignedToSchool`, never modeled as a stored join reference, the same pattern Teacher Subject Assignment's own `subjectId` reference already established), `weeklyPeriods Int` (required, positive), `doublePeriodRequired Boolean @default(false)`, timestamps.
- **`@@unique([weeklySubjectAllocationId, subjectId])`** — Business Rule #8 ("a Subject may appear at most once within a single allocation"), an ordinary unique constraint.
- Relationship cardinality: `WeeklySubjectAllocation` → `WeeklySubjectAllocationSubject` is one-to-many, `onDelete: Cascade` (a line item has no meaning independent of its owning allocation — the same "child has no independent lifecycle" reasoning already applied to `Section`/`Class` and `Period`/`Shift`, though in this project's own established style, deletion of the parent is not itself a supported action; `Cascade` here is a data-integrity backstop, not a feature this design exposes).
- Indexing: `@@index([weeklySubjectAllocationId])`, since every query is scoped to one allocation.
- Allocation lifecycle (create, correct, and every Needs-Review transition surfaced by a read) is recorded in the platform's shared audit log mechanism, consistent with the standard audit record (Tenant, User, Action, Timestamp) defined in Multi-Tenancy.md.

# API Design

High-level shape only — exact payloads and per-case status codes belong in a separate API Specification if requested.

- REST, versioned under `/api/v1`, per API-Standards.md. Resource name is plural: `/weekly-subject-allocations`, consistent with Naming-Conventions.md's API Endpoints section.
- `GET /weekly-subject-allocations` — list (School-Admin-only), filterable by `academicYearId` (defaults to the school's own Current Academic Year, the same default pattern Teacher Subject Assignment's own list endpoint already establishes) and `gradeLevelId`. Each row in the response includes a freshly-computed `availablePeriodsNow` and a derived `needsReview` boolean (see Architecture) alongside the stored `availablePeriodsAtSave` — never only the stale snapshot.
- `GET /weekly-subject-allocations/{id}` — single record detail (School-Admin-only), including its own line items and the same freshly-computed `availablePeriodsNow`/`needsReview` pair.
- `POST /weekly-subject-allocations` — create (School-Admin-only). Body: `academicYearId` (optional, defaults to Current), `gradeLevelId` (required), `subjects: [{ subjectId, weeklyPeriods, doublePeriodRequired }]` (required, at least one entry). Rejects (422) if the total of `weeklyPeriods` does not exactly equal the calculated available figure at the moment of the request, per Business Rules #6–#7.
- `PATCH /weekly-subject-allocations/{id}` — replace the full `subjects` array (School-Admin-only) — this is a "Reviewing an Existing Allocation" re-save (Business Lifecycle Step 5/6), always replacing the entire line-item set rather than a partial patch of individual lines, since the "total must exactly equal available" rule is only meaningful evaluated over the complete set. `gradeLevelId`/`academicYearId` are immutable after creation (Guard by Construction) — correcting either is "create a new allocation for the correct Grade/Form or Academic Year," not an edit to this one.
- No delete endpoint exists — the Business Specification names no removal action; a Grade/Form's allocation is superseded by a fresh save for the current Academic Year, or simply not recreated for a following Academic Year, never explicitly deleted.
- **No Super Admin oversight route** — the Business Specification's own Permissions section grants Super Admin no role in this feature at all (unlike School Schedule Management, which does grant Super Admin read-only oversight); consistent with that, no `/schools/{schoolId}/weekly-subject-allocations` route is introduced.
- Every endpoint requires a valid JWT and passes through the same Authentication/Authorization middleware chain every other feature already uses; no new authentication mechanism is introduced.

# Backend Design

- New feature module `backend/src/features/weekly-subject-allocations/`, structured per Folder-Structure.md (controller, service, repository, validation, routes, tests).
- **`calculateAvailablePeriods(schoolId, gradeLevelId)`** — the one shared helper every other piece of this design calls, never re-implemented: resolves the Grade/Form's own shared Shift via `classesService.getGradeLevelShift(schoolId, gradeLevelId)` (throwing/returning a clear error if the Grade/Form has no member Classes yet, since there is then no Shift to derive a figure from), then `schoolScheduleService.getWorkingDays(schoolId).length * schoolScheduleService.getShiftPeriods(schoolId, shiftId, { status: 'ACTIVE' }).filter(p => p.type === 'TEACHING').length`.
- **`isAllocationCurrent(allocation)`** — `calculateAvailablePeriods(allocation.schoolId, allocation.gradeLevelId) === allocation.availablePeriodsAtSave`; the single comparison every read path and the generation pre-check both call, per Architecture's "derived, never stored" decision. Returns the freshly-computed figure alongside the boolean, so callers needing to *display* the current figure (not just know whether it drifted) never call `calculateAvailablePeriods` a second time. **(Technical Design Review finding, fixed here — see Change History)** `calculateAvailablePeriods` itself throws when a Grade/Form has zero member Classes (Risks already names this as reachable — every existing allocation's own `GradeLevel` can lose all its member Classes after the fact, via reassignment or archival, entirely independent of anything this feature does). The v1.0 draft let that exception propagate straight out of `isAllocationCurrent`, meaning every `GET` read and every generation pre-check against such an allocation would crash instead of reporting it. Fixed: `isAllocationCurrent` now catches the "no Shift derivable" condition specifically and treats it as an unconditional Needs-Review state (`{ current: false, availablePeriodsNow: null }`) rather than letting the exception reach the controller layer — a Grade/Form with no Classes left to derive a figure from can never be "current" by definition, so this is a correct classification, not merely an error swallowed.
- **`assertAllocationComplete(subjects, availablePeriods)`** — Business Rules #6–#7: sums `weeklyPeriods` across the proposed line items and rejects (422) unless the sum exactly equals `availablePeriods`; rejects a zero, negative, or non-integer `weeklyPeriods` on any line (Business Rule #10); rejects a duplicate `subjectId` across lines (Business Rule #8, also backed by the database's own unique constraint as a secondary layer, the same two-layer discipline this project applies to every uniqueness invariant).
- **`assertSubjectsAssignable(schoolId, subjects)`** — Business Rule #9: each `subjectId` must exist, be ACTIVE, and be currently assigned to the school, via `subjectsService.getSubjectById`/`isSubjectAssignedToSchool`, the identical pattern Teacher Subject Assignment's own `assertSubjectAssignable` already established.
- **`createAllocation(schoolId, { academicYearId, gradeLevelId, subjects }, actingUser)`** — validates `gradeLevelId` via `classesService.validateGradeLevel`, resolves `academicYearId` (defaulting to Current, then validated via `academicYearsService.getAcademicYearById`, the same defaulted-value-still-validated discipline Teacher Subject Assignment's own `academicYearId` default already established), computes `availablePeriods` via `calculateAvailablePeriods`, runs `assertAllocationComplete` and `assertSubjectsAssignable`, then inserts the header (`availablePeriodsAtSave: availablePeriods`) and its line items inside one `prisma.$transaction` (a single-write operation with no cross-row uniqueness race to guard against beyond what the database's own `@@unique` constraints already backstop — no advisory lock is needed here, since there is no "exactly one flagged row among many" invariant of the kind that has needed one elsewhere in this project; a plain unique-constraint violation on `(schoolId, academicYearId, gradeLevelId)` is sufficient and is surfaced as an ordinary 409).
- **`correctAllocation(schoolId, allocationId, { subjects }, actingUser)`** — loads the existing header, re-runs `calculateAvailablePeriods` fresh (not the stored snapshot — re-saving must validate against *today's* real figure, per Business Lifecycle Step 5), then the same `assertAllocationComplete`/`assertSubjectsAssignable` sequence, replaces the entire line-item set (delete-then-recreate inside the same transaction, the simplest correct way to enforce "no duplicate Subject" and "total exactly equals" without a diffing algorithm — a school's own per-allocation Subject count is small, so this is not a performance concern), and updates `availablePeriodsAtSave` to the freshly-computed figure. This single function *is* what resolves a Needs-Review allocation back to current, per Business Lifecycle Step 6 — there is no separate "acknowledge Needs Review" action; saving a valid, complete allocation against today's real figure is the only way out of Needs Review, by construction.
- Cross-feature calls are this feature's only dependencies for validation, per System-Architecture.md's Modular Monolith style: `classesService.getGradeLevelShift`/`getClassById`/`validateGradeLevel`/`listGradeLevels`, `schoolScheduleService.getWorkingDays`/`getShiftPeriods`, `subjectsService.getSubjectById`/`isSubjectAssignedToSchool`/`registerRemovalDependencyCheck`, `academicYearsService.getAcademicYearById`/`getCurrentAcademicYear`.
- **This module registers its own checker against Subject Management's existing dependency-validation extension point — `subjectsService.registerRemovalDependencyCheck('weekly-subject-allocations', checkFn)` — at its own module-load time. (Technical Design Review finding, fixed here — see Change History.)** The v1.0 draft never registered one, even though Teacher Subject Assignment — the closest analogous feature, which also references Subject — already established exactly this defense for exactly this risk (a Subject archived elsewhere silently invalidating this feature's own already-saved reference to it). Without it, Subject Management would allow archiving a Subject that a current `WeeklySubjectAllocationSubject` line still references; `getWeeklyPeriodsForAssignment` would then keep returning a non-null weekly-period figure for a Subject no longer assigned to the school, and Timetable Management's own generation engine would keep scheduling Lessons for it. `checkFn(schoolId, subjectId)` queries for any current `WeeklySubjectAllocationSubject` row referencing that `(schoolId, subjectId)` pair and returns a blocking reason string if one exists, `null` otherwise — the identical shape Teacher Subject Assignment's own registered checker already uses.
- Repository layer is the only code touching Prisma, per Coding-Standards.md.

# Stable Public Service Interface

Per this project's established pattern — the only functions another feature module may call directly, in-process; everything else in this module is private.

- **`getWeeklyPeriodsForAssignment(schoolId, classId, academicYearId, subjectId)`** — returns `{ weeklyPeriods, doublePeriodRequired }` for the matching allocation line, or `null` if no current allocation/line exists for that combination. **(Technical Design Review finding, fixed here — see Change History)** the v1.0 draft's signature took `gradeLevelId` directly, but this function's own stated caller — Timetable Management's generation engine, iterating `TeacherSubjectAssignment` rows — never has a `gradeLevelId` on hand at that call site; a `TeacherSubjectAssignment` carries `classId`, never `gradeLevelId`. As originally designed, the generation engine could not actually call this function with the data available to it. Fixed: the signature now takes `classId`, resolving `classId → gradeLevelId` internally via `classesService.getClassById(schoolId, classId).gradeLevelId` before doing its own lookup — keeping "which Grade/Form does this Class belong to" resolution in the one place that already owns the narrow interface to answer it, rather than pushing that extra hop onto every caller. This is the literal replacement for `TeacherSubjectAssignment.weeklyLessonTarget`/`SubjectSchedulePreference.doublePeriodPreferred` that Teacher Subject Assignment's and Timetable Management's own Technical Design docs will call once each is amended (see Dependencies) — named to make its calling context self-evident at the call site, rather than a generic `getAllocation`.
- **`isSchoolNeedsReview(schoolId, academicYearId)`** — `true` if any `WeeklySubjectAllocation` for that school + Academic Year currently fails `isAllocationCurrent`; `false` otherwise (including when zero allocations exist yet — an empty set cannot be "in conflict" with itself). This is the one function Timetable Management's own generation pre-check calls to enforce Business Rule #13's school-wide block, without needing to know anything about this feature's own schema.
- **`listAllocationsForGradeLevel(schoolId, gradeLevelId, academicYearId)`** — the full set of Subject/period/Double-Period rows for one Grade/Form + Academic Year, or an empty array on a miss — the read shape Teacher Subject Assignment's own future "read from WSA instead of asking again" UI flow will call when a School Admin creates a Teacher-Subject-Class binding, to show which Subjects still have room.
- No future feature may reach into this module's repository or query `WeeklySubjectAllocation`/`WeeklySubjectAllocationSubject` directly — the same Loose Coupling discipline every other narrow interface in this project already enforces.

# Frontend Design

- `web/src/features/weekly-subject-allocation/` (React/Vite/JavaScript), positioned in the Timetable section of the navigation as `Timetable > Weekly Subject Allocation` (the first item, above Generate Timetable), per the Business Specification's own Architecture Position — a navigation-only placement; the module itself is not physically nested under `web/src/features/timetable/`.
- A Grade/Form picker (sourced from `classesService`'s own new `listGradeLevels`-equivalent Web API, added alongside Class Management's own Grade/Form management screen) plus Academic Year picker (defaulting to Current), showing: the calculated available figure, a running total against it, a per-Subject row (Subject picker sourced from the school's own assigned Subjects, a weekly-period number input, a Double Period checkbox), and a save action disabled until the running total exactly matches the calculated figure — the frontend mirrors, but never re-implements, `assertAllocationComplete`'s own arithmetic; the backend's own rejection is still the authoritative gate.
- A Needs-Review badge/banner on any allocation whose `needsReview` field (from `GET`) is `true`, with the freshly-computed `availablePeriodsNow` shown alongside the stale `availablePeriodsAtSave` so a School Admin can see exactly what changed, prompting the same re-save flow `correctAllocation` implements.
- The frontend never re-implements the completeness/duplicate/positive-integer validation, the Needs-Review comparison, or the available-periods calculation itself; it only reflects what the backend returns, per System-Architecture.md's Business Logic Ownership rule.

# Validation Strategy

- All validation happens server-side, in the feature's `validation/` layer, before reaching the service layer — never trust client input, per Coding-Standards.md and API-Standards.md.
- Shape-only in `validation/`: `gradeLevelId`/`academicYearId` (non-empty strings when present); `subjects` (a non-empty array; each entry has a `subjectId` string and a `weeklyPeriods` positive integer; `doublePeriodRequired`, if present, a boolean).
- Data-dependent checks — Grade/Form and Academic Year existence/eligibility; Subject existence/assignment-to-school; the exact-total constraint; no duplicate Subject within the array — all stay in the service layer's assertion helpers, per this project's established validation/service split.
- `PATCH /weekly-subject-allocations/{id}` rejects any field other than `subjects` at the `validation/` layer (Guard by Construction) — `gradeLevelId`/`academicYearId` are immutable after creation.

# Performance Considerations

- Both list/detail endpoints recompute `calculateAvailablePeriods` on every call — a small, bounded, in-process computation (a Grade/Form lookup, a Working Days array, a Shift's own small Period list), not a database aggregate query; no caching is introduced, consistent with this project's "no premature optimization for small, bounded data" precedent (Academic Year Management, Class Management, School Schedule Management all reason identically about their own small datasets).
- An allocation's own line-item count is bounded by a school's own assigned Subject count for one Grade/Form — small (typically fewer than 15); no pagination needed for the nested `subjects` array.
- `schoolId` + `academicYearId` are indexed together, since the most common list/filter query scopes by both, per Database-Standards.md's indexing guidance.

---

# Error Handling

- Consistent with API-Standards.md's status codes: 401/403 for authentication/role failures, 404 for a nonexistent or cross-tenant allocation, 422 for validation and completeness errors, 409 for a uniqueness conflict.
- **422** — an incomplete or over-allocated total (Business Rules #6–#7); a duplicate Subject within the array; a non-positive or non-integer `weeklyPeriods`; a `subjectId` that does not exist, is not Active, or is not assigned to the school; a `gradeLevelId` that does not exist, is Archived, or belongs to a different school; any field other than `subjects` present in a `PATCH` body (Guard by Construction); a Grade/Form with no member Classes yet (no Shift to derive an available figure from).
- **409** — an attempt to create a second allocation for the same `(schoolId, academicYearId, gradeLevelId)` (the database's own unique-constraint backstop, surfaced as a clean conflict rather than a raw database error).
- Errors never expose internal implementation details, per Coding-Standards.md.

The genuine ambiguity this Review resolved on Timetable's own behalf — a missing allocation line contributes **zero** required-lesson units, never a silent default of `1` — shipped exactly as resolved here. # Risks

- **The Class Management "Architecture Update (Grade/Form)" dependency is a hard, blocking prerequisite, not a soft preference.** This feature's own Implementation Planning cannot produce a meaningful task sequence until that Architecture Update has itself cleared Phase 4 (Technical Design Review) and Phase 5 (Implementation Planning) — the same category of cross-feature ordering constraint School Schedule Management's own Technical Design already flagged for `Class.shiftId`, but here the dependency is even tighter: this feature has no schema of its own that doesn't reference `gradeLevelId`.
- **"Needs Review" as a pure derived comparison, never a persisted flag, means there is no standing, proactively-maintained list of "every currently Needs-Review allocation in the platform."** A Super Admin-level cross-school report of Needs-Review allocations (not requested by the Business Specification, and explicitly out of this feature's own scope) would require iterating every allocation and recomputing its own comparison on demand, rather than a simple `WHERE needsReview = true` query. Accepted as the correct trade-off for this feature's own actual, much narrower need (a single school's own generation-time check, and a single school's own list/detail view) — flagged here so a future feature request for such a report does not assume a stored flag already exists.
- **`calculateAvailablePeriods` throws/rejects for a Grade/Form with zero member Classes** (no Shift to derive a figure from) — a genuinely reachable state immediately after Class Management's own migration (the placeholder `"Ungrouped"` `GradeLevel` has members; any *newly created*, empty `GradeLevel` does not until a School Admin assigns a Class to it), and equally reachable later if every one of an already-allocated Grade/Form's own Classes is subsequently reassigned or archived elsewhere. At **create/correct time**, this remains a real, expected edge case whose error handling must surface clearly ("this Grade/Form has no Classes yet") rather than a generic 500 — worth explicit test coverage during Implementation. At **read/Needs-Review-check time**, this exception is now caught by `isAllocationCurrent` itself, per this Review's own finding (see Backend Design) — no longer a risk of an unhandled crash, only a design constraint Implementation must preserve.
- **No advisory lock is used for `createAllocation`/`correctAllocation`.** Unlike Teacher Subject Assignment's and School Schedule Management's own proactively-locked "exactly one flagged row" invariants, this feature's own uniqueness constraint (`schoolId`+`academicYearId`+`gradeLevelId`) is a plain, non-partial unique index with no flag-reassignment race condition of the kind that has needed a lock elsewhere in this project (there is no "unset the old one, set the new one" two-step anywhere in this feature's own write paths) — a concurrent double-create attempt for the same natural key simply collides on the database's own constraint and the second request receives an ordinary 409. This is a deliberate simplicity judgment, not an oversight; revisit only if a future finding shows otherwise.
- **Downstream amendments to Teacher Subject Assignment's and Timetable Management's own Technical Design docs are named here but not yet written** — see Dependencies. This is intentional sequencing (amending an already-Accepted feature's Technical Design before the feature driving that amendment has itself cleared Technical Design Review would risk documenting a design that still changes), not an oversight; both amendments are already scoped precisely enough here that writing them later should require no new design decisions, only transcription.
