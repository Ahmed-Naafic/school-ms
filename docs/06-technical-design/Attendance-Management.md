# Overview

Attendance Management introduces two new attendance-record shapes — `StudentAttendance` and `StaffAttendance` — plus one small supporting model (`SchoolNonWorkingDay`) and one settings model (`AttendanceSettings`). No existing model is modified. The feature is read-heavy on three existing modules (School Schedule Management, Timetable Management, Class/Student Management) and read/write on Account (to resolve role and identity), but owns no write access to any of them.

The central design tension this document resolves is that attendance has two structurally different "who is being marked" shapes — Students (contextualized by a Lesson or a Class-wide checkpoint) and Staff (Teachers, Accountants, Managers — contextualized only by a day) — while sharing one authority/audit pattern (source, recorder, timestamp, correction) across both. The design keeps these as two tables, not one, because their uniqueness shapes and their "who may write" rules are genuinely different; it keeps Staff attendance as one table, not two (Manager→Teacher/Accountant and Admin→Manager), because those two flows are structurally identical and only their source/role combination differs.

# Architecture

## A. Module boundaries

`attendance` becomes a new feature module (`backend/src/features/attendance/`), following this project's established feature-module shape (`*.routes.js`, `*.controller.js`, `*.service.js`, `*.repository.js`, `*.validation.js`, plus route/service test files). It owns the `StudentAttendance`, `StaffAttendance`, `SchoolNonWorkingDay`, and `AttendanceSettings` tables exclusively — no other feature module ever queries them directly, mirroring the Stable Public Service Interface convention already established by Timetable, School Schedule, and Weekly Subject Allocation.

Attendance consumes, but never owns or duplicates:
- **School Schedule Management** — Shifts, Periods (including which Period is the break), working days.
- **Timetable Management** — a Teacher's current Lesson assignment (PUBLISHED version).
- **Class Management** — Class/Section rosters, a Class's assigned Shift.
- **Student Management** — Student identity and `status` (for lifecycle exclusion).
- **Authentication & Authorization** — Account identity, role, and tenant (`schoolId`).
- **Audit Logs** — the shared `recordAuditEvent` utility (`backend/src/shared/audit.js`).

No other feature is expected to consume Attendance Management's own data in this version (Reports/Notifications are explicitly out of scope per the Business Specification) — its Stable Public Service Interface (below) is kept intentionally narrow because nothing currently needs it, not because it is closed on principle.

## B. Roles and authorization

Enforced with this project's existing RBAC middleware pattern (role-check middleware in `*.routes.js`, the same shape as every other feature) — no new authorization mechanism is introduced. Route-level role gates:

| Route group | Allowed roles |
|---|---|
| Teacher Student-attendance record/edit | `TEACHER` |
| Manager Student-attendance record/correct | `MANAGER` |
| Staff self-check-in ("Come") | `TEACHER`, `ACCOUNTANT`, `MANAGER` (**v1.7** — self-service only; see Change History. Replaces the v1.2–v1.6 "Manager staff-attendance record" and "Admin Manager-attendance record" rows below, which no longer exist.) |
| Manager-recorded Teacher/Accountant arrival ("Come") | `MANAGER` (**v2.0, new** — a narrower, explicit re-addition alongside self-check-in above; never `SCHOOL_ADMIN`-recording-Manager, which remains self-service only.) |
| Manager `EXCUSED` correction (Teacher/Accountant) | `MANAGER` |
| Admin `EXCUSED` correction (Manager) | `SCHOOL_ADMIN` |
| Read (own recorded/subject records, scoped views) | `TEACHER`, `MANAGER`, `SCHOOL_ADMIN` (each scoped to what Business Rules/Permissions allow them to see — see Section R) |

`MANAGER` here assumes ACR-010's role is implemented as part of this feature's own Phase 1/2 (see Implementation Plan) — Attendance Management is the first, and currently only, consumer of that role, so its RBAC middleware entry and Prisma `UserRole` enum value are added as part of this feature, not a prerequisite delivered separately.

**`SUPER_ADMIN` is never an allowed role on any Attendance route — this is total, definitive, and by design (Business Rule #34), not merely "not yet defined."** `STUDENT` is likewise never allowed on any route. Both are excluded from every recording, correction, and read path. This must be implemented as an explicit denial, not an absence: Attendance's role-check middleware is an **allow-list** (`TEACHER`, `MANAGER`, `SCHOOL_ADMIN`, scoped per route per the table above) evaluated before any tenant/`schoolId` check runs, so `SUPER_ADMIN` is rejected purely on role, before its normal platform-wide cross-school allowance (Authentication-and-Authorization.md Business Rule #4) ever gets a chance to apply. See Section C for why this ordering matters, and Section R for the route-level guarantee this produces.

Every recording/correction service function independently re-validates the actor's role and, for Teacher/Manager Student-attendance writes, the actor's actual current assignment (Section D below) — never trusting the route-level gate alone, matching this project's existing defense-in-depth convention (e.g. Timetable's own lock/assignment checks inside the service layer, not just the route).

## C. Tenant isolation

Every table below carries its own `schoolId` (denormalized, not derived through a join at query time) — the same convention `Lesson`, `Student`, and `Teacher` already use, chosen over relying solely on a joined parent's `schoolId` because attendance queries are frequently filtered and indexed directly on `schoolId` (daily/period listing, reporting) and a join-only tenant check would cost an extra hop on every one of them. Every repository function accepts and applies `schoolId` as a mandatory filter — never optional — the same "no schoolId, no query" convention every existing feature repository already follows. Every cross-module read (Lesson, Period, Student, Account) is additionally validated to belong to the same `schoolId` as the acting user before use, the same pattern Timetable's own `getTeacherTimetable` already applies to its own joins.

**Tenant scoping is deliberately not the mechanism that keeps `SUPER_ADMIN` out.** Authentication & Authorization's platform-wide default is that Super Admin is the *one* role exempt from the "own school only" check (Authentication-and-Authorization.md Business Rule #4) — if Attendance's authorization stack applied only a tenant check, a generic implementation of that default would let Super Admin through for *any* `schoolId`, exactly the "indirect access through a school context" the Product Owner explicitly ruled out. Attendance Management's middleware therefore runs the role allow-list (Section B) as an independent, prior gate — `SUPER_ADMIN` is rejected on role alone, before the request ever reaches the tenant-scoping logic that would otherwise wave it through. This is the one place in this feature that deliberately does not reuse Authentication & Authorization's generic cross-school exemption; the divergence is intentional and recorded here so it is never "fixed" back to the platform default by a future refactor.

## D. Domain/entity model

Four new models, no changes to any existing model:

**`StudentAttendance`** — one row per (Student, calendar date, context), where context is either a specific Lesson (Teacher-recorded) or a Class-wide checkpoint (Manager-recorded). See Section E/F/G for exactly how date/context is resolved, and Section U for the two uniqueness shapes this single table must enforce.

**`StaffAttendance`** — one row per (staff Account, calendar date), covering both Manager→Teacher/Accountant and Admin→Manager. See Section H.

**`SchoolNonWorkingDay`** — one row per one-off non-working calendar date (holiday, closure), per school. See Section P.

**`AttendanceSettings`** — one row per school, holding two categories of configuration: (1) the minutes/hours-based window values the Business Specification leaves as Open Questions (Teacher edit window, Teacher grace period, Manager correction window, Admin correction window); (2) **(v1.3)** the three staff-attendance-specific time-of-day settings — start time, late threshold, absence cutoff — that drive automatic "Come" status derivation (Business Lifecycle §11, Business Rules #35–39). Mirrors the existing one-row-per-school `SchoolOptimizationSettings` precedent. See Sections H and K. Replaces this model's own v1.0 `staffAttendanceOpeningOffsetMinutes` field (an unenforced stub, per the v1.0 Risks section) with three concrete `HH:mm` time fields — the offset-from-Shift-start idea it stood in for is superseded entirely by v1.3's explicit, Shift-independent configured times.

Two new enums:

```
enum AttendanceStatus {
  PRESENT
  ABSENT
  LATE
  EXCUSED
}

enum AttendanceSource {
  TEACHER
  MANAGER_BEFORE_BREAK
  MANAGER_AFTER_BREAK
  MANAGER_STAFF_ATTENDANCE
  ADMIN_MANAGER_ATTENDANCE
}
```

`AttendanceStatus` is shared by both `StudentAttendance` and `StaffAttendance` — the Business Specification defines the same four values for both (Business Rule #5), so one enum, not two, avoids a duplicate definition of an identical value set. `AttendanceSource` is a single enum spanning both tables for the same reason (Business Rule #21 names all five sources together as one concept); each table's own check constraint/service-layer validation restricts which subset of values is legal for that table (Student: `TEACHER`/`MANAGER_BEFORE_BREAK`/`MANAGER_AFTER_BREAK`; Staff: `MANAGER_STAFF_ATTENDANCE`/`ADMIN_MANAGER_ATTENDANCE`), rather than defining two smaller enums that would need to stay manually in sync with the same five source names used throughout the Business Specification.

No `UserRole` enum value beyond the already-approved `MANAGER` (ACR-010) is needed. No dedicated `Manager` profile model is introduced — mirroring the existing `Accountant` precedent (represented purely as `Account.role = ACCOUNTANT`, no profile table), a `Manager` is represented purely as `Account.role = MANAGER`, referenced directly by `Account.id` everywhere this design needs "the Manager." This keeps the model consistent with the one profile-table precedent that does exist (`Teacher`/`Student`) being reserved for roles with their own employment/enrollment lifecycle data — Manager, like Accountant, has none.

## E. Attendance session model

An "attendance session" is never a materialized row — it is always a derived comparison, the same "derived, never persisted" pattern this project already uses for WSA's Needs-Review comparison, TSA's Active/Ended state, and Academic Year's label. Concretely:

- A **Teacher session** is the pair (Lesson, calendar date), valid only when: the date's weekday equals `Lesson.dayOfWeek`; the date is a genuine school day for the Lesson's Shift (Section P); the owning `TimetableVersion.status = PUBLISHED` (Section F); and `Lesson.status = ACTIVE`. No row is ever created to represent this pair existing — it is computed on read, from Timetable Management's own data, exactly the same way the Teacher's timetable itself is already computed.
- A **Manager checkpoint session** is the tuple (Class, calendar date, checkpoint), valid only when the date is a genuine school day for that Class's own Shift (Section P). Likewise never materialized.

Whether a session has been acted on is answered by checking for the presence of a matching `StudentAttendance` row (by Lesson+date+student, or by Class+date+checkpoint+student) — its absence is the `NOT_RECORDED` state (Section N), never a separately stored flag.

## F. Lesson/period linkage

`Lesson.dayOfWeek` is a recurring weekday, not a calendar date (confirmed directly from the schema) — so a Teacher-recorded `StudentAttendance` row must key on **(Lesson, specific calendar date)**, never on `Lesson` alone; the same Lesson recurs every week, and each week's occurrence needs its own independent attendance outcome per student.

Resolving "what is the Teacher's current lesson right now" reuses `timetableService.getTeacherTimetable(schoolId, teacherId, { versionType: 'PUBLISHED' })` unmodified (Section T) — Attendance Management never re-derives or duplicates lesson-assignment logic, and deliberately requests the `PUBLISHED` version, never `DRAFT`, since a Draft timetable is a working proposal, not yet the school's authoritative schedule a Teacher should be marking real attendance against.

## G. Manager Before Break / After Break model

A checkpoint's covered Periods are derived, not stored, from School Schedule Management's own `Period` data: for the applicable Class's Shift, the covered set is every `Period` where `type = TEACHING` and `startTime` is before (Before Break) or after (After Break) the Shift's own `Period` where `type = BREAK`. This directly reuses the schema's existing `PeriodType.BREAK` marker — no new "break time" concept is introduced, and no assumption is hardcoded about which Period is the break; it is read from whichever Period the school itself configured as `BREAK` for that Shift.

This computation assumes exactly one `BREAK`-type Period per Shift, matching Assumption Requiring Approval #1 in the Business Specification (still open). If a Shift has zero or more than one `BREAK` Period, the checkpoint computation is undefined in this version and must reject with a clear configuration error rather than guess — this is flagged as a hard dependency on that Assumption being resolved before Implementation begins on the Manager checkpoint phase (see Implementation Plan, Phase 4).

A Manager-recorded `StudentAttendance` row does not separately store which Periods it covers — the covered set is always re-derived from current School Schedule Management configuration at read time. This is a deliberate implementation-mechanism choice (the Business Specification does not mandate storage either way): storing a snapshot would let a later Period/Shift edit silently desynchronize historical attendance from the schedule it was actually recorded against, while re-deriving keeps exactly one source of truth. The trade-off — a retroactive Shift/Period edit could change how an old checkpoint record's "covered Periods" are reported — is accepted as consistent with how this project already treats Shift/Period as the live source of truth for Timetable itself.

## H. Staff attendance model

**(v1.3 — supersedes the original manual-status design; v1.7 — supersedes v1.2–v1.6's Manager/Admin-recorded "Come" with self-recorded "Come"; see Change History.)** One table, `StaffAttendance`, for both the Teacher/Accountant relationship (Manager's correction jurisdiction) and the Manager relationship (Admin's correction jurisdiction), since both are structurally identical: one row per (staff Account, calendar date), a status, a recording Account/role/timestamp, and optional correction fields. The two flows are distinguished purely by `source` (`MANAGER_STAFF_ATTENDANCE` vs. `ADMIN_MANAGER_ATTENDANCE` — **v1.7 note:** these names now identify correction jurisdiction, not who recorded the row; see Section J) and by which role is legal in `staffRole` for each source — enforced at the service layer, not by two separate tables, matching this project's consistent convention of keeping the schema layer purely structural and pushing role-shaped rules into the service layer (e.g. Enrollment's `sectionId`/`academicYearId` validity). No schema change from v1.2, and none from v1.7 either — `status` and `recordedAt` already exist and already meant "server-derived, self-captured at write time" (Section H.1); v1.7 changes *who is allowed to trigger the write* (the account itself, never a third party), not the table shape, the status derivation, or the correction/audit fields.

`staffRole` (a denormalized `UserRole` snapshot, not a live join to `Account.role`) is stored because a staff member's role could theoretically change over time (e.g. a rare Manager→Teacher move); the attendance record must always reflect the role they held on the day it describes, never the account's current role.

`recordedAt` **is** the arrival time — Business Lifecycle §11's "arrival timestamp" and this field are the same value; no separate `arrivalTime` column is introduced. This is a deliberate reuse, not a coincidence: `recordedAt` already means "the moment this row was created, server-captured" (Section J), and a "Come" row is created at the exact moment the arrival happens — the two concepts collapse into one field by construction. A correction (Section L) never changes `recordedAt`, so a later `EXCUSED` correction still shows the original arrival time (or lack of one) it's correcting, per Business Rule #13.

### H.1 — Recording arrival ("Come") — self-recorded (v1.7)

**A staff member records their own arrival.** `POST /attendance/staff/me/come` (Section R) always operates on `req.user`: `accountId`, `role`, and `schoolId` come from the authenticated session, exactly as every other "act on my own account" endpoint in this project does — there is no client-suppliable target account for this route. **(v2.0 note — this route itself is unchanged; a *separate*, explicit route now also exists for a Manager to record a Teacher's/Accountant's arrival, Section H.1b below. This route continues to accept no target account of any kind, ever.)** **(v1.8)** The same holds for *which day* the arrival counts against: `date` is likewise never client input — it is always `todayDateStr()`, the current school date computed server-side, per Business Rule #40. The controller for this route does not read `req.body` at all, so a `date`, `recordedAt`, or `status` field in the request is not merely rejected — it is never inspected in the first place. This was already true when v1.7 shipped; v1.8 makes it an explicitly named guarantee with its own dedicated test coverage, after a report (not reproduced against this implementation) claimed a client could backdate or postdate a self-recorded arrival. The service layer:

1. Resolves the school's `AttendanceSettings` row. If none exists, or any of the three staff-timing fields (Section K) is unset, the action is rejected (422) — the system never guesses a default (Business Rule #38).
2. Rejects (422) if the current **Mogadishu** wall-clock time (Business Rule #43, Section H.4) is before the configured start time. **(v2.1 — previously compared raw UTC; see Section H.4 and Change History.)**
3. Captures `now = new Date()` server-side — this real absolute instant becomes `recordedAt`, unchanged (Business Rule #43 does not affect what is stored, only what is compared). `date` (the calendar date portion) is `now`'s **Mogadishu** calendar date (Section H.4), not its UTC calendar date. The request body carries no date, time, status, or target-account field at all — there is nothing for a client to supply here (Business Rules #38–39, Validation Rule #4).
4. Derives `status` by comparing `now`'s **Mogadishu** time-of-day (Section H.4) against the late threshold (itself entered as Mogadishu time, Section K): at or before → `PRESENT`; after → `LATE` (Business Rule #35). No comparison against the absence cutoff happens here — a genuine arrival is recorded as `LATE` no matter how late (Business Lifecycle §11).
5. Determines `source` and `staffRole` from `req.user.role` alone (never client input): `TEACHER`/`ACCOUNTANT` → `source = MANAGER_STAFF_ATTENDANCE` (Manager's correction jurisdiction); `MANAGER` → `source = ADMIN_MANAGER_ATTENDANCE` (Admin's correction jurisdiction). `SCHOOL_ADMIN` is never a valid caller (Business Rule #33 — structurally enforced by the route's own role gate, Section B, not merely by this branch).
6. Creates the `StaffAttendance` row with `recordedByAccountId = req.user.id` (always the subject themselves, by construction). The existing `@@unique([staffAccountId, date])` constraint (Section U) rejects a second "Come" for the same person/day with a 409, exactly as it already did for the v1.2–v1.6 third-party-recorded path — this constraint's meaning is unchanged, only who triggers a write against it.

**What replaced what (v1.7):** `POST /attendance/manager/staff/:accountId/come` and `POST /attendance/admin/managers/:accountId/come` — the v1.2–v1.6 routes where a Manager or Admin clicked "Come" *for* a specific `:accountId` — were removed in v1.7, on the reasoning that self-recording was the only path going forward. **(v2.0)** That reasoning has been partially revisited: a route matching the first of the two shapes (Manager recording a Teacher's/Accountant's arrival) has been reintroduced, deliberately, as its own explicit action — see Section H.1b. `POST /attendance/admin/managers/:accountId/come` (Admin recording a Manager's arrival) remains removed and out of scope for v2.0; only the Manager↔Teacher/Accountant relationship regained this capability.

### H.1b — Recording arrival ("Come") — Manager-recorded, for a Teacher/Accountant (v2.0, new)

**(v2.0 — restores a narrower form of the pre-v1.7 Manager-recorded "Come," per Business Rule #42; see Change History.)** `POST /attendance/manager/staff/:accountId/come` targets a specific `:accountId`, unlike H.1's self-only route — this is the one deliberate exception, scoped exactly to the Manager↔Teacher/Accountant relationship, to H.1's "no client-suppliable target account" framing; that framing still holds absolutely for the self-check-in route itself and for the Manager's own attendance (Admin never gets an equivalent route). The service layer (`recordManagerStaffArrival(schoolId, accountId, actingUser)`):

1. Resolves `:accountId` against `authService.listAccountsByRole(schoolId, ['TEACHER', 'ACCOUNTANT'])` — the same target-resolution pattern `markStaffExcused` (Section H.2) already uses for its own create-branch. Not found (wrong role, wrong school, or nonexistent) → 422 `ValidationError`, the identical shape and message `markStaffExcused` already returns for an invalid target — deliberately reused, not a new error shape. This is the structural mechanism that makes "a Manager can never record arrival for another Manager or for an Admin" true in code: neither role ever appears in that role list.
2. Resolves the school's `AttendanceSettings` row exactly as H.1 step 1 — 422 if unconfigured.
3. Rejects (422) if the current Mogadishu wall-clock time is before the configured start time — identical to H.1 step 2 (Business Rule #43, Section H.4).
4. Captures `now = new Date()` server-side — `recordedAt` is this real absolute instant, unchanged; `date` is `now`'s Mogadishu calendar date. Exactly as H.1 step 3. The request has no body at all; the only client input is the `:accountId` path segment itself.
5. Derives `status` exactly as H.1 step 4, from `now`'s Mogadishu time-of-day (`deriveStaffAttendanceStatus`, shared, unduplicated).
6. Creates the `StaffAttendance` row with `staffAccountId` = the *target* account, `staffRole` = the target's role, `source = MANAGER_STAFF_ATTENDANCE` (the same source self-recorded Teacher/Accountant arrival already uses — this is what lets the Manager's existing `EXCUSED`/`Unexcuse` authority (Section H.2) reach a Manager-recorded row exactly as it already reaches a self-recorded one, with no new authorization branch needed), `recordedByAccountId` = the **acting Manager's** id, `recordedByRole = MANAGER`. The existing `@@unique([staffAccountId, date])` constraint (Section U) rejects with 409 if that staff member already has a record for today, from either path — self-recorded or Manager-recorded, indistinguishably, since the constraint keys only on `(staffAccountId, date)`, not on who created the row.
7. Records a distinct audit event, `attendance.staff.manager_arrival_recorded` (Section V) — kept separate from H.1's `attendance.staff.arrival_recorded` so a Manager-recorded arrival is distinguishable from a self-recorded one in the audit trail without inferring it from `recordedByAccountId != staffAccountId`. `metadata` carries both `staffAccountId` (the subject) and the audit row's own `userId` (the acting Manager, i.e. the recorder) — the same two-distinct-facts guarantee Business Rule #22 requires.

No date is ever accepted from the client for this action, identically to H.1 (Business Rule #40, extended to this path by Business Rule #42) — reaching a past date remains exclusively the Manager's `EXCUSED`/historical-correction authority (Section H.2), never this action.

### H.2 — Marking or un-marking `EXCUSED`

**(v1.6 — replaces v1.5's "Correct" action with a narrow "Unexcuse" action. v1.9 — splits Excuse itself into a today-only normal action and a separate, explicitly-authorized historical-correction action; see Change History for both.)** Four actions:

**Come** (Section H.1) — create-only, server-derived `PRESENT`/`LATE`. Unchanged.

**Excuse** — a Manager (for Teacher/Accountant) or Admin (for Manager) one-click shortcut that always targets `EXCUSED` for **today only** (v1.9, Business Rule #41 — a client-supplied `date` other than today is rejected with 422; omitting it defaults to today), whether or not a row already exists for `(staffAccountId, today)`:
- If a row exists (whether from a "Come" or a prior Excuse), **corrects** it — `status → EXCUSED`, `correctedByAccountId`/`correctedAt` set, `recordedBy*`/`recordedAt` untouched.
- If no row exists — the derived-`ABSENT`/`NOT_RECORDED` case (Section H.3) — **creates** a fresh row directly: `status = EXCUSED`, `recordedByAccountId` = the acting Manager/Admin, `recordedAt` = now (the moment the mark was made, not an arrival — there was no arrival), `correctedBy*` left null.

This create branch is deliberately still EXCUSED-only — `PRESENT`/`LATE` can only ever originate from a genuine "Come," and `ABSENT` is never manually created (Business Rule #36). This is the restriction Business Rule #37 actually describes.

**Excuse (historical correction)** (v1.9, new) — the *only* path to applying `EXCUSED` against a date other than today. A Manager (for Teacher/Accountant) or Admin (for Manager) action requiring an explicit `date` in the body (never defaulted, unlike the normal action) that must be strictly **before** today — today itself is rejected (422: "use the normal Excuse action") and any future date is rejected (422: "future dates are never allowed"). Once the date passes that gate, the mutation is byte-for-byte the same create-or-correct-to-`EXCUSED` logic as the normal action above (`markStaffExcused`, Section T — never duplicated), the only differences being which dates are legal and which audit action is recorded (below).

**Unexcuse** (v1.6, replaces v1.5's "Correct") — a Manager/Admin action that requires an *existing* row currently `status = EXCUSED` (404 if no row exists; 422 if the row exists but isn't currently `EXCUSED` — there is nothing to un-excuse). It never accepts a client-supplied target status — the outcome is always a full reversal of the Excuse action, computed entirely server-side from the row's own stored data:
- If `correctedByAccountId` is set (a genuine "Come" arrival was excused — Excuse is, by construction, the only correction path that can ever set it), **recompute** `PRESENT`/`LATE` from that arrival's own untouched `recordedAt`, read as its **Mogadishu** time-of-day (Section H.4; **v2.1** — previously read as raw UTC), against the configured late threshold (`deriveStaffAttendanceStatus`, Section H.1) and clear `correctedByAccountId`/`correctedAt` back to null — the row returns to exactly the state it was in before the mistaken Excuse.
- If `correctedByAccountId` is null (Excuse created this row fresh — no arrival ever happened), **delete** the row outright, restoring the derived `ABSENT`/`NOT_RECORDED` read-time state (Section H.3).

**(v1.9)** `Unexcuse`'s own date is deliberately left unrestricted — it only ever operates on a row that already exists (404 otherwise), so unlike Excuse it cannot fabricate arbitrary historical or future data; the risk this fix addresses does not apply to it, and it is unchanged by this version.

This is the only way a mistaken `EXCUSED` click is undone. There is no general-purpose "Correct to any status" capability for staff attendance, unlike Student attendance's Section L — a Manager/Admin can never manually select `PRESENT`, `LATE`, or `ABSENT` for a staff member, at any point, for any reason (Business Rule #37, re-amended).

All four go through the same `@@unique([staffAccountId, date])` constraint.

### H.3 — Deriving `ABSENT` and `NOT_RECORDED` at read time

**Never a stored value.** Every read that reports a staff member's status for a date computes it live:

1. If a `StaffAttendance` row exists for `(staffAccountId, date)` → return its `status` and `recordedAt` as `Time` (Business Rule #36's "no arrival time" clause does not apply here — a row always means *some* arrival or explicit mark happened).
2. Else, if the real absolute instant `date@absenceCutoff` — `absenceCutoff` read as **Mogadishu** wall-clock time, converted to the real instant it refers to (Section H.4; **v2.1** — previously constructed as if `absenceCutoff` were itself UTC) — has already passed → report `ABSENT`, `Time: null`.
3. Else → report `NOT_RECORDED` (the window is still open; "Come" is still possible).

This is the same "derived, never persisted" pattern Section N already established for `NOT_RECORDED` generally — v1.3 adds a second derived outcome (`ABSENT`) to the same computation, gated by the absence cutoff instead of by "does any row exist." No background job, cron, or scheduled task ever runs to "convert" a pending staff member into a stored `ABSENT` row — the derivation re-runs on every read, for any date, past or present, and is therefore always consistent with the current `AttendanceSettings` configuration (a later change to the absence cutoff reclassifies historical un-recorded staff-days consistently, the same trade-off Section G already accepts for retroactive Period/Shift edits).

### H.4 — Mogadishu business-time helpers (v2.1, new — fixes a real, live-reported bug)

**Business Rule #43: this application's operating timezone is permanently Africa/Mogadishu (UTC+3, no DST) — a platform-wide constant, never a School setting, never configurable.** Staff Attendance Timing Settings (Section K) are entered and interpreted as Mogadishu wall-clock time. Before this version, every "what time is it right now" computation in Sections H.1/H.1b/H.2/H.3 read `Date#toISOString().slice(...)`, which is always UTC, regardless of the server process's own operating-system timezone. Because the school this system serves operates in Mogadishu (UTC+3), this produced a systematic 3-hour lag between the wall-clock meaning a School Admin typed into the settings screen and what the code actually compared against — e.g. a configured start time of "06:00" (meant as 6 AM Mogadishu) effectively did not open until 09:00 Mogadishu (06:00 UTC), and "Staff attendance has not opened yet for today" could be shown at 07:39 AM Mogadishu even though the school's own intended opening time (6 AM) had already passed.

**Fix:** four small helper functions in `attendance.service.js`, added alongside — not replacing — the existing UTC-based `toDateOnly`/`dayOfWeekFor`/`nowTimeString`/`todayDateStr` helpers (Section T), which remain exactly as they were and continue to back Teacher/Manager **Student** attendance's current-lesson and working-day resolution, deliberately out of scope for this fix:

- `mogadishuTimeString(date)` — the `"HH:mm"` a Mogadishu wall clock would show for a given real instant, via `Intl.DateTimeFormat('en-CA', { timeZone: 'Africa/Mogadishu', hourCycle: 'h23', hour: '2-digit', minute: '2-digit' })`. Used for "is it past the start/late-threshold time" comparisons (H.1 steps 2/4, H.1b steps 3/5) and for reinterpreting an already-stored `recordedAt`'s time-of-day (H.2's Unexcuse recompute).
- `mogadishuDateStr(date)` — the `"YYYY-MM-DD"` a Mogadishu wall clock would show for a given real instant, via the same `Intl.DateTimeFormat` approach with date-only fields. Used for `date` on a newly-created `StaffAttendance` row (H.1 step 3, H.1b step 4) and for "today" in the Excuse date-scope gates (`assertTodayOnly`/`assertPastDateOnly`, Section H.2) — so a record's "today" is the same Mogadishu calendar day regardless of which Staff Attendance action produced or reads it.
- `mogadishuOffsetMinutes(date)` — the zone's actual UTC offset at a given instant, computed by formatting that instant through the Mogadishu formatter and re-interpreting the resulting digits as if they were themselves UTC, then diffing against the real instant. This is the standard `Intl`-only technique for a named zone's offset, used so this stays correct against the real IANA tzdata rather than assuming a hardcoded `+180` that could go stale — Africa/Mogadishu has had a stable +03:00 offset with no DST transitions since 1957, but this code verifies that against the runtime's own tzdata rather than hardcoding the assumption.
- `mogadishuWallClockToInstant(dateStr, timeStr)` — the reverse direction: a `"YYYY-MM-DD"` date and `"HH:mm"` time, both meant as Mogadishu wall-clock (e.g. a configured absence cutoff on a specific date), converted to the real absolute instant they refer to, via `mogadishuOffsetMinutes`. Used only in H.3's `ABSENT` derivation, which must compare a wall-clock setting against `new Date()` (a real instant).

**No new dependency.** All four use only the built-in `Intl` API, already relied on elsewhere in this codebase's build/runtime environment (Node's ICU is complete by default) — no `moment-timezone`/`luxon`/`date-fns-tz` package was added.

**What did not change:** every stored timestamp (`recordedAt`, `correctedAt`, `AuditLog.createdAt`, etc.) remains a real, absolute, timezone-agnostic instant in Postgres, exactly as before (Business Rule #39 is completely unaffected — the arrival instant is still always server-captured, never client-supplied). Only the *business-time interpretation* of "now," or of an already-stored instant's time-of-day, changed. `AttendanceSettings`' own TIME columns (`staffAttendanceStartTime`/`staffAttendanceLateThreshold`/`staffAttendanceAbsenceCutoff`) are read exactly as before, via the existing `formatTimeField` (Section T) — those are naive `HH:mm` digit strings with no timezone concept of their own (a Postgres `TIME` column, anchored at `1970-01-01`), and reading them back needed no change; what changed is what those digit strings are *compared against*.

## I. Manager attendance — self-recorded, School Admin correction jurisdiction

Uses the same `StaffAttendance` table (Section H) with `source = ADMIN_MANAGER_ATTENDANCE`, `staffRole = MANAGER`. **(v1.7 — retitled and rewritten; see Change History.)** The Manager records their own arrival via the identical self-recorded "Come" mechanism as Section H.1 — `recordedByRole = MANAGER` (the Manager themselves), never `SCHOOL_ADMIN`. The Admin's role is limited to the `EXCUSED` correction mechanism (Section H.2) — `correctedByRole = SCHOOL_ADMIN` only ever appears in the `correctedBy*` fields, never `recordedBy*`. The service layer still enforces, independent of any client input: only a genuine `MANAGER` account can create a row with `staffRole = MANAGER`; only a genuine `SCHOOL_ADMIN` (for that Manager's own `schoolId`) can correct one; and — critically — no service function, no route, and no valid `staffRole` value can ever create a `StaffAttendance` row for an Admin (this is the structural mechanism that makes Business Rule #33 true in code, not just in the Business Specification).

## J. Attendance source/recorder/audit fields

Every row in both `StudentAttendance` and `StaffAttendance` carries the same authority/audit field group, so "who is this about" and "who recorded/corrected it" are always two distinct, independently readable facts (Business Rule #22):

- `recordedByAccountId`, `recordedByRole` (snapshot), `recordedAt` — set once, at creation, **never overwritten** by a later correction (Business Rule #13). **(v1.7)** For `StaffAttendance` specifically, `recordedByAccountId` is now always the same account the row is *about* — self-recording (Section H.1) means "who recorded it" and "who this is about" are the same fact for the initial write, though they remain two independently-readable fields (never collapsed into one column); a later `EXCUSED` correction is what actually exercises the "recorder ≠ corrector" distinction for staff rows.
- `correctedByAccountId`, `correctedAt` — both null until the first correction; updated (not appended) on each subsequent correction, since the Business Specification requires preserving the *original* recording, not a full chain of every intermediate correction — a full chronological trail of every correction event, if ever needed beyond "original vs. most recent," lives in the shared Audit Log (Section V), not as additional row-versioning columns here.
- `source` (`AttendanceSource`) — set once at creation, never changed by a correction (a correction changes `status`/`correctedBy*`, never who originally recorded or through which channel).
- `status` (`AttendanceStatus`) — the current, corrected-if-applicable value.

## K. Teacher editing window and Staff Attendance Timing Settings

**Teacher editing window** (unchanged from v1.2): the exact window value is an approved Open Question, not resolved by this document (per the Business Specification and per the explicit instruction not to invent one). The mechanism, however, is fixed here: `AttendanceSettings` (Section D) holds `teacherEditWindowMinutes` (nullable — null means "use the system default", the same override-with-fallback pattern already implicit in how e.g. `SchoolOptimizationSettings` rows are seeded with defaults at school creation). The service layer computes "is this still editable" by comparing the current time against `Lesson.period.endTime` (or the session's date+Period boundary) plus the resolved window.

**Staff Attendance Timing Settings (v1.3)** — three new `AttendanceSettings` fields, each an `HH:mm` time-of-day value (same wire/storage convention School Schedule Management already established for `Shift`/`Period` times — a native Postgres `TIME` column, formatted to/from an `"HH:mm"` string at the service boundary, per `school-schedule.service.js`'s own `timeStringToDate`/`dateToTimeString` precedent, reused here rather than reinvented):

- `staffAttendanceStartTime` — before this, "Come" is rejected (Section H.1 step 2).
- `staffAttendanceLateThreshold` — the `PRESENT`/`LATE` boundary (Section H.1 step 4).
- `staffAttendanceAbsenceCutoff` — the point after which an un-recorded staff member reads as `ABSENT` (Section H.3).

All three are nullable, and — deliberately unlike the minutes-based window fields above — **null does not mean "use a system default."** There is no system default for these three (Business Rule #38 rejects the exact value being invented); null means "not yet configured," and every "Come"/derivation computation must treat that as a hard stop (422 for `Come`; `NOT_RECORDED` never resolving to `ABSENT` for the derivation, since there is no cutoff to compare against — Edge Cases). This is a genuinely different null-handling contract from `teacherEditWindowMinutes` immediately above it in the same table, and is called out explicitly here so a future reader does not assume the two behave alike.

**(v2.1) All three `HH:mm` values are entered and interpreted as Africa/Mogadishu wall-clock time (Business Rule #43) — not UTC, and not whatever timezone the server process's own OS happens to be configured with.** The stored `TIME` column itself carries no timezone information (Postgres `TIME` never does) — the digits are read back exactly as entered (`formatTimeField`, unchanged); the Mogadishu interpretation lives entirely in what "now" is computed as when comparing against them (Section H.4). This is a fixed, platform-wide constant, not a per-school configuration — there is no timezone field anywhere in `AttendanceSettings` or elsewhere in this feature, and none is planned; see Business Rule #43 for why (this system is currently scoped to Mogadishu, Somalia only).

These settings are shared by **both** staff-attendance flows — Manager→Teacher/Accountant and Admin→Manager use the identical three values, per the Business Specification's own "same arrival-time/status concept" framing; there is no separate configuration for Manager-attendance timing.

## L. Manager correction behavior

A Manager corrects a `StudentAttendance` row (whether originally Teacher- or Manager-recorded) by updating `status`, `correctedByAccountId`, `correctedAt` on the existing row — never by deleting and re-inserting, which would destroy the original `recordedBy*`/`source` attribution (Business Rule #13). The correction is authorized only when the Manager has authority over that record's checkpoint context (i.e., any Student-attendance row for a Class/date the Manager could themselves record against — Business Rule #7's "all Classes, all Students" authority extends naturally to correction, since no narrower correction-scope rule exists). Every correction additionally calls `recordAuditEvent` (Section V) with both the prior and new status in `metadata`, so the full correction history remains reconstructable even though the row itself only holds the most recent correction.

## M. Lock/authority behavior after Manager attendance

The moment a Manager `StudentAttendance` row exists for (Class, date, checkpoint) covering a given Student, the service layer must reject any Teacher write attempt for a Lesson at a Period within that checkpoint's covered set, for that same Student and date (Business Rules #10–#11). Implementation: before accepting a Teacher-recorded write, the service checks for an existing Manager-sourced `StudentAttendance` row for the same `(studentId, classId, date)` whose `source`'s covered-Period set (Section G) includes the target Lesson's `periodId`. If found, the write is rejected with a clear "recorded by Manager, read-only" error (Section W) — the Teacher retains read access to that data through the ordinary read endpoints, never through the write path. This check is re-run at write time, not cached, so a Manager checkpoint recorded after a Teacher already started viewing the page is still correctly enforced.

## N. NOT_RECORDED handling

`NOT_RECORDED` is never a value of `AttendanceStatus` and is never written to any row (Business Rules #5, #25). It is computed purely by absence: for a given session (Section E), if no matching `StudentAttendance` row exists, every read endpoint that lists a roster's attendance for a date reports that Student as `NOT_RECORDED` in its response shape — a response-level annotation, not a database value. For **Student** attendance, no background job, scheduled task, or write-path ever converts a `NOT_RECORDED` roster entry into a stored `ABSENT` row (Business Rule #26) — an `ABSENT` `StudentAttendance` row is only ever created by a genuine, explicit recording action by an authorized Teacher or Manager. **Staff** attendance follows the deliberately different rule in Section H.3 (Business Rule #36): `NOT_RECORDED` still applies before the configured absence cutoff, but past it, the read-time computation itself reports `ABSENT` — still never a written row, but a different derived outcome than Student attendance ever produces on its own.

## O. Multiple shifts

No cross-Shift assumption is made anywhere in this design (Business Rule #32). Every session/checkpoint computation (Sections E–G) resolves entirely from the specific Class's own assigned Shift (via `classesService.getGradeLevelShift` or the Class's own Shift reference) and that Shift's own Periods — never a school-wide "the current Period," since two Shifts at the same school can be at different points in their own day simultaneously. `AttendanceSettings` (Section K) is deliberately scoped per-school, not per-shift, in this version — the Business Specification's per-shift independence (Business Rule #32) is about schedule-derived timing (current Period, break boundaries, working days), not about the configurable window values themselves, which the approved decisions never describe as varying by Shift. If a future decision requires per-shift window configuration, `AttendanceSettings` gains an optional `shiftId` scoping column then — not speculatively added now.

## P. Holidays/non-working days

No existing model tracks one-off non-working calendar dates — `SchoolCalendar.workingDays` only expresses a recurring weekly pattern (`DayOfWeek[]`), which cannot represent a single closed Tuesday. This is a genuine, confirmed gap; the new `SchoolNonWorkingDay` model closes it minimally, scoped to this feature for now:

```
model SchoolNonWorkingDay {
  id       String   @id @default(uuid())
  schoolId String
  date     DateTime @db.Date
  reason   String?
  createdAt DateTime @default(now())
  @@unique([schoolId, date])
  @@index([schoolId])
}
```

"Is this date a genuine school day for this Shift" is computed as: the date's weekday is in `SchoolCalendar.workingDays`, **and** no `SchoolNonWorkingDay` row exists for `(schoolId, date)`. This check gates every session computation in Sections E–G. This model is deliberately minimal (no recurrence rules, no per-Shift holidays, no half-day concept) — it exists only to satisfy Business Rule #31, and is flagged, per the Business Specification's own reasoning, as a candidate to migrate into School Schedule Management's own ownership in a future ACR if another feature ever needs one-off closed dates; it is not claimed as that feature's permanent home here.

## Q. Student lifecycle/history preservation

No cascade-delete or update touches `StudentAttendance` when a Student's `status` changes (Transfer/Withdrawal/Graduation) — `Student.id` is referenced with the default `RESTRICT`-equivalent behavior already implicit in every other feature's own Student foreign keys (e.g. `Enrollment.studentId`), never `Cascade` (Business Rule #29). Exclusion from *new* sessions (Business Rule #30) is enforced purely at the roster-resolution step: every roster-building read (the student list a Teacher's Lesson attendance screen loads, or a Manager's Class-wide checkpoint screen loads) filters to `Student.status = ACTIVE` (or `ELIGIBLE_FOR_GRADUATION`, consistent with how Class Management's own active-roster reads already treat that status), reusing `studentsService.listStudents` rather than re-implementing status filtering. A Student's own historical attendance records remain queryable by `studentId` regardless of current `status` — the read path for "this Student's attendance history" never applies the active-roster filter.

## R. API design

**Implemented shape (v1.2 — see Change History):** all routes are mounted at the top-level `/api/v1/attendance` prefix, matching this project's dominant existing convention (Academic Years, Teacher Subject Assignments, Weekly Subject Allocations) rather than this section's originally-designed `/api/schools/:schoolId/attendance` — `schoolId` is derived exclusively from the authenticated token (`req.user.schoolId`), never from a URL path segment, so the outcome (`schoolId` is never client-supplied, per Business Rule #24) is identical either way. `GET /attendance/manager/classes` was added beyond the original design — a narrow, Manager-only read (backed by a new `classesService`-consuming `listClassesForManager` in `attendance.service.js`) letting the Manager-facing UI enumerate Classes to record checkpoint attendance against, without granting Manager any of Class Management's own `SCHOOL_ADMIN`-only routes.

**Every single route below rejects `SUPER_ADMIN` with 403, unconditionally, regardless of the `:schoolId` path value supplied** (Business Rule #34; Section B's allow-list, Section C's ordering). There is no Attendance route, present or future, that a Super Admin token can successfully call — this is verified per-route in Phase 9's automated test suite (Implementation Plan), not left as an inference from the role table alone.

**Teacher Student attendance**
- `GET /attendance/teacher/current-lesson` — resolves and returns the Teacher's current Lesson (via `timetableService.getTeacherTimetable`), its Student roster, and each Student's current `StudentAttendance` status or `NOT_RECORDED`. Role: `TEACHER`.
- `POST /attendance/teacher/lessons/:lessonId/records` — body: `{ date, records: [{ studentId, status }] }`. Creates `StudentAttendance` rows (`source = TEACHER`). Rejects any Student already covered by a Manager checkpoint for that date/Period (Section M), and any date that is not a genuine school day (Section P) or does not match `Lesson.dayOfWeek`. Role: `TEACHER`.
- `PATCH /attendance/teacher/lessons/:lessonId/records/:date` — same body shape; edits existing Teacher-recorded rows. Rejected once the edit window (Section K) has closed. Role: `TEACHER`.

**Manager Student attendance**
- `GET /attendance/manager/classes/:classId/checkpoints/:checkpoint` — query: `date`. Returns the Class roster with each Student's current status or `NOT_RECORDED`, and the resolved covered-Period list (Section G) for transparency. Role: `MANAGER`.
- `POST /attendance/manager/classes/:classId/checkpoints/:checkpoint/records` — body: `{ date, records: [{ studentId, status }] }`. Creates `StudentAttendance` rows (`source = MANAGER_BEFORE_BREAK`/`MANAGER_AFTER_BREAK`). Role: `MANAGER`.
- `PATCH /attendance/manager/records/:studentAttendanceId` — corrects an existing `StudentAttendance` row (Teacher- or Manager-recorded), per Section L. Role: `MANAGER`.

**Staff self-check-in — (v1.7, new; see Change History)**
- `POST /attendance/staff/me/come` — no body, no path parameter. Captures server time for the *authenticated* account, derives `PRESENT`/`LATE`, creates the row (`source` derived from `req.user.role` per Section H.1 step 5). Always dated the current school date (Business Rule #40) — a client-supplied `date`, `recordedAt`, or `status` is never read, not merely overridden. 409 if already recorded today; 422 before the configured start time or if Staff Attendance Timing Settings aren't configured. Role: `TEACHER`, `ACCOUNTANT`, `MANAGER`.

**Manager staff attendance (Teacher/Accountant) — (v1.3, replaced the v1.2 bulk manual-status endpoint; v1.7, `.../come` removed; v2.0, a narrower `.../come` reintroduced — see Change History)**
- `GET /attendance/manager/staff` — query: `date`. Returns every Teacher/Accountant at the school with their current status (`PRESENT`/`LATE`/`EXCUSED`/derived-`ABSENT`) or `NOT_RECORDED`, and `time` (`recordedAt`, or `null` when the status is `NOT_RECORDED` or derived-`ABSENT`), per Section H.3. Role: `MANAGER`.
- `POST /attendance/manager/staff/:accountId/come` — **(v2.0, new — see Section H.1b and Change History.)** No body. Records the arrival of the Teacher/Accountant identified by `:accountId`, captured and derived identically to self-recorded "Come" (Section H.1). 422 if `:accountId` does not resolve to a Teacher/Accountant at the acting Manager's own school (this is the structural enforcement of "never another Manager, never an Admin," per Business Rule #42); 422 before the configured start time or if Staff Attendance Timing Settings aren't configured; 409 if that staff member already has a record for today, from either this action or self-check-in. Role: `MANAGER`.
- `PATCH /attendance/manager/staff/:accountId/excuse` — body: `{ date? }` (defaults to today; **v1.9** — a value other than today is rejected with 422, per Business Rule #41). Applies `EXCUSED` — per Section H.2's Excuse action, this remains the one-click shortcut that works whether or not a row already exists (creates fresh if none, corrects to `EXCUSED` if one does) — unchanged from v1.4 except for the date restriction. Role: `MANAGER`.
- `PATCH /attendance/manager/staff/:accountId/excuse-historical` — **(v1.9, new)** body: `{ date }` — **required**, never defaulted. 422 if `date` equals today ("use the normal Excuse action") or is a future date ("future dates are never allowed"). Applies `EXCUSED` per Section H.2's historical Excuse action — the only path to a non-today `EXCUSED` mark. Role: `MANAGER`.
- `PATCH /attendance/manager/staff/:accountId/unexcuse` — **(v1.6, replaces v1.5's `.../correct`)** body: `{ date? }` — no status field; the outcome is never client-supplied. Requires an existing row currently `status = EXCUSED` — 404 if no row, 422 if the row exists but isn't currently `EXCUSED`. Reverses the Excuse action per Section H.2's Unexcuse action: recomputes `PRESENT`/`LATE` from the real prior arrival if one exists, or deletes the row if Excuse created it fresh. **Not date-restricted** (v1.9 note — see Section H.2). Role: `MANAGER`.

**Admin Manager attendance — (v1.3, replaced the v1.2 bulk manual-status endpoint; v1.7, `.../come` removed — see Change History)**
- `GET /attendance/admin/managers` — query: `date`. Returns every Manager at the school with current status or `NOT_RECORDED`, and `time`, identical shape to the Manager staff endpoint above. Role: `SCHOOL_ADMIN`.
- `PATCH /attendance/admin/managers/:accountId/excuse` — body: `{ date? }` (defaults to today; **v1.9** — a value other than today is rejected with 422). Role: `SCHOOL_ADMIN`.
- `PATCH /attendance/admin/managers/:accountId/excuse-historical` — **(v1.9, new)** body: `{ date }` — required. 422 for today or a future date. Identical mechanism to the Manager `.../excuse-historical` endpoint above, applied to a Manager account. Role: `SCHOOL_ADMIN`.
- `PATCH /attendance/admin/managers/:accountId/unexcuse` — **(v1.6, replaces v1.5's `.../correct`)** body: `{ date? }`. Identical mechanism to the Manager `.../unexcuse` endpoint above, applied to a Manager account. Not date-restricted (v1.9). Role: `SCHOOL_ADMIN`.
- ~~`POST /attendance/admin/managers/:accountId/come`~~ — **removed (v1.7).** An Admin never records a Manager's arrival; a Manager self-records via the new Staff self-check-in route above.

**Read/reporting (informational, no dedicated report per Business Specification's own scope)**
- `GET /attendance/students/:studentId/history` — a Student's own historical `StudentAttendance` records, unfiltered by current roster status (Section Q). Role: `TEACHER` (own-lesson records only, enforced server-side), `MANAGER`, `SCHOOL_ADMIN`.

No route exists for creating, viewing, or correcting an Admin's own attendance — deliberately absent, not merely unimplemented, per Business Rule #33.

## S. Validation

`attendance.validation.js` (plain manual validation functions throwing `ValidationError`, matching every existing feature's actual convention — e.g. `academic-years.validation.js` — not Zod, which this project does not use anywhere; corrected here from this document's original v1.0 text) validates request shape only: `status` ∈ the four enum values, `date` is a valid ISO date, `records` is a non-empty array, `checkpoint` ∈ `BEFORE_BREAK`/`AFTER_BREAK`. All business-meaning validation — current-lesson membership, roster membership, working-day/holiday check, lock/authority check, role-vs-source legality, edit/correction window — happens in the service layer against live data, never in the Zod schema, matching this project's consistent "schema validates shape, service validates meaning" split (e.g. WSA's own `academicYearId` handling).

## T. Service/repository responsibilities

`attendance.repository.js` — pure Prisma access, one function per query/write shape (`findStudentAttendance`, `createStudentAttendanceRecords`, `correctStudentAttendance`, `findStaffAttendance`, `createStaffAttendanceRecord` **(v1.3 — single-row, replacing the v1.2 bulk `createStaffAttendanceRecords`)**, `correctStaffAttendance`, `findNonWorkingDay`, `getAttendanceSettings`) — no business logic, matching every existing feature's repository layer.

`attendance.service.js` — owns every business rule in Sections E–Q: resolving current Teacher lesson (delegates to `timetableService.getTeacherTimetable`), resolving checkpoint coverage (delegates to `schoolScheduleService`'s Period/Shift reads), resolving working-day/holiday validity (delegates to `schoolScheduleService.getWorkingDays`/`getWeekendDays` plus the new `SchoolNonWorkingDay` repository read), resolving Class/Student rosters (delegates to `classesService`/`studentsService`), enforcing the Teacher-lock-after-Manager-checkpoint rule, enforcing edit/correction windows, deriving staff status from arrival time (Section H), deriving the read-time `ABSENT`/`NOT_RECORDED` split for staff (Section H.3), and calling `recordAuditEvent` on every write/correction. No repository function is ever called directly from a controller — the existing layering convention.

## U. Database constraints and uniqueness

`StudentAttendance` requires two different uniqueness shapes depending on `source`, expressible only as two partial unique indexes added via raw SQL migration — the same justified exception already established by `Shift.isDefault`, `Class.isFinal`, `AcademicYear.isCurrent`, and `TeacherSubjectAssignment`'s own composite index, since Prisma's schema DSL cannot express a partial/conditional unique constraint directly:

```sql
CREATE UNIQUE INDEX student_attendance_teacher_unique
  ON student_attendance (student_id, lesson_id, date)
  WHERE source = 'TEACHER';

CREATE UNIQUE INDEX student_attendance_manager_unique
  ON student_attendance (student_id, class_id, date, source)
  WHERE source IN ('MANAGER_BEFORE_BREAK', 'MANAGER_AFTER_BREAK');
```

The first guarantees one Teacher-recorded row per Student per Lesson occurrence (Business Lifecycle §1). The second guarantees one Manager-recorded row per Student per checkpoint per day (Business Lifecycle §2) — `source` is included in the index columns because a Student legitimately has up to two Manager rows per day (one per checkpoint), not one.

`StaffAttendance` needs only one uniqueness shape (Business Lifecycle §5–6 both describe "exactly one record per staff member per day," regardless of source) — an ordinary `@@unique([staffAccountId, date])`, expressible directly in Prisma's schema DSL, no raw SQL needed.

`SchoolNonWorkingDay` needs `@@unique([schoolId, date])`, also directly expressible.

Every uniqueness violation surfaces at the database layer as the final backstop against a race condition (Section Y), not merely as a pre-write existence check.

## V. Audit requirements

Every create, and every correction, on `StudentAttendance` and `StaffAttendance` calls the shared `recordAuditEvent({ schoolId, userId, action, metadata })` (`backend/src/shared/audit.js`) — the same utility every other feature already uses, never a feature-specific audit mechanism. `action` values: `attendance.student.recorded`, `attendance.student.corrected`, `attendance.staff.arrival_recorded` **(v1.3, replaces `attendance.staff.recorded`)**, `attendance.staff.excused` **(v1.3, new — distinguishes a direct `EXCUSED` mark from an arrival)**, `attendance.staff.corrected`, `attendance.staff.unexcused` **(v1.6, new, replaces v1.5's now-removed generic-correct usage of `attendance.staff.corrected` for this path — records whether the row was recomputed to a real prior status or deleted)**, `attendance.staff.historical_excuse` **(v1.9, new — recorded in addition to, never instead of, whichever of `attendance.staff.excused` or `attendance.staff.corrected` the underlying create-or-correct write already produces, so a historical correction is unambiguous in the audit trail rather than requiring a reader to cross-reference the row's own `date` against `createdAt`)**, `attendance.staff.manager_arrival_recorded` **(v2.0, new — recorded for a Manager-recorded Teacher/Accountant arrival, Section H.1b, in place of `attendance.staff.arrival_recorded`; the two are mutually exclusive per row, since a given "Come" is either self- or Manager-recorded, never both)**. `metadata` always includes the record's id, the subject's id, the `source`, the `status` (and, for corrections, the prior `status`), satisfying the audit-trail requirement in Business Rules #21–#22 and the Business Specification's own Audit Requirements section beyond what the row's own `recordedBy*`/`correctedBy*` fields already capture directly. No derived `ABSENT` read ever produces an audit event — there is no write to audit (Section H.3).

## W. Error handling

**Implemented (v1.2):** this project's `ValidationError` maps to HTTP **422** uniformly (`shared/errors.js`), not 400 — corrected from this document's original v1.0 text, which assumed a 400/422 split that doesn't match the actual codebase convention. The real grouping:

- **404** — referenced Lesson/Class/Student/Account does not exist, or does not belong to the acting user's `schoolId`.
- **403** — role not permitted for the route (Section B); any actor attempting a cross-school request past the tenant guard.
- **409** — a `StudentAttendance`/`StaffAttendance` row already exists for a write path that expects to create (translated from the Prisma unique-constraint violation, Section U); a Teacher write rejected because a Manager checkpoint already covers that Period (Section M); a second "Come" for a staff member already recorded today, whether the first was self- or Manager-recorded (Section H.1, H.1b).
- **422** — every `ValidationError`: malformed request body/shape; recording attendance for a date that fails the working-day/holiday check (Section P); an `accountId`/`studentId` not eligible for the target role/roster (e.g. a Manager targeting another Manager or an Admin account via the Manager-recorded arrival action, Section H.1b, or via `EXCUSED`, Section H.2; a School Admin targeting their own account); edit/correction attempted outside the configured window (Section K); a "Come" attempted (self- or Manager-recorded) before the configured staff attendance start time, or before Staff Attendance Timing Settings have been configured for the school at all (Section H.1, H.1b, K).

## X. Security considerations

- Every route enforces tenant isolation and role gating (Sections B–C) independently at both the route and service layers.
- No route ever accepts a client-supplied `recordedByAccountId`, `recordedAt`, `correctedByAccountId`, or `correctedAt` — all four are always server-derived from the authenticated session and system clock (Business Rules #15, #18, #23), never trusted from the request body.
- **(v1.3)** No route ever accepts a client-supplied `status` or arrival time for a "Come" action — `POST .../come` takes no body at all; `status` is computed server-side from the server-captured timestamp, full stop (Business Rules #35, #39).
- **(v1.7)** `POST /attendance/staff/me/come` takes no path parameter and no body — there is no `accountId` for a client to supply at all, because the target account is always `req.user`, never client input of any kind. This is the structural fix for the anti-pattern the v1.2–v1.6 routes had: those took `:accountId` in the URL, which meant a Manager/Admin *could* (and, per the approved v1.2–v1.6 design, was required to) act on a different account's behalf. Removing the parameter, not merely restricting who could supply it, is what makes third-party recording structurally impossible rather than just policy-forbidden.
- **(v1.8)** The same "not merely restricting, but never reading" property applies to `date`: the controller never reads `req.body` for this route, so a client-supplied `date` (to backdate to yesterday or postdate to tomorrow), `recordedAt`, or `status` cannot reach the write path at all — verified with a dedicated regression test suite that spoofs each field individually and in combination and asserts the created row still carries the real server date/time (Business Rule #40; Implementation Plan Testing Strategy). The Manager/Admin `EXCUSED` routes are a deliberate, unrelated exception — their `date` field is real client input by design, since correcting a specific day's record requires naming which day; **(v1.9 correction)** that `date` is not unrestricted, though — see below.
- **(v1.6)** The only staff-attendance write that ever accepts a client-supplied `status` is `.../excuse`, and it accepts exactly one legal value, `EXCUSED` (Business Rule #37) — any other value is a 422, never silently coerced. `.../unexcuse` (v1.6, replaces v1.5's `.../correct`) accepts **no** status field at all — the restored status is always computed server-side (recomputed from the real arrival timestamp, or the row is deleted), never a client-supplied value. This closes a real gap in v1.5's design: `.../correct` accepted any of the four statuses from the client, which meant a Manager/Admin could manually assign `PRESENT`/`LATE`/`ABSENT` at will — reintroducing the exact subjective override the arrival-based model (Business Rules #35, #39) exists to prevent. `.../unexcuse` reuses the same role/tenant/source checks as every other staff-attendance write (Section C).
- **(v2.0)** `POST /attendance/manager/staff/:accountId/come` (Section H.1b) is the one deliberate exception to the "no client-suppliable target account" property described above for `/staff/me/come` — here, `:accountId` **is** real client input, by design, since a Manager acting on someone else's behalf requires naming who. The safety property is therefore enforced differently: `:accountId` is validated server-side against `authService.listAccountsByRole(schoolId, ['TEACHER', 'ACCOUNTANT'])` before any write — a value naming another Manager, an Admin, an account from a different school, or a nonexistent account all fail this check identically (422), the same target-resolution pattern `markStaffExcused` already uses for its own create branch. `date`, `recordedAt`, and `status` remain entirely server-derived for this route, exactly as for self "Come" — only the *subject* is client-supplied, never the *when* or *what status*.
- **(v1.9)** `.../excuse`'s client-supplied `date` **is** restricted, correcting v1.8's own claim above: live-testing found it previously accepted any syntactically-valid date with no legality check, letting a Manager/Admin apply `EXCUSED` against an arbitrary past or future date through the single normal route. Fixed by validating the date server-side (`assertTodayOnly`) before any write happens — a non-today value is rejected with 422, not silently honored and not merely restricted-in-theory. The separate `.../excuse-historical` route has its own equally strict server-side gate (`assertPastDateOnly`) — required, non-today, non-future — so reaching a historical date is still possible but only through an action whose name and audit trail make that reach explicit (Business Rule #41).
- A Manager's Student-attendance authority is intentionally school-wide ("all Classes"), not Class-scoped — this is a deliberate, approved authority breadth (Business Rule #7), not an oversight; it is still bounded to the Manager's own `schoolId`.
- No path exists, anywhere in the routes, controllers, or services, that can create a `StaffAttendance` row with `staffRole = SCHOOL_ADMIN` — this is enforced as a structural validation (Section I), not merely a documented convention, so it cannot be bypassed by a future route addition that forgets the rule.
- **`SUPER_ADMIN` has zero Attendance access, enforced independently at three layers**: (1) the frontend never renders an Attendance navigation entry or route for a Super Admin session; (2) the backend role allow-list (Section B) rejects `SUPER_ADMIN` before any tenant check runs (Section C); (3) even a manually-crafted request to an Attendance API with a valid Super Admin token, any `:schoolId` value, and no client involved at all is rejected with 403 by layer (2) alone — the frontend guard is defense-in-depth, never the actual security boundary.

## Y. Concurrency considerations

Two actors could attempt to record the same (Student, Lesson, date) or (Student, Class, date, checkpoint) simultaneously (e.g. a Teacher and a Manager racing at a checkpoint boundary). The service layer performs an existence check before insert as the common-case fast path, but the actual guarantee against a race is the database-level partial unique index (Section U) — a losing concurrent insert fails with a Postgres unique-violation, which the service layer catches and translates into the 409 response (Section W), never a silently-overwritten row. This is the same pattern this project already relies on wherever a uniqueness invariant matters more than an optimistic pre-check alone (e.g. `Shift.isDefault`).

## Z. Reporting/query considerations

Detailed records (per-Lesson Teacher rows, per-checkpoint Manager rows) are always the queried source of truth (Business Rule #27); a "daily summary" view, if built, is computed at read time by grouping a Student's or staff member's rows for a given date — never written as a second, independently-maintained row. This version defines no dedicated report or dashboard (Out-of-Scope Items), so no new aggregate table or materialized view is introduced; if a future Reports feature needs one, it is designed then, against the detailed tables defined here, not anticipated now.

Indexes: `@@index([schoolId])`, `@@unique([staffAccountId, date])`.

All four new models use `onDelete: Restrict`-equivalent (Prisma's default) on every foreign key — never `Cascade` — consistent with Business Rule #29's history-preservation requirement; nothing about a Student's, Teacher's, Manager's, or Account's own lifecycle change should ever cascade-delete an attendance record.

# Backend Design

Key service-layer functions (`attendance.service.js`), each mapped to the Business Rule(s) or Technical Design section it implements:

- `resolveTeacherCurrentLesson(schoolId, teacherId)` — Section F.
- `resolveCheckpointCoverage(schoolId, classId, checkpoint)` — Section G.
- `isSchoolDay(schoolId, shiftId, date)` — Section P.
- `assertNotManagerLocked(studentId, classId, date, periodId)` — Section M.
- `recordTeacherAttendance(...)`, `editTeacherAttendance(...)` — Business Rules #3–#6.
- `recordManagerCheckpointAttendance(...)`, `correctStudentAttendance(...)` — Business Rules #7–#13, Section L.
- `recordSelfArrival(schoolId, actingUser)` **(v1.7, replaces `recordStaffArrival`/`recordManagerStaffArrival`/`recordAdminManagerArrival`)** — captures server time, derives `PRESENT`/`LATE`, creates the row for `actingUser`'s own account; `source`/`staffRole` derived entirely from `actingUser.role` (Section H.1 step 5), never from a client-supplied target. One function for all three self-checking-in roles (`TEACHER`, `ACCOUNTANT`, `MANAGER`) — there is no separate "Manager→Teacher/Accountant" vs. "Admin→Manager" recording flow anymore, since there is no third-party recorder at all (Business Rules #14–#15, #17–#18, #35, #39).
- `recordManagerStaffArrival(schoolId, accountId, actingUser)` **(v2.0, new — Section H.1b, Business Rule #42)** — the Manager-recorded counterpart to `recordSelfArrival` for a specific `:accountId`. Resolves `accountId` against `authService.listAccountsByRole(schoolId, ['TEACHER', 'ACCOUNTANT'])` (422 if not found — this is the structural guarantee that a Manager can never record arrival for another Manager or an Admin through this function); otherwise shares `assertStaffAttendanceTimingConfigured` and `deriveStaffAttendanceStatus` with `recordSelfArrival` unduplicated. Creates the row with `staffAccountId` = the target, `source = MANAGER_STAFF_ATTENDANCE`, `recordedByAccountId` = the acting Manager — the first "Come"-family write in this feature's history where subject and recorder are genuinely different accounts.
- `mogadishuTimeString(date)` / `mogadishuDateStr(date)` / `mogadishuOffsetMinutes(date)` / `mogadishuWallClockToInstant(dateStr, timeStr)` **(v2.1, new — Section H.4, Business Rule #43)** — `Intl`-only Africa/Mogadishu business-time helpers used by `recordSelfArrival`, `recordManagerStaffArrival`, `assertTodayOnly`/`assertPastDateOnly`, `unexcuseStaffAttendanceByAccount`'s recompute, and the read-time `ABSENT` derivation. Deliberately separate from the pre-existing UTC-based `toDateOnly`/`dayOfWeekFor`/`nowTimeString`/`todayDateStr`, which are unchanged and continue to back Student attendance.
- `deriveStaffAttendanceStatus(arrivalTime, settings)` **(v1.3, new, pure function)** — the `PRESENT`/`LATE` comparison against the late threshold (Business Rule #35); no I/O, easily unit-tested in isolation.
- `getStaffAttendanceRoster(schoolId, staffAccountIds, date, actingUser)` **(v1.3, new)** — the read-time `ABSENT`/`NOT_RECORDED` derivation (Section H.3) shared by both `GET /attendance/manager/staff` and `GET /attendance/admin/managers`.
- `markStaffExcused(schoolId, accountId, date, actingUser, { targetRoles, source, historical = false })` **(v1.3, new, replaces the old bulk-status write for this one case; v1.9, gained the `historical` flag)** — the create-or-correct `EXCUSED` action (Section H.2), shared by both flows and both date-scopes. `historical` selects which date-legality assertion runs (`assertTodayOnly` vs. `assertPastDateOnly`, both new in v1.9) and which audit action is recorded — the actual create-or-correct mutation is identical either way, never duplicated between the normal and historical callers.
- `excuseManagerStaff(...)` / `excuseAdminManager(...)` — thin wrappers calling `markStaffExcused` with `historical` omitted (today-only). `excuseManagerStaffHistorical(...)` / `excuseAdminManagerHistorical(...)` **(v1.9, new)** — the historical-correction counterparts, calling `markStaffExcused` with `historical: true`.
- `unexcuseStaffAttendanceByAccount(schoolId, accountId, date, actingUser)` / its `unexcuseManagerStaff(...)` and `unexcuseAdminManager(...)` role-specific wrappers **(v1.6, new, replaces v1.5's `correctStaffAttendanceByAccount`/`correctManagerStaff`/`correctAdminManager`)** — the Unexcuse action (Section H.2): looks up the existing row for `(accountId, date)` (404 if none, 422 if not currently `EXCUSED`), then either recomputes `PRESENT`/`LATE` from the row's own `recordedAt` via `deriveStaffAttendanceStatus` and clears `correctedBy*` (delegating the write to `correctStaffAttendance` below), or deletes the row outright if it was never a genuine arrival. Never accepts or produces a client-chosen status.
- `correctStaffAttendance(...)` — Business Rules #17–#19, Section I (unchanged from v1.2 — still corrects an existing row's `status`, now called only from `markStaffExcused`'s existing-row branch and from `unexcuseStaffAttendanceByAccount`'s recompute branch — never with a client-supplied `status`, unlike v1.5's now-removed Correct wrappers).
- `getStudentAttendanceHistory(studentId, actingUser)` — Section Q, role-scoped per Section B.

Each of these is a genuinely new function — none duplicates or re-implements logic already owned by Timetable, School Schedule, Class, or Student Management; each instead calls that module's own existing exported function (Section T) and applies attendance-specific rules on top of the result.

# Performance Considerations

`StudentAttendance` and `StaffAttendance` are both indexed on `schoolId` and on the natural lookup keys used by the read endpoints (`[studentId, date]`, `[lessonId, date]`, `[staffAccountId, date]`) so that a Teacher's daily roster view, a Manager's checkpoint view, and a Student's history view each resolve via an index, not a table scan. `resolveCheckpointCoverage` (Section G) re-derives covered Periods on every read rather than caching — accepted as cheap (a small, per-Shift Period list, already an in-memory-sized read in School Schedule Management today) relative to the correctness cost of a stale cache silently disagreeing with a live schedule change.

# Risks

- **Assumption Requiring Approval #1 (single break per Shift) is still open** — the checkpoint-coverage computation (Section G) is undefined for a Shift with zero or more than one `BREAK` Period. This must be resolved before Phase 4 (Manager checkpoint attendance) begins implementation; Phases 1–3 do not depend on it.
- **The four Open Questions (exact time windows) are still open** — `AttendanceSettings` (Section K) is designed to hold them without requiring a schema change once answered (nullable columns, default-fallback pattern), but the *default* fallback values themselves are not yet chosen and must not be invented during implementation without Product Owner input.
- **`SchoolNonWorkingDay` is a new, minimal model with no UI/management flow defined anywhere yet** — School Admin currently has no way to actually populate holiday dates; this must be scoped explicitly in the Implementation Plan (Phase 1) rather than assumed to already exist.
- **`MANAGER` role implementation is bundled into this feature** rather than delivered as a separate, prerequisite piece of work — if Authentication & Authorization's own roadmap later wants to implement it independently, this dependency direction should be revisited before Phase 2 begins.
- **(v1.3) No School-Admin-facing UI exists yet to configure Staff Attendance Timing Settings** — until a school's start time/late threshold/absence cutoff are set, every "Come" action for that school is rejected (Section H.1, Business Rule #38) and staff attendance is effectively unusable there. This must be scoped explicitly in the Implementation Plan's corresponding phase, not assumed to already exist alongside the `SchoolNonWorkingDay` gap already noted above.
- **(v1.3) `staffAttendanceAbsenceCutoff`'s read-time derivation (Section H.3) must be re-verified against every historical date query, not just "today"** — a naive implementation that only checks "is it currently past the cutoff" (ignoring which calendar date is being queried) would incorrectly report every past un-recorded staff-day as `NOT_RECORDED` forever, never `ABSENT`. This is a genuine implementation-correctness risk worth a dedicated test (Implementation Plan).

# Definition of Done

Technical Design is complete when: every lettered section (A–Z) required by the Product Owner is addressed with a traceable Business Rule reference or an explicit "pure implementation choice" note (done, above); the domain model resolves both the recurring-Lesson/calendar-date distinction and the two-shaped-uniqueness requirement without contradiction (done, Sections F, U); the WHO-IS-MARKED vs. WHO-IS-RECORDING distinction is explicit and exemplified (done, Section J plus the worked example below); no reusable existing service/repository function is duplicated (done, Section T cross-references every reused function); and no code, migration, API, or UI has been produced in this phase (true — this document contains no executable artifact).

**Worked example, as required verbatim by the Product Owner:**
- *Student X ← recorded by Teacher A* — `StudentAttendance{ studentId: X, source: TEACHER, recordedByAccountId: A's Account, recordedByRole: TEACHER }`.
- *Student X ← recorded by Manager B* — `StudentAttendance{ studentId: X, source: MANAGER_BEFORE_BREAK (or AFTER_BREAK), recordedByAccountId: B's Account, recordedByRole: MANAGER }`.
- *Teacher A ← recorded by Manager B* — `StaffAttendance{ staffAccountId: A's Account, staffRole: TEACHER, source: MANAGER_STAFF_ATTENDANCE, recordedByAccountId: B's Account, recordedByRole: MANAGER }`.
- *Manager B ← recorded by School Admin A* — `StaffAttendance{ staffAccountId: B's Account, staffRole: MANAGER, source: ADMIN_MANAGER_ATTENDANCE, recordedByAccountId: Admin's Account, recordedByRole: SCHOOL_ADMIN }`.
- *Admin A ← recorded by anyone* — no such record shape exists anywhere in this design (Section I; Business Rule #33).
