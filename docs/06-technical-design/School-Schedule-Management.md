Feature: School Schedule Management

Version: 1.3

Status: **Phase 4 (Technical Design Review) complete — Approved, for both the original (Calendar/Shift) scope and the Architecture Update (Periods).** Following Phase 2 (Business Review) approval (`docs/03-business/School-Schedule-Management.md` v1.1, Approved) and the Business Specification's own v1.2 extension adding Period Management. This Review found and fixed one significant cross-entity gap (`updateShift` could silently invalidate Period containment via a cross-lock-key race) and resolved two smaller open items (the wizard's slot-assembly algorithm; confirming the manual single-Period-create endpoint) — see Change History. # Overview

This document designs the technical approach for the Business Specification approved in `docs/03-business/School-Schedule-Management.md` (v1.2, including the Architecture Update that added Period Management).

It applies the already-approved architecture (`System-Architecture.md`, `Folder-Structure.md`), technology stack (`Technology-Decisions.md`), and standards (`Database-Standards.md`, `API-Standards.md`, `Security-Standards.md`, `Naming-Conventions.md`) to this specific feature. No new business rule is introduced anywhere below; every design decision either directly implements an already-approved Business Rule or is a pure implementation-mechanism choice the Business Specification deliberately left open (e.g. the exact Start/End Time storage type, the exact auto-created Shift's initial time values).

This design applies, from its first draft, a lesson this project has now applied three times already: Subject Management's `assignSubjectToSchool` and Academic Year Management's `createAcademicYear`/`archiveAcademicYear`/`designateCurrentAcademicYear` each shipped an unlocked check-then-act race that later code review found and fixed; Teacher Subject Assignment then proactively adopted a per-school Postgres advisory lock from its own first Implementation pass, rather than waiting for a third finding. `Shift.isDefault` is the same shape of "exactly one X per school" invariant — this would be the fourth instance — combined for the first time with a second, related invariant this project has not yet locked anywhere: a contiguous 1..N renumbering sequence (`Shift.displayOrder`). Both are locked from day one here — see Architecture and Risks.

# Architecture

- Implemented as a feature module: `backend/src/features/school-schedule/` — singular, kebab-case, matching the feature's own name, the same convention Academic Year Management's `academic-years/` module uses for its own feature name. This module owns two peer entities (`SchoolCalendar`, `Shift`), the same "one module, two related resources" shape Subject Management already established for `Subject`/`SchoolSubject`.
- **`SchoolCalendar` is a single, current-configuration-only record per school — never versioned, never historical (Business Rule #6).** One row per school, created once (at school creation) and only ever updated in place afterward; no new row is ever created for the same school. This is a *new* Prisma model owned by School Schedule Management, not additional fields bolted onto `School` — consistent with this project's Feature Ownership principle (every other feature that needed school-scoped configuration, Academic Year Management included, created its own model rather than extending `School` directly; `School.educationLevels`, added by ACR-003, is the one exception, and that addition was made *by* School Management itself, to its own entity, not by a different feature).
- **`Shift` is a school-scoped entity with two invariants needing careful concurrency handling, both new to this specific combination:**
  1. Exactly one `Shift` per school may have `isDefault = true`, and it must always be `status = ACTIVE` (Business Rules #8, #10) — the same shape as `Class.isFinal` and `AcademicYear.isCurrent`, backed by the same partial unique index pattern (see Database Impact).
  2. Every active Shift's `displayOrder` must be unique and contiguous (1..N) among a school's active Shifts, with archived Shifts holding no `displayOrder` at all (Business Rules #13–#14) — the same *shape* of sequencing problem Class Management's own `sequenceOrder`/`reorderClass` already solves, but not identical: Class Management keeps archived Classes *in* its sequence (appended after actives); this feature's Business Review explicitly resolved that archiving a Shift *removes* it from the active ordering entirely (`displayOrder` becomes `null`), and restoring appends it back to the end. This design follows that explicit resolution, not Class Management's own precedent, where the two diverge.
- **A Postgres advisory lock, scoped per school, is acquired as the first statement inside every transaction that writes `isDefault`, `displayOrder`, or any Shift's overlap-checked time range** — creation, correction (editing an existing Shift's own time range), reorder, designate-default, archive, and reactivate — via `pg_advisory_xact_lock(hashtext(schoolId))`, serializing all such writes for one school. This is the same pattern Teacher Subject Assignment already applied proactively; applying it here too, for a *combined* uniqueness + sequencing invariant that has never been locked together in this codebase before, is a deliberate continuation of that lesson, not an oversight waiting to be found a fifth time. **(Technical Design Review finding)** the v1.0 draft only listed creation among the overlap-checked writes; Shift Correction (`updateShift`) and reactivation (`reactivateShift`) both also change which time range is "active" and therefore need the identical lock + overlap check — see Backend Design and Change History.
- **Shift time overlap has no database-level backstop, the same Accepted Technical Debt already approved for Academic Year Management's own date-range overlap check.** A `tsrange`/`EXCLUDE` constraint could express this natively in Postgres, but no feature in this project has ever used a Postgres exclusion constraint, and introducing one here — for a single feature's one field — would be a bigger technology decision than this Technical Design should make unilaterally (Decision-Making-Principles' Consistency Over Preference). The overlap check is the application-level primary mechanism, run inside the same per-school locked transaction as every other Shift write, which is a strictly *safer* position than Academic Year Management's own accepted gap (that check runs outside any lock at all).
- **A new, additive, required dependency on the already-Accepted Class Management feature**: `Class` gains a required `shiftId` foreign key. This is delivered as part of *this* feature's own Implementation (per the Business Review's explicit resolution), the same category of post-Acceptance additive change already used for Teacher Management's `getTeacherById` — it does not reopen Class Management's own Feature Acceptance. See Database Impact and Dependencies.

## Architecture Update (Periods)

- **`Period` is a new, third entity owned by this same module, one level below `Shift`** — `SchoolCalendar` and `Shift` are school-scoped; `Period` is shift-scoped (Business Rule #23: "Periods belong to Shifts, and Shifts belong to Schools. A Period cannot exist without a Shift."). This module now owns three entities instead of two, still one feature, per the Business Specification's explicit "not a standalone feature" decision.
- **Period's own two invariants are the exact same *shape* as Shift's own two invariants, one level down:**
  1. Every active Period's `displayOrder` must be unique and contiguous (1..N) — but **scoped to its own Shift, not to the school** (Business Rule #26). Two Periods in different Shifts may both legitimately be `displayOrder = 1`.
  2. Active Period time ranges must not overlap — again **scoped to the Period's own Shift, not the school** (Business Rule #25) — and must additionally fit entirely inside that Shift's own `startTime`/`endTime` (a containment check Shift itself has no equivalent of, since Shift has no parent to be contained inside).
- **New locking decision: the advisory lock for Period writes is scoped to the `shiftId`, not the `schoolId`** — `pg_advisory_xact_lock(hashtext(shiftId))`, a different key from the `hashtext(schoolId)` key every Shift write already uses. This is a deliberate divergence from simply reusing the Shift-level lock, reasoned the same way this project has always scoped a lock to the actual shared invariant it protects (Decision-Making-Principles' Avoid Premature Abstraction / Consistency Over Preference cuts the other way here: Shift's own invariants are genuinely school-wide, so its lock is school-wide; Period's own invariants are genuinely shift-wide, not school-wide, so its lock should not force two Admins editing two *different* Shifts' Periods in the same school to serialize against each other for no invariant-preserving reason).
- **(Technical Design Review finding) The v1.2 draft's claim that "Shift writes never touch Period rows" was wrong — `updateShift` (Shift Correction) can silently invalidate a Period's own containment invariant, and this was not accounted for anywhere.** If a School Admin narrows a Shift's `startTime`/`endTime` after Periods inside it already have configured times fitting the *old* range, nothing previously re-checked whether those Periods still fit the *new* range — the exact category of gap the original TDR already found twice for Shift itself (an edit silently invalidating a downstream invariant nothing re-checks). Worse, because Period writes and `updateShift` use two *different* lock keys (`shiftId` vs `schoolId`), a genuine cross-key race also existed: a concurrent `updateShift` (narrowing the range) and `createPeriod`/`updatePeriod` (validating containment against the *old*, about-to-change range) could interleave, each seeing a version of the Shift's own times that the other was about to make stale, leaving a committed Period outside its own Shift's final operating hours with no error to either caller. **Fixed:** `updateShift` now acquires **both** locks, always in the same fixed order — `acquireSchoolLock(schoolId, tx)` first, then `acquireShiftLock(shiftId, tx)` — before doing anything else. Acquiring the `shiftId` lock forces `updateShift` to serialize against any concurrent Period write for that same Shift (whichever transaction acquires the `shiftId` lock first runs to completion before the other's own acquisition unblocks). After both locks are held, `updateShift` loads that Shift's own active Periods and rejects (409) if the new `startTime`/`endTime` would leave any configured Period outside the new range, requiring the Admin to adjust or archive the conflicting Periods first — the same "must clear the same gate a fresh write would" principle `reactivateShift`'s own original TDR fix already established. **This fixed lock order (`schoolId` then `shiftId`, never the reverse) is now a required invariant of this design, not a suggestion** — see Backend Design and Risks for why no other code path may ever acquire them in the opposite order, which would reintroduce deadlock risk.
- Aside from `updateShift`'s new dual-lock acquisition above, no other Shift write path touches Period rows or their invariants — `createShift`, `reorderShift`, `designateDefaultShift`, `archiveShift`, and `reactivateShift` never change a Shift's own `startTime`/`endTime`, so none of them can invalidate Period containment, and none of them need the `shiftId` lock.
- **Exception: generating a new Shift's default Period structure (the setup wizard) happens inside `createShift`'s own existing transaction, under its own existing `schoolId` lock — not a separate `shiftId` lock.** The new Shift does not exist yet at the moment its own Periods are being generated, so there is nothing else in the system that could concurrently be racing to write Periods for a `shiftId` that has no rows referencing it until this same transaction commits; acquiring a second, `shiftId`-scoped lock here would be locking a key nothing else could possibly contend for yet. Every Period write against an *already-existing* Shift (create, correct, reorder, archive, reactivate) uses the `shiftId` lock described above.
- **Period's `startTime`/`endTime` are nullable — a new state this codebase has not modeled before.** Shift's own `startTime`/`endTime` are required at creation; Period's are optional until the School Admin configures them (Business Rule #25, Validation Rules #13–14), because both this feature's own bootstrap structure and the setup-wizard's generated structure create Period rows before any real time value is known. This is a genuinely new "structurally valid but not yet fully configured" record shape for this project — flagged for Technical Design Review's attention, the same way the native `TIME` column itself was flagged in v1.0.

# Database Impact

## New enums

```prisma
enum DayOfWeek {
  SUNDAY
  MONDAY
  TUESDAY
  WEDNESDAY
  THURSDAY
  FRIDAY
  SATURDAY
}

enum ShiftStatus {
  ACTIVE
  ARCHIVED
}
```

`ShiftStatus` duplicates the same two-value shape as `ClassStatus`/`SubjectStatus`/`AcademicYearStatus` rather than reusing one of them, consistent with this project's existing convention of one status enum per owning entity.

## `SchoolCalendar`

- `id`, `schoolId` (`@unique` — one row per school, ever), `workingDays DayOfWeek[]`.
- **Weekend Days are never stored** — `getWeekendDays()` derives them as the complement of `workingDays` against the full 7-day set (Business Rule #4's "never both, never neither" is structurally guaranteed this way: a day cannot be simultaneously in `workingDays` and its own complement). This mirrors this project's existing "derived, never stored" judgment calls (Academic Year Management's `YYYY/YYYY` label, Teacher Subject Assignment's Active/Ended status) — storing both arrays independently would let them drift out of sync with each other, which a derived complement structurally cannot.
- No status/archived concept — a `SchoolCalendar` row is never archived or deleted; it is only ever updated in place (Business Rule #6).
- Created once, automatically, in the same transaction as the school's own creation (see Backend Design) — this is School & Platform Management's own `createSchool` transaction gaining one additional insert, the same category of in-transaction addition already used when Teacher Management's Onboarding wraps Account creation and Teacher-record creation together.

## `Shift`

- `id`, `schoolId`, `name String`, `startTime`, `endTime`, `displayOrder Int?` (nullable), `isDefault Boolean @default(false)`, `status ShiftStatus @default(ACTIVE)`, `createdAt`/`updatedAt`.
- **`startTime`/`endTime` are stored as Postgres native `TIME` columns** (`@db.Time()` in Prisma, surfaced as a `DateTime` in the generated client using a fixed reference date), not a `String` in `"HH:mm"` format and not a full `DateTime` representing an actual calendar date. This is a genuinely new technology choice for this project (no prior feature has stored a time-of-day-only value) — chosen over a string because a native type gives Postgres itself the ability to reject a malformed time value and to compare two times correctly without ad hoc string-parsing logic, consistent with Decision-Making-Principles' Protect Data principle. No time zone is stored or applied; a Shift's times are the same wall-clock hours for every day they apply to, which is exactly what Postgres's `TIME WITHOUT TIME ZONE` represents.
- **`displayOrder` is nullable, and is `NULL` exactly when `status = ARCHIVED`** — an Archived Shift holds no position in the active ordering at all (Business Rule #14), a deliberate divergence from Class Management's own `sequenceOrder` (which keeps archived Classes in its sequence, appended after actives). Postgres's default NULL-handling in a unique index already gives the exact behavior needed here with no special syntax: two archived Shifts, both `displayOrder = NULL`, are never considered duplicates of each other by a plain `@@unique([schoolId, displayOrder])` constraint — unlike Teacher Subject Assignment's own `NULLS NOT DISTINCT` case, this feature *wants* NULLs to be treated as distinct from one another, which is Postgres's ordinary default, so no raw-SQL migration addition is needed for this particular constraint.
- **A partial unique index enforces "exactly one Default Shift per school," the same pattern as `Class.isFinal` and `AcademicYear.isCurrent`:**
  ```sql
  CREATE UNIQUE INDEX "shifts_school_default_shift_unique" ON "shifts"("schoolId") WHERE "isDefault" = true;
  ```
  Hand-written raw SQL appended to the generated migration, the same justified, established exception to "only Prisma accesses the database" (Database-Standards.md) `Class.isFinal`'s own migration already set the precedent for.
- Indexing: `schoolId` (every list/filter query is scoped to one school), consistent with Database-Standards.md.

## Architecture Update (Periods) — new enums and `Period`

```prisma
enum PeriodType {
  TEACHING
  BREAK
}

enum PeriodStatus {
  ACTIVE
  ARCHIVED
}
```

`PeriodStatus` duplicates `ShiftStatus`'s own two-value shape rather than reusing it, for the same "one status enum per owning entity" reason `ShiftStatus` itself was kept distinct from `ClassStatus`/`SubjectStatus`/`AcademicYearStatus`.

## `Period`

- `id`, `shiftId` (FK to `Shift`, required — Business Rule #23), `name String`, `type PeriodType`, `startTime`/`endTime` (`@db.Time()`, **nullable** — see Architecture Update above), `displayOrder Int?` (nullable, same "`null` exactly when Archived" convention as `Shift.displayOrder`), `status PeriodStatus @default(ACTIVE)`, `createdAt`/`updatedAt`.
- **No `schoolId` column on `Period` itself.** Tenant isolation is enforced by loading the parent `Shift` first and checking *its* `schoolId`, the same "no denormalized tenant column on a child-of-a-child entity" pattern Class Management's own `Section` already established relative to `Class` (a `Section` has no `schoolId` column either; `getSectionOrThrow` loads via `classId` and checks the Class's own `schoolId`). Avoids a second, derivable column that could theoretically drift from the parent's own value.
- **`@@unique([shiftId, displayOrder])`** — scoped to `shiftId`, not `schoolId` (Business Rule #26), the same NULL-values-are-distinct-by-default Postgres behavior `Shift`'s own `@@unique([schoolId, displayOrder])` already relies on — no `NULLS NOT DISTINCT` needed here either, since two archived Periods in the same Shift both holding `displayOrder = NULL` are correctly never treated as duplicates.
- Indexing: `@@index([shiftId])`, since every Period query this feature runs is scoped to one Shift.
- No partial unique index is needed for Period (unlike `Shift.isDefault`/`Class.isFinal`/`AcademicYear.isCurrent`) — Period has no "exactly one X" invariant; `TEACHING` vs `BREAK` is an ordinary enum value, not a flag with a uniqueness constraint (Business Rule #28: zero, one, or multiple Breaks are all valid).

## `Class` (additive change to an already-Accepted feature)

- New required `shiftId String` column with a foreign key to `Shift`.
- **Migration sequencing is the single most important cross-feature detail in this design.** This feature's own migration (creating `SchoolCalendar` and `Shift`, and backfilling every existing school with its own Somalia Default Calendar and default "Morning" Shift) must be applied *and its data backfill completed* before Class Management's own migration runs, because Class Management's backfill (assigning every existing Class to its own school's Default Shift) depends on that Default Shift already existing. This is not expressible as a single migration; it is two migrations, strictly ordered, with School Schedule Management's own backfill-of-existing-schools step completing first. Implementation Planning must sequence these as two explicit, ordered steps, not a single combined change.
- The `shiftId` column itself is added as nullable first, backfilled via a hand-written `UPDATE` statement (each existing Class set to its own school's current Default Shift id) inside the same migration, then altered to `NOT NULL` — the same "generated migration, hand-edited with one additional raw-SQL step" pattern already established for `NULLS NOT DISTINCT` and partial-unique-index additions, except the addition here is a data backfill, not an index.
- No other change to Class Management's own Business Rules, validation, or lifecycle — `createClass`/`updateClass` gain one additional required field, validated via this feature's own `validateShift`, the same way Student Management's `enrollStudent` validates `classId`/`sectionId`/`academicYearId` via other features' own narrow interfaces.

# API Design

High-level shape only — exact payloads and per-case status codes belong in a separate API Specification if requested.

- REST, versioned under `/api/v1`, per API-Standards.md. Two resource names, both singular/plural exactly as their own entity shape suggests, per Naming-Conventions.md: `/school-calendar` (one record per school, no id in the path) and `/shifts` (a collection).
- **School Admin / Teacher's own view (School-scoped, resolved from the authenticated token, never a client-supplied schoolId):**
  - `GET /school-calendar` — the acting user's own school's Calendar (School-Admin and Teacher).
  - `PATCH /school-calendar` — update `workingDays` (School-Admin-only).
  - `GET /shifts` — list, filterable by `status` (School-Admin and Teacher).
  - `GET /shifts/{id}` — single record detail (School-Admin and Teacher).
  - `POST /shifts` — create (School-Admin-only). Body: `name`, `startTime`, `endTime`.
  - `PATCH /shifts/{id}` — correct `name`, `startTime`, `endTime` only (School-Admin-only); Guard by Construction rejects `displayOrder`/`isDefault`/`status` in this body, mirroring Teacher Subject Assignment's own PATCH-field-whitelist pattern.
  - `PATCH /shifts/{id}/sequence` — dedicated reorder action (School-Admin-only), body `{ position }`, mirroring Class Management's own identically-named `PATCH /classes/{id}/sequence` exactly.
  - `PATCH /shifts/{id}/designate-default` — dedicated action (School-Admin-only), no body, mirroring Class Management's `/designate-final` naming convention.
  - `PATCH /shifts/{id}/archive` — mirrors Class/Academic-Year naming exactly.
  - `PATCH /shifts/{id}/reactivate` — mirrors Class/Academic-Year naming exactly (the Business Specification's own word "restore" maps onto this project's established `reactivate` verb, the same mapping Teacher Subject Assignment made for its own "Assignment Ending" business term onto a technical mechanism).
- **Super Admin's cross-school oversight view (read-only), mirroring Subject Management's own `/schools/{schoolId}/subjects` nested-route precedent exactly:**
  - `GET /schools/{schoolId}/school-calendar`
  - `GET /schools/{schoolId}/shifts`
- Every endpoint requires a valid JWT and passes through the same Authentication/Authorization middleware chain every other feature already uses; no new authentication mechanism is introduced.

## Architecture Update (Periods) — API additions

- **Periods are nested under their own Shift**, matching Class Management's own `/classes/{classId}/sections` nesting for the same "child belongs to exactly one parent, never referenced independently of it in the URL" shape:
  - `GET /shifts/{shiftId}/periods` — list, filterable by `status` (School-Admin and Teacher).
  - `GET /periods/{id}` — single record detail (School-Admin and Teacher). Not nested under `shiftId` in the path, mirroring `GET /shifts/{id}` and `GET /sections/{id}`'s own existing precedent of a flat detail route once an id is known.
  - `POST /shifts/{shiftId}/periods` — create a single Period (School-Admin-only). Body: `name`, `type`, `startTime?`, `endTime?`. Operationalizes Business Rule/FR "School Admin must be able to manage Periods within each Shift" (FR22) beyond the two bulk-generation paths below — the same "auto-created default, plus full manual CRUD afterward" shape Shift itself already has relative to School creation. **(Confirmed during Technical Design Review)** this endpoint is retained as designed — FR22's "manage Periods within each Shift" is broad enough to require it (a School Admin must be able to add an 8th Period later, not just accept whatever the wizard generated), and it introduces no ambiguity with the wizard, since the wizard only ever runs once, at Shift creation.
  - `PATCH /periods/{id}` — correct `name`, `type`, `startTime`, `endTime` only (School-Admin-only); Guard by Construction rejects `displayOrder`/`status` in this body, the same convention `PATCH /shifts/{id}` already established.
  - `PATCH /periods/{id}/sequence` — dedicated reorder action (School-Admin-only), body `{ position }`, mirroring `PATCH /shifts/{id}/sequence` and `PATCH /classes/{id}/sequence` exactly — position is 1-based *within that Period's own Shift*, not the school.
  - `PATCH /periods/{id}/archive`, `PATCH /periods/{id}/reactivate` — mirror `Shift`'s own naming exactly.
- **The setup wizard is not a separate endpoint — it is folded into `POST /shifts` itself**, since the Business Specification's own Business Lifecycle describes it as one combined action ("when a School Administrator creates a new Shift, provide a simple setup wizard... the system then generates the Period structure automatically"), not a later, separate step against an already-existing Shift. `POST /shifts`'s body gains three optional fields — `teachingPeriodCount` (default `6`), `includeBreak` (default `true`), `breakAfterPeriod` (default `3`) — matching the Business Specification's own named defaults exactly. `createShift` generates the new Shift's Period structure inside the same transaction as the Shift row itself (see Backend Design), the same "create the parent and its default child structure together, atomically" shape `createDefaultScheduleForSchool` already uses for a brand-new school's Calendar + default Shift + default Period structure. This also sidesteps a "regenerate against an already-populated Shift" edge case entirely — the wizard only ever runs once, at the Shift's own creation, never as a later action against an existing Shift. A School Admin who wants to add more Periods afterward uses the ordinary `POST /shifts/{shiftId}/periods` single-Period create above.
- **Super Admin's oversight view** gains one nested read route: `GET /schools/{schoolId}/shifts/{shiftId}/periods` — read-only, mirroring the existing two oversight routes' own shape.

# Backend Design

- New feature module `backend/src/features/school-schedule/`, structured per Folder-Structure.md (controller, service, repository, validation, routes, tests), exporting two routers (`scheduleRouter`, `schoolScheduleAdminRouter`) from its own `index.js`, the same shape Subject Management's `index.js` already exports `{ subjectsRouter, schoolSubjectsRouter }`.
- **`assertOneWorkingAndOneWeekendDay(workingDays)`** — Business Rule #5; rejects an empty or full 7-day `workingDays` array (no valid Weekend or Working Day would remain). Business Rule #4's "never both, never neither" needs no separate runtime check here — it is structurally guaranteed by storing only `workingDays` and deriving the complement, per Database Impact.
- **`updateSchoolCalendar(schoolId, { workingDays }, actingUser)`** — loads the school's single `SchoolCalendar` row, re-validates via the assertion above, updates in place. No transaction/lock needed — this is a single-row update with no uniqueness or sequencing invariant across other rows, unlike every Shift write below.
- **Shared internal helpers, called from every write path below that needs them — never a hand-rolled partial re-implementation of any one of them:**
  - `getShiftOrThrow(schoolId, shiftId, tx)` — loads the Shift, throws `NotFoundError` if missing or cross-school, the same convention every other feature's own `get*OrThrow` already uses.
  - `assertNoOverlap(schoolId, { startTime, endTime }, excludeShiftId, tx)` — loads every active Shift for the school (excluding `excludeShiftId`, when checking an edit or a reactivation against itself) and checks `startA <= endB && startB <= endA` against each, the same inclusive-boundary reading Academic Year Management's own `rangesOverlap` already established for its own date ranges, applied here for consistency (Business Rule #12 does not pin down the exact touching-boundary case, so the already-established conservative reading is reused rather than inventing a second convention).
  - `nextEndOfSequencePosition(schoolId, tx)` — `Math.max(...activeShifts.map(s => s.displayOrder)) + 1`, or `1` if none exist — the same shape as Class Management's own function of the same name, scoped to active Shifts only (since archived Shifts hold no `displayOrder` here, unlike Class Management's own version which considers archived Classes too).
- **`createShift(schoolId, { name, startTime, endTime }, actingUser)`** — inside `prisma.$transaction`, `acquireSchoolLock` first, then `assertNoOverlap(schoolId, { startTime, endTime }, null, tx)`, then insert with `displayOrder = nextEndOfSequencePosition(...)`, `isDefault = false`, `status = ACTIVE`.
- **`updateShift(schoolId, shiftId, { name, startTime, endTime }, actingUser)`** — **(Technical Design Review finding, fixed here — see Change History)** the v1.0 draft omitted this function from Backend Design entirely, even though API Design's `PATCH /shifts/{id}`, Business Rule #12, and the Edge Cases table all already required edit-time overlap checking. Inside `prisma.$transaction`, `acquireSchoolLock` first (the same lock every other Shift write acquires — an edited time range is exactly as capable of introducing an overlap as a newly created one), then `getShiftOrThrow`, then `assertNoOverlap(schoolId, { startTime, endTime }, shiftId, tx)` — passing the Shift's own id as `excludeShiftId` so it is never compared against its own prior, about-to-be-replaced time range — then updates `name`/`startTime`/`endTime` only. Never touches `displayOrder` or `isDefault` — Guard by Construction in `validation/` already rejects those fields in this request body. **(Architecture Update — Periods, Technical Design Review finding, fixed here)** immediately after `acquireSchoolLock`, also calls `acquireShiftLock(shiftId, tx)` — this fixed order (`schoolId` lock, then `shiftId` lock) must never be reversed anywhere in this codebase, or a deadlock becomes possible. After both locks and the overlap check pass, loads this Shift's own active Periods and rejects (409) if any configured Period would fall outside the *new* `startTime`/`endTime` — see Architecture Update above for why this check and its lock are both necessary.
- **`reorderShift(schoolId, shiftId, targetPosition, actingUser)`** — inside the locked transaction: `getShiftOrThrow`, then loads the school's active Shifts ordered by `displayOrder`, removes the target, re-inserts it at the clamped target position, and rewrites every active Shift's `displayOrder` to the resulting 1..N sequence in one batch — the same algorithm as Class Management's own `reorderClass`, adapted to this feature's own "archived Shifts are excluded from the sequence entirely" rule (Class Management's version renumbers active *and* archived Classes together; this version only ever touches active Shifts, since archived ones have no `displayOrder` to renumber).
- **`designateDefaultShift(schoolId, shiftId, actingUser)`** — inside the locked transaction: `getShiftOrThrow`, rejects if `status !== ACTIVE` (Business Rule #10), unsets the school's current Default Shift (if any) and sets the new one, mirroring `academicYearsService.setCurrentAcademicYear`'s own unset-then-set pattern exactly.
- **`archiveShift(schoolId, shiftId, actingUser)`** — inside the locked transaction: `getShiftOrThrow`, rejects if any active Class references it (Business Rule #16, via this feature's own `classesService`-equivalent — actually the reverse: Class Management would need its own `countActiveClassesByShift`-shaped narrow query, or this feature queries its own `Class.shiftId` column directly since `Class` is a *consumer* of Shift, not the other way around — **this direction is the same "which feature owns the join query" question Subject Management already answered for its own removal-dependency check**: this feature will need either its own read of `Class` rows (acceptable, since `Class.shiftId` is the very column this feature's own Implementation adds, making it reasonable for this feature's own migration/backfill code to also read it directly at that point) or a narrow interface addition to Class Management symmetrical to Subject Management's `registerRemovalDependencyCheck` extension point. **This exact mechanism choice — direct read vs. a registered dependency check — is deferred to Implementation Planning**, since Technical Design's job is to identify the dependency, not necessarily pick between two structurally-equivalent, already-precedented mechanisms without Implementation-time information (e.g., whether Class Management's own module conveniently already exposes a "list Classes by Shift" narrow query it would want anyway). Rejects if it would leave zero active Shifts (Business Rule #9). Rejects if it is the current Default Shift (Business Rule #10) — the caller must call `designateDefaultShift` first. On success: sets `status = ARCHIVED`, `displayOrder = null`, and renumbers the remaining active Shifts to close the gap (the same renumbering step `reorderShift` performs, factored into one shared helper both call).
- **`reactivateShift(schoolId, shiftId, actingUser)`** — inside the locked transaction: `getShiftOrThrow`, rejects if `status !== ARCHIVED`. **(Technical Design Review finding, fixed here — see Change History)** the v1.0 draft did not re-check overlap before restoring an Archived Shift. A Shift archived at one point in time can no longer assume its own old time range is still conflict-free: a *different* Shift may since have been created, or edited, into a range that now overlaps it, while the first Shift sat archived (and therefore excluded from every overlap check run in the meantime). Restoring a Shift is, in effect, reintroducing an active time range, and must clear the exact same gate a fresh creation would — the same category of gap Teacher Subject Assignment's own Technical Design Review already found in a first `replaceTeacher` draft that skipped re-validating everything a direct creation would check. Fixed: `reactivateShift` now also calls `assertNoOverlap(schoolId, { startTime: shift.startTime, endTime: shift.endTime }, shiftId, tx)` before restoring; on success, sets `status = ACTIVE` and `displayOrder = nextEndOfSequencePosition(...)` (append to the end, Business Rule #14) — never automatically `isDefault`. If the check fails, the Shift remains Archived and the School Admin must first resolve the conflict (e.g. by editing the other Shift) before retrying.
- Cross-feature calls are the feature's only dependencies for validation, per System-Architecture.md's Modular Monolith style — this feature has none of its own (it is upstream of Class Management, not downstream of anything except School & Platform Management, whose only touchpoint is the one additional insert at school-creation time).
- Repository layer is the only code touching Prisma, per Coding-Standards.md.

## Architecture Update (Periods) — Backend Design

- **Shared internal helpers, the same "call the shared helper, never a partial re-implementation" discipline as Shift's own:**
  - `getPeriodOrThrow(shiftId, periodId, tx)` — loads the Period, throws `NotFoundError` if missing or belonging to a different Shift.
  - `assertPeriodNoOverlap(shiftId, { startTime, endTime }, excludePeriodId, tx)` — loads every active Period for the Shift (excluding `excludePeriodId`), same inclusive-boundary check as `assertNoOverlap`. Skipped entirely when either `startTime`/`endTime` is `null` (an unconfigured Period cannot overlap anything).
  - `assertPeriodFitsWithinShift(shift, { startTime, endTime })` — Business Rule #25/Validation Rule #15: rejects a configured Period whose `startTime`/`endTime` falls outside the parent Shift's own `startTime`/`endTime`.
  - `nextEndOfSequencePosition(shiftId, tx)` — the same algorithm as Shift's own function of the same name, scoped to `shiftId` instead of `schoolId`.
- **`createPeriod(schoolId, shiftId, { name, type, startTime, endTime }, actingUser)`** — inside `prisma.$transaction`: `acquireShiftLock(shiftId, tx)` first (the new `hashtext(shiftId)` key, see Architecture Update above), `getShiftOrThrow(schoolId, shiftId, tx)` (tenant-isolation check via the parent Shift, since Period itself has no `schoolId`), then — only if both times are provided — `assertPeriodFitsWithinShift` and `assertPeriodNoOverlap`, then insert with `displayOrder = nextEndOfSequencePosition(shiftId, tx)`, `status: 'ACTIVE'`.
- **`updatePeriod(schoolId, shiftId, periodId, { name, type, startTime, endTime }, actingUser)`** — same shape as `updateShift`: lock, load-or-throw, re-validate containment + overlap (again, only if both times are present after the edit), update `name`/`type`/`startTime`/`endTime` only. Never touches `displayOrder`/`status`.
- **`reorderPeriod(schoolId, shiftId, periodId, targetPosition, actingUser)`** — identical algorithm to `reorderShift`, scoped to the Period's own Shift.
- **`archivePeriod(schoolId, shiftId, periodId, actingUser)`** — lock, load-or-throw; **no downstream-reference check exists yet** (unlike `archiveShift`'s check against `Class.shiftId`) because no consuming feature (Timetable, Attendance, Exam Management) exists yet to reference a specific Period — this is a genuine, narrower rule than Shift's own archive, not an oversight; a future feature that needs to block Period archival while referenced will add that check itself, the same way this feature's own `archiveShift` check was added when Class Management's dependency became concrete, not before. On success: `status: 'ARCHIVED'`, `displayOrder: null`, renumber the remaining active Periods in that Shift.
- **`reactivatePeriod(schoolId, shiftId, periodId, actingUser)`** — lock, load-or-throw, rejects if not Archived, **re-checks containment + overlap before restoring, only if the Period's own stored times are both non-null** (an unconfigured, never-timed Period can always be restored with no conflict possible) — the same "an archived record cannot assume its old state is still valid" reasoning `reactivateShift` already established. On success: `status: 'ACTIVE'`, `displayOrder: nextEndOfSequencePosition(shiftId, tx)`.
- **`generatePeriodStructure(shiftId, { teachingPeriodCount, includeBreak, breakAfterPeriod }, tx)`** — a private helper, not itself part of the public service surface, called by both `createShift` (wizard case) and `createDefaultScheduleForSchool` (bootstrap case, with fixed arguments `{ teachingPeriodCount: 6, includeBreak: true, breakAfterPeriod: 3 }` reproducing the Business Specification's own literal default structure: Period 1, Period 2, Period 3, Break, Period 4, Period 5, Period 6).
  - **(Technical Design Review finding, fixed here)** the v1.2 draft specified the *naming* rule but never the *slot-assembly* rule — how `breakAfterPeriod` actually determines where the Break lands was left implicit. **Assembly algorithm, now made explicit:** build `teachingPeriodCount` Teaching slots in order; if `includeBreak` is true, insert exactly one Break slot immediately after the `breakAfterPeriod`-th Teaching slot (1-based — `breakAfterPeriod: 3` means the Break sits between the 3rd and 4th Teaching slots; `breakAfterPeriod` equal to `teachingPeriodCount` is a valid edge case meaning the Break sits after the last Teaching slot, at the very end of the sequence). The resulting slot count is `teachingPeriodCount + (includeBreak ? 1 : 0)`; each slot's `displayOrder` is its 1-based position in this final, assembled sequence. When `includeBreak` is false, `breakAfterPeriod` is ignored entirely (not validated, not used).
  - **Naming algorithm** (inferred from the Business Specification's one worked example, since no explicit naming rule is stated beyond it — **confirmed during this Technical Design Review as the correct reading, not left open**): iterate the full 1..N slot sequence produced by the assembly algorithm above; a `BREAK` slot is always named literally `"Break"`; a `TEACHING` slot is named `"Period {k}"` where `k` is that slot's own ordinal position *among TEACHING slots only*, counting continuously through any Break (so the six Teaching Periods in the default structure are named 1 through 6 in the order they appear, and the Break in between is simply "Break," never "Period 4").
  - All rows get `status: 'ACTIVE'` and `startTime`/`endTime` left `null`. Runs inside the caller's own already-locked transaction — `createShift`'s `schoolId` lock for the wizard case (the new Shift does not exist yet, so no `shiftId` lock is needed or even possible to acquire meaningfully beforehand), no separate lock for the bootstrap case (mirrors `createDefaultScheduleForSchool`'s own existing no-lock-needed reasoning, since nothing else can reference a school that does not exist yet).
- **`createShift` (extended)** — after inserting the Shift row (inside the same `schoolId`-locked transaction it already uses), calls `generatePeriodStructure(newShift.id, { teachingPeriodCount, includeBreak, breakAfterPeriod }, tx)` using the caller-supplied wizard values or their defaults (`6`/`true`/`3`).
- **`createDefaultScheduleForSchool` (extended)** — after creating the default "Morning" Shift, calls the same `generatePeriodStructure` helper with the fixed default arguments, before returning.
- Repository layer is the only code touching Prisma, per Coding-Standards.md — `period.repository`-shaped functions live in the same `school-schedule.repository.js` file as `Shift`'s own, consistent with this module's existing "one repository file per feature module" shape.

# Stable Public Service Interface

Per this project's established pattern — the only functions another feature module may call directly, in-process; everything else in this module is private.

- `getSchoolCalendar(schoolId)` — returns the school's `SchoolCalendar` row, or `null` if the school somehow has none (should never happen post-Implementation, but the narrow-interface contract is "return null on a miss," matching every other feature's own convention, never throw).
- `getWorkingDays(schoolId)` — the stored `workingDays` array.
- `getWeekendDays(schoolId)` — the derived complement (see Database Impact).
- `getSchoolShifts(schoolId, { status })` — the full list, optionally filtered.
- `getActiveShift(schoolId)` — the school's current Default Shift, the same convenience-default role `academicYearsService.getCurrentAcademicYear` already plays for Academic Year Management (used, for example, by Class Management's own `createClass` to suggest a default `shiftId` when the caller doesn't supply one — mirroring Student Management's own Promotion-default pattern).
- `getShiftById(schoolId, shiftId)` — returns `null` on a miss or cross-school id, never throws, the same contract every other narrow interface in this project already uses.
- `validateWorkingDay(schoolId, dayOfWeek)` — `true` if that weekday is currently a Working Day for this school, `false` otherwise (including for an invalid school or day value) — a genuinely new interface *shape* for this project (every other feature's narrow interface is a plain getter; the Business Specification explicitly named this and `validateShift` as their own published functions, so this design honors that literal shape rather than substituting the "get, then check the fields yourself" pattern other features use).
- `validateShift(schoolId, shiftId)` — `true` if the Shift exists, belongs to the school, and `status === ACTIVE`; `false` otherwise.
- **(Architecture Update — Periods) `getShiftPeriods(schoolId, shiftId, { status })`** — the full list of a Shift's Periods, optionally filtered by status; returns an empty array on a miss or cross-school `shiftId`, never throws — matching the exact function name Business Rule #21 names.
- **(Architecture Update — Periods) `getPeriodById(schoolId, periodId)`** — returns `null` on a miss or a Period whose parent Shift belongs to a different school, never throws, the same contract `getShiftById` already uses.
- **(Architecture Update — Periods) `validatePeriod(schoolId, periodId)`** — `true` if the Period exists, its parent Shift belongs to the school, and the Period's own `status === ACTIVE`; `false` otherwise. The one function future Timetable/Attendance/Exam Management consumers are expected to call before accepting a `periodId` into their own data, the same role `validateShift` plays for Class Management's `shiftId` today.
- No future feature may reach into this module's repository or query `Period` directly — the same Loose Coupling discipline already applied to `SchoolCalendar`/`Shift`.

# Validation Strategy

- All validation happens server-side, in the feature's `validation/` layer, before reaching the service layer — never trust client input, per Coding-Standards.md and API-Standards.md.
- Shape-only in `validation/`: `workingDays` (an array containing only valid `DayOfWeek` enum values, no duplicates); Shift `name` (non-empty string), `startTime`/`endTime` (valid time-of-day strings, `startTime` earlier than `endTime`); `position` (a positive integer) for the reorder action.
- Data-dependent checks — at least one Working Day and one Weekend Day; Shift overlap; exactly one Default Shift, always Active; at least one active Shift; archiving blocked by an active Class reference or current-Default status — all stay in the service layer's assertion helpers, per this project's established validation/service split.
- `PATCH /shifts/{id}` rejects any field other than `name`, `startTime`, `endTime` at the `validation/` layer (Guard by Construction) — `displayOrder`, `isDefault`, and `status` are never modifiable through this endpoint; each has its own dedicated action.
- **(Architecture Update — Periods)** Shape-only: Period `name` (non-empty string), `type` (must be `TEACHING` or `BREAK`, Validation Rule #12); `startTime`/`endTime` are optional, but if either is present both must be present, and `startTime` must be earlier than `endTime` (Validation Rules #13–14). `POST /shifts`'s wizard fields: `teachingPeriodCount` (positive integer), `includeBreak` (boolean), `breakAfterPeriod` (a positive integer not exceeding `teachingPeriodCount`, only meaningful/validated when `includeBreak` is true). `PATCH /periods/{id}` rejects any field other than `name`/`type`/`startTime`/`endTime` (Guard by Construction) — `displayOrder`/`status` are never modifiable through this endpoint.
- **(Architecture Update — Periods)** Data-dependent checks — configured-time containment within the parent Shift (Validation Rule #15); no overlap among a Shift's own active Periods (Validation Rule #16); active Period Display Order unique/contiguous within a Shift (Validation Rule #17); cross-shift/cross-school Period references rejected (Validation Rule #18) — all stay in the service layer, per the same validation/service split as Shift's own checks.

# Error Handling

- Consistent with API-Standards.md's status codes: 401/403 for authentication/role failures, 404 for a nonexistent or cross-tenant Calendar/Shift, 422 for validation and eligibility errors, 409 for state-conflict errors.
- **422** — invalid `workingDays` (wrong enum values, or would leave zero Working or zero Weekend days); missing/invalid Shift `name`/`startTime`/`endTime`; any field other than `name`/`startTime`/`endTime` present in a `PATCH /shifts/{id}` body (Guard by Construction); an invalid `position` value.
- **409** — a new, edited, or reactivated Shift's time range overlapping an existing active Shift (reactivation included — restoring an Archived Shift re-checks overlap against whatever is active now, not just what was active when it was archived); attempting to designate an Archived Shift as Default; attempting to archive the school's only remaining active Shift, its current Default Shift, or a Shift referenced by one or more active Classes.
- Errors never expose internal implementation details, per Coding-Standards.md.
- **(Architecture Update — Periods) 422** — invalid Period `type`; missing/invalid `name`; only one of `startTime`/`endTime` provided; `startTime` not before `endTime`; a configured Period's times falling outside its parent Shift's own operating hours; any field other than `name`/`type`/`startTime`/`endTime` present in a `PATCH /periods/{id}` body; an invalid `position`; an invalid wizard field (`teachingPeriodCount` not positive, `breakAfterPeriod` exceeding `teachingPeriodCount`).
- **(Architecture Update — Periods) 409** — a new, edited, or reactivated Period's time range overlapping another active Period in the same Shift (the same "reactivation re-checks against current state" rule Shift's own reactivation already has).
- **(Architecture Update — Periods, Technical Design Review finding) 409** — editing a Shift's own `startTime`/`endTime` (Shift Correction) in a way that would leave one or more of that Shift's own configured Periods outside the new operating hours. The Admin must first adjust or archive the conflicting Period(s).

# Risks

- **Migration sequencing is a hard, cross-feature ordering constraint, not a soft preference.** School Schedule Management's own migration (and its data backfill of every existing school's default Calendar and Shift) must complete before Class Management's own migration (which backfills every existing Class's `shiftId` from those same rows) can run. Getting this order wrong would either leave Class Management's backfill with nothing to point Classes at, or require Class Management's migration to be re-run. Implementation Planning must sequence these as two explicit, ordered steps.
- **Concurrency — addressed proactively, not deferred, for a combined invariant this codebase has not locked before.** `Shift.isDefault`'s "exactly one" invariant is the same shape Class Management and Academic Year Management already needed a per-school advisory lock for (both found this gap via later code review, not from the start); `Shift.displayOrder`'s contiguous-renumbering invariant has never been locked at all in this codebase — Class Management's own `reorderClass`/`archiveClass`/`nextEndOfSequencePosition` currently run with no `prisma.$transaction` or advisory lock whatsoever. This design locks both invariants together from the first Implementation pass. **Observation, not a fix in scope for this design:** Class Management's own sequencing code appears to have the same unlocked check-then-act shape this project has now fixed three times elsewhere; that is Class Management's own already-Accepted code, and fixing it is outside this feature's scope — flagged here as a candidate for a future, separately-approved Architecture Decision Record against Class Management, not silently patched as a side effect of this work. **Update (Phase 9 review, original Calendar/Shift scope):** a genuinely new instance of this exact class of race was found live during this feature's own Phase 9 code review — `Class.shiftId`'s own validate-then-write path in `createClass`/`updateClass` had no lock at all, so a concurrent `archiveShift` could archive a Shift after `assertShiftAssignable` had already validated it as Active but before the Class row committed, leaving an active Class referencing an Archived Shift with no error to either caller. Reproduced live, then fixed by having `createClass`/`updateClass` acquire the identical `hashtext(schoolId)` advisory lock `archiveShift` already holds (a second, independent copy of the same one-line primitive in Class Management's own repository, not a shared import — see Code-Review-Report.md for the full writeup). This is now the fourth instance of this project's own recurring lesson, and the first one caught live during that same feature's own Phase 9 rather than a later one's.
- **`startTime`/`endTime` as native Postgres `TIME` columns is a new technology choice for this project.** No prior feature has stored a time-of-day-only value; this design chose a native type over a string for data-integrity reasons (see Architecture), but it is worth Technical Design Review's explicit attention as the first instance of this pattern, since it sets precedent for any future feature needing the same kind of value (e.g., Timetable's own period start/end times).
- **The archive-dependency check against `Class.shiftId` (which feature reads which table) is deliberately left as an Implementation Planning decision, not fixed here** — see Backend Design's `archiveShift` note. Either a direct read (justified since this feature's own migration creates the column) or a Subject-Management-style registered extension point are both consistent with this project's existing patterns; picking between them benefits from Implementation-time information this Technical Design does not have.
- **(Architecture Update — Periods) The `shiftId`-scoped advisory lock is a new lock granularity for this project — every prior lock in this codebase has been school-scoped.** The reasoning is laid out in Architecture above; **Technical Design Review confirmed** no Period invariant actually needs school-wide scope (every Business Rule governing Period ordering/overlap is explicitly stated "within the same Shift," never "within the same school") — but Review also found this second lock key introduces a genuine cross-key race (`updateShift` vs. Period writes), fixed by having `updateShift` acquire both locks in a fixed order. **Implementation must confirm no other code path is ever added that acquires `shiftId` before `schoolId`** — the reasoning must be preserved as an in-code comment at both lock-acquisition call sites, not only in this document, so a future contributor doesn't accidentally introduce the reverse order while adding some future write path.
- **(Architecture Update — Periods) Period's nullable `startTime`/`endTime` is a new "structurally valid but unconfigured" record shape.** Every overlap/containment check must correctly treat a `null`-timed Period as "not yet a possible conflict," in both directions (an unconfigured Period neither overlaps anything nor can be overlapped) — this needs explicit test coverage, not just an assumption that skipping the check when times are `null` is obviously correct.
- **(Architecture Update — Periods, resolved by Technical Design Review) The wizard's Period-naming algorithm was inferred from a single worked example, with no assembly rule stated at all.** Both are now made explicit in Backend Design (continuous Teaching numbering through any Break; Break always literally named "Break"; `breakAfterPeriod` is a 1-based insertion point, with equality to `teachingPeriodCount` a valid "Break at the end" case) — no longer an open question for Implementation to guess at.
- **(Architecture Update — Periods, resolved by Technical Design Review) `updateShift` narrowing a Shift's own operating hours could previously leave existing Periods silently out of bounds, with a genuine cross-lock-key race alongside it.** Both closed: `updateShift` now acquires the `shiftId` lock (in addition to, and always after, its existing `schoolId` lock) and re-validates every active Period's containment before committing a narrower range. This was the single most significant finding of this Review — the same *class* of gap ("an edit invalidates a downstream invariant nothing re-checks") the original Shift-only design already made twice, now found a third time at the new Shift/Period boundary specifically *because* Period introduced a second, independent lock key.
