# Overview

This document designs the technical approach for the Business Specification approved in `docs/03-business/Teacher-Subject-Assignment.md` (v1.1).

It applies the already-approved architecture (`System-Architecture.md`, `Folder-Structure.md`), technology stack (`Technology-Decisions.md`), and standards (`Database-Standards.md`, `API-Standards.md`, `Security-Standards.md`, `Naming-Conventions.md`) to this specific feature. No new business rule is introduced anywhere below; every design decision either directly implements an existing Business Rule or is a pure implementation-mechanism choice the Business Specification deliberately left open.

This design deliberately applies a lesson already learned twice in this project — Subject Management's `assignSubjectToSchool` and Academic Year Management's `createAcademicYear`/`archiveAcademicYear`/`designateCurrentAcademicYear` each shipped with an unlocked check-then-act uniqueness race that an independent code review later found and fixed with a Postgres advisory lock. This feature's own uniqueness invariant (Business Rule #4) is designed with that lock from day one, not deferred to a future review finding — see Architecture and Risks below.

# Architecture

- Implemented as a feature module: `backend/src/features/teacher-subject-assignments/` — plural, kebab-case, matching Naming-Conventions.md's existing worked examples (`students`, `academic-years`, `classes`, `subjects`).
- **Web vs. Mobile split, per System-Architecture.md's Applications section:** School Admin (create, view, correct, end, replace, copy) is a Web-only role — this entire management surface belongs in `web/src/features/teacher-subject-assignments/`. Teacher's own read-only self-service view (Business Specification's Permissions section) belongs on Mobile only, in `mobile/lib/features/teacher/`, since Teacher is a Mobile-application role, not a Web-application role — the same split Student Management already established for Student's own self-service. The backend endpoint itself (`GET /teacher-subject-assignments/me`) is not blocked by Mobile's own absence — it is built now, exactly as `GET /students/me` was built before any Mobile screen existed to call it — but the Mobile screen itself is deferred to a future Mobile bootstrap phase, per Student Management's own precedent.
- **Assignment status (Active/Ended) is a derived, non-stored value, never a database column** — computed as `effectiveEndDate === null ? 'ACTIVE' : 'ENDED'`, per Business Rule #10. This mirrors Academic Year Management's own "no stored derived label" judgment call (there, the `YYYY/YYYY` label; here, the status itself), applying the same reasoning: a derived value stored redundantly can drift from the fields that actually define it, while a `deriveAssignmentStatus(assignment)` helper, called wherever the API response is shaped, never can.
- **Business Rule #4's uniqueness invariant — "exactly one Active assignment per School + Academic Year + Class + Section (or its absence) + Subject" — needs a partial, nullable-aware unique index, which plain Prisma schema DSL cannot express.** Two distinct technical difficulties stack here, both handled the same way Academic Year Management's own `isCurrent` invariant was: a hand-written raw SQL statement appended to the generated migration file.
  1. The index must be **partial** (`WHERE "effectiveEndDate" IS NULL`) — only Active rows participate in the uniqueness check; Ended rows for the same scope must never conflict with each other or with a new Active row.
  2. The index must treat `sectionId IS NULL` as equal to itself for uniqueness purposes (two whole-Class assignments, both with `sectionId = NULL`, for the same Subject/Academic Year, must still collide) — Postgres's default unique-index behavior treats every `NULL` as distinct from every other `NULL`, which would silently defeat the invariant for exactly the Class-with-no-Sections case Business Rule #23 relies on. Postgres 15+ (this project's Postgres 16) supports `UNIQUE NULLS NOT DISTINCT` for precisely this situation, avoiding a `COALESCE`-based functional-index workaround:
     ```sql
     CREATE UNIQUE INDEX "teacher_subject_assignments_active_scope_unique"
       ON "teacher_subject_assignments" ("schoolId", "academicYearId", "classId", "subjectId", "sectionId")
       NULLS NOT DISTINCT
       WHERE "effectiveEndDate" IS NULL;
     ```
  3. As with every other two-layer invariant in this project (`Class.isFinal`, `AcademicYear.isCurrent`), this index is the **backstop**, not the primary mechanism — the primary mechanism is an application-level check inside a transaction, described next.
- **A Postgres advisory lock, scoped per school, is acquired as the first statement inside every transaction that could create a new Active assignment** — direct creation, Replace Teacher, and each individual candidate inside a copy operation — via `pg_advisory_xact_lock(hashtext(schoolId))`, serializing all such writes for one school. This is the exact pattern Academic Year Management's own code review converged on; applying it here from the start, rather than waiting for an identical finding a third time, is a deliberate choice, not an oversight. Locking at school granularity (rather than a finer hash of the full uniqueness-scope tuple) is a deliberate simplicity choice consistent with Academic Year Management's own precedent — see Risks.
- **A new narrow interface addition to Teacher Management: `getTeacherById(schoolId, teacherId)`.** Teacher Management's current public surface (`getTeacherOrThrow`) throws on a not-found or cross-school Teacher, which does not fit this project's established Stable Public Service Interface contract — every other narrow read interface a feature exposes to another feature (`classesService.getClassById`, `subjectsService.getSubjectById`, `academicYearsService.getAcademicYearById`) returns `null` on a miss, letting the *calling* feature decide its own error shape. `getTeacherById` is added to `teachers.service.js`'s exports, alongside the existing `getTeacherOrThrow` (unchanged, still used internally by Teacher Management's own routes), following exactly the pattern Class Management's `listActiveSectionsForClass` and School Management's `hasEducationLevel` already established: an additive, non-breaking interface extension to an already-Accepted feature that does not reopen that feature's own Feature Acceptance.
- **Subject Management's dependency-validation extension point is consumed, not extended.** This module registers its own checker — `subjectsService.registerRemovalDependencyCheck('teacher-subject-assignments', checkFn)` — at its own module-load time (this project's app.js require-order guarantee, already relied upon by every prior consumer of this same registry). `checkFn(schoolId, subjectId)` queries for any Active `TeacherSubjectAssignment` referencing that `(schoolId, subjectId)` pair and returns a blocking reason string if one exists, `null` otherwise. No change to Subject Management's own code is required.
- **The "past Academic Year with downstream records" reason requirement (Business Rule #17) is designed as its own extensibility registry, mirroring Subject Management's dependency-validation registry exactly** — `registerDownstreamRecordCheck(name, checkFn)`, where `checkFn(schoolId, academicYearId, classId, subjectId) -> boolean`. If the target Academic Year's `endDate` is in the past and any registered checker returns `true`, a non-empty `reason` becomes mandatory on that create/copy-candidate call and the event is audited with it; if the registry is empty (as it is today, since Attendance, Exams, Grade Book, and Report Cards are all future, unbuilt features), a past-year assignment is always the "normal operation" case — this rule is not reachable in practice yet, the same "N/A until a future feature exists" situation Academic Year Management's own Business Rule #10 documented for its Validation Report.

# Database Impact

Conceptual data shape only — field-level schema is a separate Database Design exercise if the Product Owner wants one produced.

- A `TeacherSubjectAssignment` entity capturing: an owning-school reference (required — every assignment belongs to exactly one school, per Business Rule #2), a reference to the Academic Year (Academic Year Management's entity), a reference to the Teacher (Teacher Management's entity), a reference to the Subject (Subject Management's platform-wide catalog entity — validity of "is this Subject actually assigned to this school" is checked at write time via `isSubjectAssignedToSchool`, never modeled as a stored join reference), a reference to the Class (Class Management's entity), an optional reference to a Section within that Class (nullable, mirroring Student Management's own `Enrollment.sectionId` precedent from ACR-002 exactly), `effectiveStartDate` (required `DateTime`), `effectiveEndDate` (nullable `DateTime`), `endReason` (nullable `String`), and standard `createdAt`/`updatedAt` timestamps.
- No `status` column exists — it is always derived from `effectiveEndDate`, per the Architecture section above.
- The partial, `NULLS NOT DISTINCT` unique index described in Architecture is the database-level backstop for Business Rule #4; the application-level advisory-lock-guarded check inside each write transaction is the primary mechanism, per this project's established two-layer pattern.
- No separate uniqueness constraint is needed for historical (Ended) rows — Business Rule #4 governs only Active assignments; two Ended rows for the same scope, or an Ended row and a new Active row for the same scope, never conflict with each other.
- Relationship cardinality: School → TeacherSubjectAssignment is one-to-many; Academic Year, Teacher, Subject, and Class are each referenced many-to-one (an Academic Year/Teacher/Subject/Class may appear on many assignments); Section is optionally referenced many-to-one.
- Indexing: `schoolId` (every list/filter query is scoped to one school), `schoolId` + `academicYearId` together (the most common list filter, per Functional Requirement #3), `teacherId` (for Teacher self-service's own `/me` query and the "Teacher" list filter), per Database-Standards.md's indexing guidance.
- Assignment lifecycle audit events are written to the platform's shared audit log mechanism, consistent with the standard audit record (Tenant, User, Action, Timestamp) defined in Multi-Tenancy.md.

# API Design

High-level shape only — exact payloads and per-case status codes belong in a separate API Specification if requested.

- REST, versioned under `/api/v1`, per API-Standards.md. Resource name is plural: `/teacher-subject-assignments`, consistent with Naming-Conventions.md's API Endpoints section.
- `POST /teacher-subject-assignments` — create (School-Admin-only). Body: `teacherId`, `subjectId`, `classId`, `sectionId` (required or forbidden depending on whether the Class has active Sections, Business Rule #23), `academicYearId` (optional — defaults to the school's Current Academic Year, Business Rule #16 predecessor's own "suggest, don't enforce" pattern, mirroring how Promotion's Academic Year default already works in Student Management post-ACR-004), `effectiveStartDate` (required), `effectiveEndDate` (optional), `reason` (required only when Business Rule #17's downstream-record check applies — see Architecture).
- `GET /teacher-subject-assignments` — list (School-Admin-only), paginated, filterable by `academicYearId`, `teacherId`, `subjectId`, `classId`, `sectionId`, per Functional Requirements #3–#4.
- `GET /teacher-subject-assignments/{id}` — single record detail (School-Admin-only).
- `PATCH /teacher-subject-assignments/{id}` — correction (School-Admin-only). Accepts only `effectiveStartDate`, `effectiveEndDate`, `endReason`, each independently optional (partial-update semantics, mirroring Teacher Management's own profile-update endpoint) — any other field in the body is rejected (Guard by Construction, Business Rule #11). This single endpoint covers both "Assignment Correction" and "Assignment Ending" from the Business Lifecycle section: setting a previously-unset `effectiveEndDate` for the first time *is* ending the assignment; adjusting an already-set `effectiveEndDate` or `endReason` afterward is a correction. Attempting to clear an already-set `effectiveEndDate` back to `null` is rejected (Business Rule #24).
- `POST /teacher-subject-assignments/{id}/replace-teacher` — the dedicated Replace Teacher workflow (School-Admin-only), a named action mirroring Academic Year Management's `/current` and Class Management's `/designate-final` precedent. Body: `newTeacherId`, optional `effectiveEndDate` (defaults to the current date), optional `endReason`. Ends the existing assignment at that date and creates a new assignment for the same Subject/Class/Section/Academic Year with `newTeacherId`, starting on that same date, atomically (Business Rule #9).
- `POST /teacher-subject-assignments/copy` — the selective copy action (School-Admin-only). Body: `fromAcademicYearId`, `toAcademicYearId`, `assignmentIds` (an explicit array — copying is always selective, per Business Rule #12, never "copy everything"). Response: `{ copied: [...], skipped: [{ assignmentId, reason }, ...] }`, per Business Rule #13.
- `GET /teacher-subject-assignments/me` — Teacher self-service (Teacher-only), resolved strictly from the authenticated Teacher's own token, never a client-supplied `teacherId`, per Security-Standards.md and Business Rule #1's read-only self-service grant. No write endpoint exists for this role.
- **(UI Redesign) `GET /teacher-subject-assignments/grouped`** — School-Admin-only, registered before `/:assignmentId` so the literal path is never captured as a param. A pure read-side presentation over the exact same Active rows `GET /teacher-subject-assignments` already returns, grouped Teacher → Subject → Classes for the approved presentation change; optionally filtered by `academicYearId` (defaults to the school's Current Academic Year, the same default `POST` itself already uses). Response shape: `[{ teacherId, teacherName, subjects: [{ subjectId, subjectName, classes: [{ assignmentId, classId, className, sectionId }] }] }]` — deliberately minimal, carrying only identity fields needed to render the grouped view and to re-open the existing Correct/End and Replace Teacher actions against a specific `assignmentId`; no weekly lesson target, workload, or any other field is added to this shape, per this feature's own reaffirmed narrow responsibility.
- Every endpoint requires a valid JWT and passes through the same Authentication/Authorization middleware chain every other feature already uses; no new authentication mechanism is introduced.

# Backend Design

- New feature module `backend/src/features/teacher-subject-assignments/`, structured per Folder-Structure.md (controller, service, repository, validation, routes, tests).
- The service layer enforces every data-dependent Business Rule via a set of shared assertion helpers, each called from every write path that needs it (creation, Replace Teacher, and each copy candidate) — mirroring Student Management's own `assertClassEnrollable`/`assertSectionEnrollable`/`assertAcademicYearEnrollable` shared-helper pattern exactly:
  - `assertTeacherAssignable(schoolId, teacherId)` — Teacher exists, belongs to this school, and is ACTIVE (Business Rule #7), via `teachersService.getTeacherById` (the new narrow interface addition described in Architecture).
  - `assertSubjectAssignable(schoolId, subjectId)` — Subject exists, is ACTIVE, and is currently assigned to this school (Business Rule #14), via `subjectsService.getSubjectById` and `subjectsService.isSubjectAssignedToSchool`.
  - `assertClassSectionAssignable(schoolId, classId, sectionId)` — Class exists, belongs to this school, and is ACTIVE (Business Rule #15); if the Class has one or more active Sections (via `classesService.listActiveSectionsForClass`), `sectionId` is required and must resolve to one of them; if the Class has none, `sectionId` must be absent (Business Rule #23) — the same "one shared helper both requires and validates" design Student Management's `assertSectionEnrollable` already established.
  - `assertAcademicYearAssignable(schoolId, academicYearId)` — Academic Year exists, belongs to this school, and is not Archived (Business Rule #16), via `academicYearsService.getAcademicYearById`. When `academicYearId` is omitted on create, it defaults to `academicYearsService.getCurrentAcademicYear(schoolId)`'s own id first, then still passes through this same assertion — the defaulted value can never bypass validation, mirroring Student Management's own Promotion-default pattern post-ACR-004 exactly.
  - `assertNoActiveDuplicate(schoolId, { academicYearId, classId, sectionId, subjectId }, tx)` — queries for an existing row matching the full scope with `effectiveEndDate IS NULL`; throws `ConflictError` if found (Business Rule #4). Always called last, after every other assertion has already passed, and always inside the same locked transaction as the eventual insert.
  - `assertReasonIfDownstreamRecordsExist(schoolId, { academicYearId, classId, subjectId }, reason)` — Business Rule #17; walks the `downstreamRecordCheckers` registry described in Architecture, requiring a non-empty `reason` only if the target Academic Year's `endDate` is in the past and at least one registered checker reports a downstream record. The registry starts empty, so this assertion is currently a no-op for every call — expected, not a defect, mirroring Subject Management's own "registry currently has zero registered checkers" note.
- **`createAssignment`, `replaceTeacher`, and each individual candidate inside `copyAssignments` each wrap their entire read-decide-write sequence in one `prisma.$transaction`, acquiring the per-school advisory lock as the first statement**, per Architecture — the same fix-shape Academic Year Management's own code review converged on, applied proactively here.
- `replaceTeacher(assignmentId, { newTeacherId, effectiveEndDate, endReason }, actingUser)` — inside the locked transaction: loads the existing assignment (must belong to the school and be Active, else `ConflictError`), sets its `effectiveEndDate`/`endReason`, then creates the replacement row through the exact same internal creation path `createAssignment` itself uses — running `assertTeacherAssignable` (for `newTeacherId`), `assertSubjectAssignable`, `assertClassSectionAssignable`, and `assertAcademicYearAssignable` against the carried-over `academicYearId`/`classId`/`sectionId`/`subjectId`, not merely re-checking the new Teacher. **This is a direct application of Business Rule #18's own wording** — "archiving only prevents that Class, Section, or Academic Year from being selected for a new assignment **or replacement** afterward" — which the Business Specification states explicitly for Class/Section/Academic Year and which this design extends identically to Subject eligibility (Business Rule #14), for the same reason: a Replace Teacher is, underneath, creating a new assignment row, so it must clear every eligibility gate a direct creation would. By the time the replacement row's `assertNoActiveDuplicate` check runs, the old row is already Ended within the same transaction, so no artificial "exclude this id" parameter is needed anywhere.
- `copyAssignments({ fromAcademicYearId, toAcademicYearId, assignmentIds }, actingUser)` — for each id: loads the source assignment (must belong to the school and to `fromAcademicYearId`; `fromAcademicYearId` itself is never required to be non-Archived — copying reads a source year's history, it does not create anything in it, so an Archived source year, the most common real case for "copy last year's assignments," is explicitly allowed), attempts `createAssignment` against `toAcademicYearId` with the same `teacherId`/`subjectId`/`classId`/`sectionId` and `effectiveStartDate` defaulted to `toAcademicYearId`'s own `startDate` (a Technical Design mechanism choice — the source assignment's own dates belong to a different Academic Year and are never directly reusable); `toAcademicYearId` itself must pass `assertAcademicYearAssignable` like any other target. Each candidate's own assertion failure is caught individually and recorded as a `skipped` entry with a human-readable reason (Business Rule #13); one candidate's failure never aborts another's attempt, and no partial/corrupted row is ever left behind, since each candidate's own creation is its own complete transaction.
- Cross-feature calls are the feature's only dependencies — direct in-process service calls, consistent with System-Architecture.md's Modular Monolith style: `teachersService.getTeacherById` (new), `subjectsService.getSubjectById`/`isSubjectAssignedToSchool`/`registerRemovalDependencyCheck` (existing), `classesService.getClassById`/`listActiveSectionsForClass` (existing), `academicYearsService.getAcademicYearById`/`getCurrentAcademicYear` (existing).
- Repository layer is the only code touching Prisma, per Coding-Standards.md.
- **(Weekly Subject Allocation Integration) `getTeacherWeeklyCommitmentAndCapacity(schoolId, teacherId, academicYearId)`** — a new, additive, read-only narrow-interface function, Product Owner-approved as the reusable *getter* half of Timetable's own new Teacher weekly capacity Hard Constraint (the *enforcement* half lives entirely in Timetable's own generation pre-flight — see that feature's Technical Design — never here, since a Teacher's total commitment can go invalid purely from a Weekly Subject Allocation edit, with no write to this feature happening at all, so no write-time gate on this side could ever be reliable on its own). Computes:
  - `committed` — the sum of `weeklyPeriods`, read via Weekly Subject Allocation's own `getWeeklyPeriodsForAssignment`, across every one of this Teacher's Active assignments for the given Academic Year (an assignment with no matching allocation line contributes `0`, never a silent default).
  - `capacity` — Working Days × Teaching Periods, summed once per **distinct** Shift referenced by those same assignments' own Classes (via `classesService.getClassById`), read through `schoolScheduleService.getWorkingDays`/`getShiftPeriods` — never per-Class, since two Classes on the same Shift would otherwise double-count identical capacity; Shifts never overlap in time within a school, per School Schedule Management's own Business Rules, so summing distinct Shifts is always valid. Deliberately **not** reduced by the Teacher's own `unavailableSlots` (Timetable's `TeacherSchedulePreference`) — that finer-grained exclusion is already correctly handled by generation's own existing per-slot Hard Constraint at actual placement time; this function only catches the unambiguous case of committed periods exceeding the full week.
  - Requires a lazy, in-function `require('../weekly-subject-allocations/weekly-subject-allocations.service')` (not a top-level import) — Weekly Subject Allocation's own module already requires this module at its own top level (for `getActiveTeacherIdsForSubjectAcrossClasses`), so a top-level require here would create a genuine load-time cycle; this mirrors this project's own established lazy-require precedent (`schools.service.js`, `timetable.generation.js`'s `getService()`).

# Validation Strategy

- All validation happens server-side, in the feature's `validation/` layer, before reaching the service layer — never trust client input, per Coding-Standards.md and API-Standards.md.
- Shape-only validation in `validation/`: `teacherId`, `subjectId`, `classId`, `academicYearId` (non-empty strings when present), `sectionId` (non-empty string when present), `effectiveStartDate`/`effectiveEndDate` (valid dates, end not preceding start when both present), `endReason`/`reason` (strings when present). Whether a given value is *eligible* (ACTIVE, assigned-to-school, belongs-to-school, Archived, required-vs-forbidden based on Sections, duplicates the Active scope, requires a reason due to downstream records) is a data-dependent, cross-feature-lookup concern and stays entirely in the service layer's assertion helpers, never in `validation/` — the same split every other feature in this project already follows for `classId`/`sectionId`/`academicYearId`-shaped fields.
- `PATCH /teacher-subject-assignments/{id}` rejects any field other than `effectiveStartDate`, `effectiveEndDate`, `endReason` in the request body at the `validation/` layer (Guard by Construction) — `teacherId`, `subjectId`, `classId`, `sectionId`, `academicYearId` are immutable per Business Rule #11 and must never even reach the service layer if present in a correction request.
- `PATCH` uses standard partial-update semantics: a field **absent** from the body is left unchanged; a field explicitly present with value `null` is treated as an attempt to clear it. This distinction is what makes Business Rule #24 enforceable: omitting `effectiveEndDate` from a correction request never triggers the "cannot un-end" check (nothing was clearing it), while explicitly sending `effectiveEndDate: null` against an already-Ended assignment does.

# Error Handling

- Consistent with API-Standards.md's status codes: 401/403 for authentication/role failures, 404 for a nonexistent or cross-tenant assignment, 422 for validation and eligibility errors, 409 for state-conflict errors.
- **422** — missing/invalid shape on any field; `teacherId` not ACTIVE or cross-school; `subjectId` not ACTIVE or not assigned to the school; `classId`/`sectionId` not ACTIVE, cross-school, or violating the Section-required/forbidden rule (Business Rule #23) — each collapsed into one message per field, mirroring `assertSectionEnrollable`'s and `assertAcademicYearEnrollable`'s own established "one message, one status code" simplification, rather than a 404-vs-409 split; `academicYearId` Archived or cross-school; a missing `reason` when Business Rule #17 applies; any field other than `effectiveStartDate`/`effectiveEndDate`/`endReason` present in a `PATCH` body (Guard by Construction).
- **409** — a duplicate Active assignment for the same scope (Business Rule #4) on direct creation or Replace Teacher; an attempt to clear an already-set `effectiveEndDate` back to unset (Business Rule #24); a Replace Teacher attempt against an assignment that is not currently Active.
- A copy operation's own per-candidate failures never surface as an HTTP error — each is caught internally and reported in the response body's `skipped` array with its own reason string, per Business Rule #13; the overall `POST /teacher-subject-assignments/copy` request itself always returns 200 (or 201) as long as the request shape itself was valid, regardless of how many candidates were skipped.
- Errors never expose internal implementation details, per Coding-Standards.md.

# Risks

- **Concurrency — addressed proactively, not deferred.** Subject Management's `assignSubjectToSchool` and Academic Year Management's `createAcademicYear`/`archiveAcademicYear`/`designateCurrentAcademicYear` each shipped their first Implementation pass with an unlocked check-then-act race that an independent code review later found and fixed with a per-school Postgres advisory lock. This Technical Design specifies that same lock, and the same `NULLS NOT DISTINCT` partial-unique-index backstop, from the very first Implementation pass — see Architecture. If a future code review still finds a gap here, it should be a genuinely new finding, not a repeat of this exact pattern for a third time.
- **Lock granularity is per-school, not per-exact-scope.** A finer-grained lock (hashing the full `schoolId`+`academicYearId`+`classId`+`subjectId`+`sectionId` tuple) would allow more concurrent writes within the same school across different Classes/Subjects, but this project has consistently chosen the coarser, simpler per-school lock for its uniqueness invariants (Academic Year Management's own `isCurrent` lock is likewise per-school, not per-more-granular-scope) given the expected low, manually-driven write volume for this kind of record. Accepted as a deliberate simplicity choice, not an oversight — revisit only if real usage ever shows write contention.
- **The downstream-record-check registry (Business Rule #17) starts empty.** A past-Academic-Year assignment requiring an explicit reason is not reachable in practice today, since Attendance, Exam Management, Grade Book, and Report Cards — the only features that could ever register a checker — do not exist yet. This is expected, not a defect, mirroring Subject Management's own "registry currently has zero registered checkers" note; worth flagging so a future reviewer doesn't mistake an always-unreachable rule for a missed check.
- **Teacher self-service has no Mobile UI yet.** The backend endpoint (`GET /teacher-subject-assignments/me`) is built and testable independently, but Teacher-facing verification of this feature is limited to API-level checks until Mobile is bootstrapped — the same situation Student Management's own Student self-service has been in since its own Implementation.
