# Overview

This document designs the technical approach for the Business Specification approved in `docs/03-business/Class-Management.md`.

It applies the already-approved architecture (`System-Architecture.md`, `Folder-Structure.md`), technology stack (`Technology-Decisions.md`), and standards (`Database-Standards.md`, `API-Standards.md`, `Security-Standards.md`, `Naming-Conventions.md`) to this specific feature. Unlike Student Management, this feature has no blocking dependency — it depends only on School & Platform Management (Approved), which is why it was re-sequenced ahead of Student Management in `Development-Roadmap.md`. Implementation Planning may proceed directly after this document is approved.

# Architecture

- Implemented as a feature module: `backend/src/features/classes/` — Folder-Structure.md already anticipates this exact module name in its feature list.
- A Class is a single, evergreen record per Business Rule #5 — it is never recreated per academic year. The academic year a Student is enrolled for lives entirely on Student Management's Enrollment record; this feature's schema has no academic-year concept at all.
- Class sequencing (Business Rule #6) is modeled as an explicit integer position on each Class, unique within its school. "The next Class" is derived by querying the Class with the next-higher position in the same school — not a linked-list of "next class" pointers, which would be harder to reorder safely. This is the simplest structure that satisfies "Classes within a school have a defined order," per "Simplicity Wins" (Decision-Making-Principles #2).
- The final-Class designation (Business Rule #7) is a boolean flag on the Class record, constrained so exactly one Class per school can hold it — see Database Impact for how this is enforced.
- This feature exposes a small, narrow public interface for Student Management to call, rather than Student Management querying this feature's tables directly, per Decision-Making-Principles' Feature Ownership and Loose Coupling (Principle 6):
  - "Get Class by ID" (used by Enrollment to validate the target Class exists, belongs to the same school, and is not archived).
  - "Get suggested next Class" (used by Promotion to default the destination; the Business Specification's Business Rule #6 requires School Admin be able to override this suggestion, so this feature never enforces the sequence as a hard constraint on Student Management's Promotion — it only supplies a suggestion).
  - "Get final Class" (used by Student Management to determine when a Student's Promotion transitions them into "Eligible for Graduation," per Student-Management.md's Business Rule #10). Per Student-Management.md's Technical Design, that transition is written once by Student Management and never re-derived — this feature has no responsibility for, and no visibility into, that stored state.
  - **(ACR-002) "List active Sections for a Class"** — `listActiveSectionsForClass(schoolId, classId)`, returning each active Section's `id` and `name`. This is the one addition ACR-002 requires: Student Management uses it both to validate a Student's chosen `sectionId` (present in the list → belongs to the Class and is active; a `sectionId` failing either check is invalid) and, in Promotion, to find a same-`name` Section in the destination Class to suggest. A single function serves both needs — no second, narrower function was added, per "Avoid Premature Abstraction."
- This feature has no responsibility for Enrollment, and therefore no reference to Student or Enrollment records anywhere in its own module — Enrollment referencing a Class is a dependency in one direction only (Student Management depends on Class Management), never the reverse, keeping this module's public interface small and stable per the Constitution's Loose Coupling principle. **(ACR-002) This remains true even with the new interface addition above** — it is a read-only query this feature exposes; this feature still never calls into Student Management, and still has no `Enrollment`/`Student` reference anywhere in its own schema or code.
- **(ACR-002) Combined Class+Section display convention.** Wherever a Class and Section are presented together in the Web UI, they are shown as one combined name — Class "F1" + Section "A" → "F1A" — formatted by a single shared frontend utility (see Frontend Design), never persisted, never a value any backend endpoint accepts or returns, and never parsed back apart to derive business meaning (Student-Management.md's ACR-002 Business Rules #18–#19 explicitly forbid deriving a Section from this string). A Class's own `name` field and a Section's own `name` field are completely free-form and unconstrained by this convention — the display formatter simply concatenates them; no validation requires a Section's name to be a single letter or to combine cleanly, since the combined string is presentation-only.

## Architecture Update (Grade/Form)

Following **ACR-009** (`docs/01-architecture/Architecture-Decision-Records/ACR-009-Class-Grade-Level-Reference.md`), itself a direct consequence of Weekly Subject Allocation's own Business Review (`docs/03-business/Weekly-Subject-Allocation.md` v1.0, Approved). This is the same category of event as School Schedule Management's own "Architecture Update (Periods)" — a new entity, owned by this already-Accepted feature, added in response to a genuine need surfaced by a later feature's Business Review, not a redesign of anything this feature already shipped.

- **`GradeLevel` is a new, fourth entity owned by this same module** — school-scoped, named, orderable, archivable, the same shape as School Schedule Management's own `Shift` (a school-scoped grouping concept one level up from the thing it groups), but sitting one level *above* `Class` rather than beside it. This module now owns `Class`, `Section`, and `GradeLevel` — still one feature, per ACR-009's own explicit reasoning that a Grade/Form is fundamentally a grouping *of Classes*, the same category of concept Class Management already owns for `Section`.
- **`Class` gains a required `gradeLevelId` foreign key to `GradeLevel`.** Unlike `Class.shiftId` (ACR-005), whose owning entity `Shift` belongs to a *different* feature (School Schedule Management) and was therefore designed and backfilled entirely within that other feature's own Technical Design, `GradeLevel` and the `Class.gradeLevelId` column that references it both live inside this same module — there is no cross-feature design split here the way there was for `shiftId`.
- **New Business Rule, enforced here, not by Weekly Subject Allocation**: every Class within the same `GradeLevel` must reference the same `shiftId`. This is what makes "a Grade/Form's own available weekly teaching periods" a single, well-defined number for Weekly Subject Allocation's own calculation (its own Architecture Questions #1–#2, both resolved by this ACR) — but the constraint itself is this feature's own responsibility to enforce, at `createClass`/`updateClass` time, the same way this feature already enforces its own name-uniqueness and final-Class-exclusivity invariants without any downstream consumer needing to re-check them.
- **No `shiftId` is stored on `GradeLevel` itself** — deliberately, per ACR-009's own "structural reference, never a second stored source of truth" reasoning, the same discipline already applied to `Lesson` never storing its own `shiftId`. A Grade/Form's own effective Shift is always derived by reading any one of its Active member Classes' own `shiftId` (guaranteed identical across all of them by the Business Rule above).
- **Honest, imperfect backfill — the same category of judgment call ACR-009 itself already made explicit, not softened here.** Unlike `Class.shiftId`'s own backfill (every school already had exactly one well-defined Default Shift to point every Class at), no reliable automatic mapping exists from an existing Class to a real Grade/Form. The migration creates one placeholder `GradeLevel` per school — `name: "Ungrouped"`, `status: ACTIVE`, `sequenceOrder: 1` — and backfills every pre-existing Class to it. This placeholder is **not** meant to be a School Admin's real, ongoing Grade/Form; see Frontend Design for how it is surfaced as a distinct, temporary artifact rather than left indistinguishable from a deliberately-created Grade/Form.
- This feature exposes new narrow interface functions alongside the existing `getClassById`/`getFinalClass`/`listActiveSectionsForClass` — for Weekly Subject Allocation's own future consumption (see Backend Design below). No other feature reads `GradeLevel` rows directly.

# Database Impact

Conceptual data shape only — field-level schema is a separate Database Design exercise if the Product Owner wants one produced.

- A Class entity capturing: an owning-school reference (required — every Class belongs to exactly one school, per Multi-Tenancy.md), a name, a sequence position (integer, unique within the school), a final-Class flag, a lifecycle status (`ClassStatus` enum: `ACTIVE` / `ARCHIVED`, PascalCase enum name and UPPER_SNAKE_CASE values per Naming-Conventions.md's Enums section), and standard `createdAt` / `updatedAt` timestamps per Database-Standards.md. **(ACR-005)** A required `shiftId` reference to School Schedule Management's own `Shift` entity — added via a migration that backfilled every pre-existing Class to its own school's Default Shift before the column was made `NOT NULL`; validated only through that feature's own narrow interface (`validateShift`, `getActiveShift`), never a direct query.
- A Section entity capturing: a reference to its Class, a name, a lifecycle status, and timestamps. Section → Class is many-to-one, required — a Section never exists without exactly one owning Class, per Business Rule #4.
- Uniqueness constraints, per Database-Standards.md's "protect the database itself, not only via application validation":
  - Class name unique within `schoolId` (not platform-wide), per Business Rule #3.
  - Class sequence position unique within `schoolId`, so "the next Class" is never ambiguous.
  - Exactly one Class per `schoolId` may have the final-Class flag set. Prisma's schema DSL does not directly express a partial unique constraint ("unique where flag = true"); this requires a partial unique index added via a custom SQL migration step on top of the Prisma-generated migration — a narrow, justified exception noted here explicitly, not a silent deviation from Database-Standards.md's "only Prisma accesses the database" (the constraint is still defined in a Prisma migration, only expressed as raw SQL within it, which Database-Standards.md already anticipates: "Raw SQL should be used only when Prisma cannot reasonably solve the problem").
- Archiving a Class or Section follows Database-Standards.md's Soft Delete Policy and Archive Before Delete — status changes to `ARCHIVED`, never a hard delete, per Business Rule #9. Reactivating reverses only the status change (back to `ACTIVE`); a reactivated Class's sequence position is reassigned to the end of the current active sequence, per Business Rule #11 — it never reuses its pre-archival position, which may since have been reassigned to another Class or fallen out of a meaningful range.
- Relationship: Class → School is many-to-one, required. Section → Class is many-to-one, required. No relationship to Student or Enrollment exists in this feature's own schema (see Architecture).
- Class lifecycle audit events are written to the platform's shared audit log mechanism, consistent with the standard audit record (Tenant, User, Action, Timestamp) defined in Multi-Tenancy.md — the same mechanism every other feature's design already uses.
- Indexing: `schoolId` should be indexed on both Class and Section, since every listing/roster query and the uniqueness constraints above are scoped to it, per Database-Standards.md's indexing guidance.

## Architecture Update (Grade/Form) — new enum and `GradeLevel`

```prisma
enum GradeLevelStatus {
  ACTIVE
  ARCHIVED
}
```

`GradeLevelStatus` duplicates `ClassStatus`'s own two-value shape rather than reusing it, consistent with this project's existing "one status enum per owning entity" convention (`ShiftStatus`, `PeriodStatus`, `SubjectStatus`, `AcademicYearStatus` all made the identical choice).

- `GradeLevel`: `id`, `schoolId`, `name String` (school-configurable free text — `"Grade 8"`, `"Form 1"` — never a fixed platform enum, since naming conventions vary by school, the same reasoning `Shift.name` already established), `sequenceOrder Int` (display ordering), `status GradeLevelStatus @default(ACTIVE)`, `createdAt`/`updatedAt`. `classes Class[]` back-relation.
- **(Technical Design Review finding, fixed here, see Change History) `sequenceOrder` is a real, maintained contiguous 1..N sequence, unique within `schoolId` — not a "set once at creation, never renumbered" value.** The v1.0 draft of this Architecture Update claimed no renumbering invariant was needed, while API Design and Backend Design both already specified a dedicated `PATCH /grade-levels/{id}/sequence` reorder action — an internal contradiction, since a reorder action only makes sense against a real, maintained sequence. Resolved in favor of the sequence being real: `GradeLevel` follows `Class.sequenceOrder`'s own exact convention, including keeping Archived rows *in* the sequence (appended after actives, per `Class`'s own established behavior) — not `Shift.displayOrder`'s alternate "archived rows hold no position" convention, since nothing in this Architecture Update ever described `GradeLevel` needing that divergent behavior.
- `Class` gains a required `gradeLevelId String` with a foreign key to `GradeLevel`.
- Uniqueness: `GradeLevel` name unique within `schoolId`, the same "unique within school, not platform-wide" convention `Class.name` and `Shift.name` already follow.
- **No partial unique index of any kind is needed for `GradeLevel` itself** — unlike `Class.isFinal`/`Shift.isDefault`/`AcademicYear.isCurrent`, a `GradeLevel` has no "exactly one X" flag; any number of Active `GradeLevel` rows are simultaneously valid.
- **Migration is two ordered steps, the same "nullable first, backfilled, then `NOT NULL`" shape ACR-005 already established for `Class.shiftId`:** (1) create `GradeLevel`, insert one placeholder row per existing school (`name: "Ungrouped"`, `sequenceOrder: 1`, `status: ACTIVE`); (2) add `Class.gradeLevelId` nullable, backfill every existing Class to its own school's new placeholder `GradeLevel`, then alter to `NOT NULL`. Both steps belong to this feature's own migration — there is no cross-feature migration-sequencing constraint here (unlike ACR-005's `Class.shiftId`, which had to wait for School Schedule Management's own separate migration to seed a real Default Shift first) — the placeholder `GradeLevel` is created by, and within, this same feature's own migration.
- **New Business Rule enforced at write time, not by a database constraint**: every Class within one `GradeLevel` must share the same `shiftId`. Checked inside `createClass`/`updateClass` — assigning a Class to a `GradeLevel` that already has one or more Active member Classes on a *different* `shiftId` is rejected (409). This is an application-level invariant, the same category as this feature's own existing final-Class-exclusivity check, not something Postgres itself can express as a simple constraint (it spans two columns across a self-referencing set of sibling rows).
- Indexing: `GradeLevel.schoolId` (every list/filter query is scoped to one school); `Class.gradeLevelId` (Weekly Subject Allocation's own future per-Grade/Form Class lookups will filter by it).

# API Design

High-level shape only — exact routes, payloads, and per-case status codes belong in a separate API Specification if requested.

- REST, versioned under `/api/v1`, per API-Standards.md. Resource name is plural: `/classes`, consistent with Naming-Conventions.md's API Endpoints section. Sections are nested under their owning Class, per API-Standards.md's Nested Resources guidance: `/classes/{classId}/sections`.
- Conceptual endpoints: create a Class (`POST /classes`, School-Admin-only), update a Class (`PATCH /classes/{id}`), archive a Class (`PATCH /classes/{id}/archive`), reactivate a Class (`PATCH /classes/{id}/reactivate`), reorder the Class sequence (`PATCH /classes/{id}/sequence`), designate the final Class (`PATCH /classes/{id}/designate-final`), create/update/archive/reactivate a Section (`POST` / `PATCH` / `PATCH .../archive` / `PATCH .../reactivate` under `/classes/{classId}/sections`), and a Class/Section roster listing (`GET /classes`, School-Admin-only, paginated per API-Standards.md).
- Every endpoint requires a valid JWT and passes through the same Authentication/Authorization middleware chain every other feature's design already uses; no separate authentication mechanism is introduced.
- Every endpoint is School-Admin-only and tenant-scoped from the authenticated user's token, per Multi-Tenancy.md's API Rules — a `schoolId` is never accepted from client input for any of these operations.

## Architecture Update (Grade/Form) — API additions

- New top-level resource, not nested under `/classes` (a `GradeLevel` is a peer grouping *above* Class, not a child of one, the same reasoning `/shifts` is not nested under any other resource): `GET /grade-levels` (list, filterable by `status`), `GET /grade-levels/{id}` (detail, includes its own member Class list), `POST /grade-levels` (create; body: `name`), `PATCH /grade-levels/{id}` (correct `name` only; Guard by Construction rejects `sequenceOrder`/`status`), `PATCH /grade-levels/{id}/sequence` (reorder, mirroring `PATCH /classes/{id}/sequence`), `PATCH /grade-levels/{id}/archive`, `PATCH /grade-levels/{id}/reactivate` — all School-Admin-only.
- `POST /classes` and `PATCH /classes/{id}` both gain a required `gradeLevelId` field (validated against this feature's own new `GradeLevel` rows and the new same-Shift Business Rule, both enforced service-side).
- No Super Admin oversight route is added for `GradeLevel` in this pass — this feature has never exposed one for `Class`/`Section` either (Class Management's Permissions section grants no role but School Admin), so none is introduced here for consistency.

# Backend Design

- New feature module `backend/src/features/classes/`, structured per Folder-Structure.md (controller, service, repository, validation, routes, dto, types, utils, tests).
- `ClassController`, `ClassService`, `ClassRepository`, per Naming-Conventions.md's Services/Repositories/Controllers sections. Sections are managed within the same module (not a separate `sections` feature), since a Section has no meaning or lifecycle independent of its owning Class, per Decision-Making-Principles' "Avoid Premature Abstraction."
- The service layer enforces: a Class's name and sequence position are unique within its school, exactly one Class per school may hold the final-Class flag at a time (reassigning it unsets the previous holder in the same transaction, per Database-Standards.md's Transactions section — never allow a moment where zero or two Classes are marked final), archiving sets status only and never touches Sections' or the Class's own historical data, reactivating a Class always assigns it a fresh position at the end of the school's active sequence rather than restoring its old one (Business Rule #11), and the "suggested next Class" and "final Class" lookups exposed to Student Management are read-only queries with no side effects.
- No hard or soft delete endpoint exists for a Class or Section, per Business Rule #12 — this is a deliberate omission, not a gap to fill later without a Business Specification change.
- Repository layer is the only code touching Prisma, per Coding-Standards.md.
- This feature makes no outbound calls into any other feature — it is called, not calling — which keeps it dependency-free among business features (only School & Platform Management is a dependency, for tenant scoping).

## Architecture Update (Grade/Form) — Backend Design

- `GradeLevel` CRUD lives in this same module's existing `classes.service.js`/`classes.repository.js` files (not a separate module), the same "one module owns Class, Section, and now GradeLevel" decision Architecture above makes explicit.
- **`assertSameShiftWithinGradeLevel(schoolId, gradeLevelId, shiftId, excludeClassId, tx)`** — the new Business Rule's enforcement helper: loads every other Active Class currently in the target `gradeLevelId` (excluding the Class being updated, when editing) and rejects (409) if any has a different `shiftId`. **Runs on every `createClass` and `updateClass` call against the Class's own final, resulting `(gradeLevelId, shiftId)` pair — regardless of which of the two fields the request actually changed.** This matters because `updateClass` already accepts an independent `shiftId` change (ACR-005): changing only a Class's `shiftId`, leaving `gradeLevelId` untouched, is exactly as capable of violating this invariant as changing only `gradeLevelId` would be, so the check is never conditioned on which field appears in the request body. This runs alongside this feature's own existing name/sequence-uniqueness checks, inside the same transaction.
- **`reactivateClass` also calls `assertSameShiftWithinGradeLevel` before restoring — (Technical Design Review finding, fixed here, see Change History).** An Archived Class's own `GradeLevel` membership cannot be assumed still valid: while it sat archived, its former `GradeLevel` could have dropped to zero other Active members, letting a brand-new Class join that same `GradeLevel` on a *different* `shiftId` in the meantime (nothing else was left to conflict with at that moment). Reactivating the original Class back into it would silently create two Active Classes in the same `GradeLevel` on different Shifts — exactly the invariant this Architecture Update exists to prevent. This is the same "an archived record cannot assume its own old state is still valid" principle already established three times elsewhere in this project (`reactivateShift`, `reactivatePeriod`, `replaceTeacher`) — now a fourth instance, caught here during Technical Design Review rather than a later finding.
- `archiveGradeLevel(schoolId, gradeLevelId, actingUser)` — rejects if any Active Class still references it (mirroring `archiveShift`'s own "referenced by an active Class" guard, and this feature's own existing pattern of blocking archival while a live reference exists), since a Class with no Grade/Form would be a structurally invalid state this feature never allows. Does not renumber the remaining active sequence — an Archived `GradeLevel` keeps its own position, the same `Class.sequenceOrder` convention Database Impact's own Technical Design Review finding now makes explicit (unlike `archiveShift`, which does renumber, since `Shift` follows the opposite convention). `reactivateGradeLevel` mirrors `reactivateClass`'s own convention symmetrically: assigns a fresh end-of-sequence position rather than restoring its old one.
- New narrow interface functions, alongside the existing `getClassById`/`getFinalClass`/`listActiveSectionsForClass`:
  - `getGradeLevelShift(schoolId, gradeLevelId)` — returns the one `shiftId` every Active member Class of that `GradeLevel` already shares (derived via a single query, never stored), or `null` if the `GradeLevel` has no member Classes yet or does not exist/belong to a different school. This is the literal function ACR-009 names, for Weekly Subject Allocation's own future consumption.
  - `listGradeLevels(schoolId, { status })` — the full list, optionally filtered, for Weekly Subject Allocation's own Grade/Form picker.
  - `getGradeLevelById(schoolId, gradeLevelId)` — returns `null` on a miss or cross-school id, never throws, the same contract every other narrow interface in this project already uses.
  - `validateGradeLevel(schoolId, gradeLevelId)` — `true` if it exists, belongs to the school, and `status === ACTIVE`; `false` otherwise.
- No other feature may query `grade_levels` directly — the same Loose Coupling discipline already applied to `Class`/`Section`.

# Frontend Design

- `web/src/features/classes/` (React/Vite/JavaScript): Class list/roster (with Sections shown per Class), Class creation and editing, sequence reordering (e.g., drag-and-drop or explicit position editing), final-Class designation control, and Section management — all School-Admin-only screens, per the Business Specification's Permissions section.
- The frontend never re-implements the uniqueness or final-Class-exclusivity rules; it only reflects what the backend returns and enforces, per System-Architecture.md's Business Logic Ownership rule.
- **(ACR-002) `formatClassSectionName(className, sectionName)`** — one small, shared formatting utility (`web/src/features/classes/utils/format-class-section-name.js`), used everywhere a Class and Section are shown together: each Section pill in `ClassesListPage.jsx`'s roster now reads "F1A" instead of just "A"; the same utility is reused by Student Management's Section pickers (Enroll/Promote/Class Correction dialogs) so the two features never diverge on formatting. Pure presentation — takes the two already-fetched `name` strings and concatenates them; no new data, no backend call.
- **(ACR-002) A global "Add Section" button**, next to "Create Class" in `ClassesListPage.jsx`'s header, opens `CreateSectionDialog` with an added Class picker (Select, listing the school's Classes by name) — reusing the same dialog and `createSection(classId, data)` service call the existing per-row "+" affordance already uses, just with `classId` now chosen inside the dialog instead of implied by which row was clicked. Both entry points remain; the per-row "+" is a shortcut that pre-fills the Class picker rather than a separate mechanism.
- **(Architecture Update — Grade/Form)** A new "Grade/Form" management screen (list, create, correct, reorder, archive/reactivate — the same shape as the existing Shifts table in School Schedule Management's own settings page), and `ClassesListPage.jsx`'s Create/Edit Class dialogs gain a required Grade/Form picker. The migration-created placeholder `"Ungrouped"` Grade/Form is visually flagged (a distinct badge/label, e.g. "Ungrouped — reassign your Classes") in both the Grade/Form list and the Class picker, so a School Admin is prompted toward the real, one-time reassignment ACR-009 itself calls out as a genuine manual follow-up, never left indistinguishable from a deliberately-created Grade/Form.

# Validation Strategy

- All validation happens server-side, in the feature's `validation/` layer, before reaching the service layer — never trust client input, per Coding-Standards.md and API-Standards.md.
- Enforces the Business Specification's Validation Rules directly: a Class cannot be created without an owning school, a Class name must be unique within its school, exactly one Class per school must be marked final, and every Class must have a defined sequence position.
- **(Architecture Update — Grade/Form)** Shape-only: `GradeLevel` `name` (non-empty string); `position` for reorder (positive integer). Data-dependent (service layer): `GradeLevel` name uniqueness within school; the new "every member Class shares one Shift" check; archival blocked by an active Class reference. `PATCH /grade-levels/{id}` rejects any field other than `name` (Guard by Construction) — `sequenceOrder`/`status` are never modifiable through this endpoint.

# Security Considerations

- Every endpoint requires authentication, School Admin role permission, and tenant (school) ownership checks, in that order, per Security-Standards.md's Authorization Security section — identical middleware chain to every other feature, no new mechanism introduced.
- Every Class/Section lifecycle event (created, updated, archived, sequence changed, final-Class designation changed) produces an audit record, per this feature's Audit Requirements and Security-Standards.md's Auditability section.
- **(Architecture Update — Grade/Form)** Every `GradeLevel` lifecycle event (created, corrected, reordered, archived, reactivated) produces an audit record, the same as every other entity in this feature. Cross-school access to a `GradeLevel` returns 404, not 403, the same convention as `Class`/`Section`.
- No personally identifiable information is handled by this feature — Class and Section records are purely structural, unlike Student Management's parent/contact data.

# Performance Considerations

- The Class/Section roster listing should be scoped and indexed by `schoolId`, per Database-Standards.md's indexing guidance — a school's full Class list is small and bounded (a handful to a few dozen rows), so pagination is not required here the way it is for Student Management's roster, but the endpoint remains schoolId-scoped regardless.
- Reassigning the final-Class flag and reordering the sequence are low-frequency administrative actions (not per-request hot paths); no special performance design is needed.
- **(Architecture Update — Grade/Form)** `GradeLevel` rows per school are expected to stay small and bounded (typically fewer than a dozen), the same reasoning already applied to `Class`/`Shift` — no pagination needed. `Class.gradeLevelId` is indexed for Weekly Subject Allocation's own future per-Grade/Form lookups.

# Error Handling

- Consistent with API-Standards.md's status codes: 403 when a non-School-Admin role or a different school's School Admin attempts a management action, 409 for a uniqueness conflict (duplicate name or sequence position within the school) or an attempt to designate a second final Class without first unsetting the current one, 422 for validation errors.
- Errors never expose internal implementation details, per Coding-Standards.md.
- **(Architecture Update — Grade/Form) 409** — duplicate `GradeLevel` name within a school; assigning/moving a Class into a `GradeLevel` whose existing member Classes use a different `shiftId`; archiving a `GradeLevel` referenced by an active Class. **422** — missing/invalid `GradeLevel` `name`; any field other than `name` present in a `PATCH /grade-levels/{id}` body (Guard by Construction); an invalid `position`; a `POST`/`PATCH /classes` request missing `gradeLevelId` or referencing an Archived/cross-school one.

# Risks

- **Partial unique index outside Prisma's schema DSL** — the final-Class exclusivity constraint requires a small amount of raw SQL within an otherwise Prisma-generated migration. Contained and well-precedented (Database-Standards.md already anticipates raw SQL "when Prisma cannot reasonably solve the problem"); not a risk to the broader architecture.
- **Sequence reordering edge cases** — inserting or moving a Class within an existing sequence requires renumbering other Classes' positions in the same school. This is a normal, bounded operation (a school's Class count is small) but should be implemented as a single transaction, per Database-Standards.md's Transactions section, to avoid a moment where two Classes share a position. This applies equally to Class creation (assigning the initial next position) and reactivation (assigning a fresh end-of-sequence position) — both must compute the next position from every Class regardless of status, not the active subset alone, since the (schoolId, sequenceOrder) uniqueness constraint applies to archived rows too. Creation and reordering each hit exactly this bug during Implementation, caught only by hands-on testing, not code review alone — reactivation's implementation must apply the same fix from the outset.
- **(Architecture Update — Grade/Form) The backfill is genuinely imperfect, not merely inconvenient — carried forward from ACR-009's own Consequences.** Every pre-existing Class lands in a placeholder `"Ungrouped"` `GradeLevel`; Weekly Subject Allocation cannot be meaningfully configured for any real Grade/Form until a School Admin does the one-time manual work of reassigning existing Classes. Frontend Design's distinct "Ungrouped" badge is this feature's own mitigation, not a fix — the underlying manual work is still required and is not tracked or enforced by any system reminder in this pass.
- **(Architecture Update — Grade/Form) The same-Shift enforcement is a new cross-sibling-row invariant, checked at write time only, with no partial-unique-index backstop** — unlike `Class.isFinal`/`Shift.isDefault`, this invariant spans an arbitrary number of sibling Classes under one `GradeLevel`, which Postgres cannot express as a simple partial unique index. It relies entirely on `assertSameShiftWithinGradeLevel` being called from every write path that can change either a Class's `gradeLevelId` or its `shiftId` — including `reactivateClass`, per this Review's own finding — a future contributor adding a new way to bulk-reassign either field (e.g., a future bulk-import) must remember to route through the same check, the same category of discipline this project already asks of every service-layer-enforced (non-database-backed) invariant.
- **(Architecture Update — Grade/Form, Technical Design Review finding, resolved) `GradeLevel.sequenceOrder` inherits the exact same reordering-edge-case risk already named above for `Class.sequenceOrder`** — insertion, reordering, and reactivation must all compute the next position from every `GradeLevel` regardless of status, inside a single transaction, the same discipline Class's own Implementation had to learn by catching this bug hands-on rather than in Technical Design Review. Naming it here, before Implementation, is the entire point of catching it now rather than a third time.
