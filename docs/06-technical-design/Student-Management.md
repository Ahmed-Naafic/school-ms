Feature: Student Management

Version: 1.8

Status: Implementation complete; Phase 7 Validation passed. An independent code review (Phase 9) found and fixed a small number of defects — see `docs/08-validation/Student-Management.md` and `docs/00-governance/Code-Review-Report.md`. Amended by ACR-002 (v1.6 below) — Enrollment may now reference a Section — and by ACR-004 (v1.8 below) — Enrollment/Promotion now reference a real Academic Year; this feature's own Feature Acceptance is not reopened by either amendment.

# Overview

This document designs the technical approach for the Business Specification approved in `docs/03-business/Student-Management.md`.

It applies the already-approved architecture (`System-Architecture.md`, `Folder-Structure.md`), technology stack (`Technology-Decisions.md`), and standards (`Database-Standards.md`, `API-Standards.md`, `Security-Standards.md`, `Naming-Conventions.md`) to this specific feature. No new technology, pattern, or architecture is introduced here.

A blocking dependency gap surfaced while producing this design and was resolved by the Product Owner — see Dependencies below. Class Management (which this feature depends on for Enrollment, Promotion, and Graduation) was re-sequenced ahead of Student Management in `Development-Roadmap.md` and is now implemented (`backend/src/features/classes/`, `web/src/features/classes/`), unblocking this feature's own Implementation Planning. No placeholder or workaround model was ever introduced to avoid the wait, per explicit Product Owner direction.

# Architecture

- Implemented as a feature module: `backend/src/features/students/` — Folder-Structure.md already anticipates this exact module name in its feature list, and Naming-Conventions.md's own worked examples use `students`/`StudentController`/`StudentService` throughout.
- Admission triggers Authentication & Authorization's account-creation service for the new Student's login account, via a single, narrow interface call ("create Student account for this school") — never reaching into that feature's internals, per Decision-Making-Principles' Feature Ownership and Loose Coupling (Principle 6), matching the same pattern School & Platform Management already uses for creating a school's first School Admin account.
- Enrollment is modeled as its own concept, separate from the Student's identity record, because Business Rule #5 requires Enrollment history to be preserved across Promotion rather than overwritten (a new Enrollment record per academic year, not a single mutable "current class" field). This is a real design decision, not a default: it directly implements the Business Specification's Business Workflow #2–#3 and Business Rule #5.
- **Web vs. Mobile split, per System-Architecture.md's Applications section:** School Admin (Admission, Enrollment, Promotion, Transfer, Withdrawal, Graduation, profile management, roster) is a Web-only role — this entire management surface belongs in `web/src/features/students/`. Student's own Self-Service Viewing (Business Workflow #7) belongs on Mobile only, in `mobile/lib/features/student/`, since Student is a Mobile-application role, not a Web-application role. There is no Web-facing Student self-service screen and no Mobile-facing School Admin management screen.
- Transfer's summary record (Business Rule #9) is designed as a small set of fields carried on the archived Student/Enrollment record (prior Class, an academic summary snippet) rather than a new, separate database entity — per "Simplicity Wins" and "Avoid Premature Abstraction" (Decision-Making-Principles #2, #15). If the summary's content grows in scope later, promoting it to its own entity is a future reconsideration, not a decision made now.
- **Transfer stores no destination-school reference anywhere in the schema, confirmed by explicit Product Owner decision.** There is no `destinationSchoolId` field, no cross-school foreign key, and no notification mechanism to another school. This is a deliberate, hard boundary — not an omission to fill in later — consistent with Multi-Tenancy.md's tenant isolation applying "without exception." The receiving school's eventual Admission of the same person is, from this system's point of view, a completely unrelated new Student record; nothing here links the two. If inter-school transfer linkage is ever approved, it requires its own Business Specification and architectural review, not an extension of this data model.
- **"Eligible for Graduation" is a stored lifecycle state on the Student record, not a computed/derived value.** An earlier version of this design computed eligibility live from the Student's current Enrollment against Class Management's final-Class designation, reasoning that a stored flag would risk drifting out of sync ("One Source of Truth," Decision-Making-Principles #21). The Product Owner corrected this: per the Business Specification's Business Rule #10, the transition into "Eligible for Graduation" is a one-way business event that must survive a later change to which Class is designated final — it cannot be a live-recomputed value, since recomputation would silently revoke eligibility already granted. The transition is written once, when a Student is promoted into the then-current final Class, and is never re-evaluated afterward by a designation change. This is the correct trade-off here: a small, deliberate duplication of state in exchange for auditability and a stable Student lifecycle, per Decision-Making-Principles' Protect Data (#12) and Fail Safely (#23).
- **Reversibility is decided per lifecycle event, not by one blanket "restore" action.** Withdrawal is reversible (Business Rule #14) — restoration flips status back to `ACTIVE` and calls Authentication & Authorization's existing account-reactivation service; it does not touch Enrollment. Transfer and Graduation are permanent (Business Rule #15) — no restoration path exists for either in this feature's service layer at all, not merely hidden in the UI, since a Transfer crosses tenant boundaries and Graduation is a final academic event.
- **Class Correction is a narrow, deliberate exception to Enrollment's otherwise-immutable history.** Every other Enrollment-affecting action (Enrollment, Promotion, Transfer's summary write) either creates a new Enrollment record or writes to a terminal record's own summary field; Class Correction is the one action that mutates a Student's *current* Enrollment's `classId` in place, per Business Rule #16 — because it corrects a data-entry mistake, not a real academic-progression event, and must never create a new Enrollment record or evaluate Graduation eligibility. This is why it is implemented as its own service function, not a variant of Promotion.
- **(ACR-002) Enrollment's Section reference is validated by one shared helper, `assertSectionEnrollable(schoolId, classId, sectionId)`, called from Enrollment, Promotion, and Class Correction alike** — mirroring `assertClassEnrollable`'s existing pattern of one shared Class-validation helper reused across all three. It calls Class Management's new `listActiveSectionsForClass(schoolId, classId)` (the one interface addition ACR-002 requires — see Class-Management.md's Technical Design) and applies Business Rule #18 in full: a present `sectionId` not found in that list (wrong Class, archived, or nonexistent) is rejected; an absent `sectionId` is rejected only if the list is non-empty (the Class has active Sections). A Class with no active Sections at all trivially passes with no `sectionId`, since the list is empty either way — no separate "does this Class have Sections" check is needed.
- **(ACR-002) Promotion's Section-matching (Business Rule #19) is attempted only when the caller did not explicitly choose a destination Section.** If the current Enrollment has a `sectionId`, its `name` is looked up (via the same `listActiveSectionsForClass` call, scoped to the *current* Class) and searched for by name in the *destination* Class's active Sections. A match becomes the suggested `sectionId`; no match leaves it unset, and `assertSectionEnrollable` then naturally enforces "required if the destination Class has active Sections" — the same helper both suggests and validates, so there is no separate enforcement path that could drift out of sync with the suggestion logic.
- **(ACR-004) Enrollment's Academic Year reference is validated by one shared helper, `assertAcademicYearEnrollable(schoolId, academicYearId)`, called from both Enrollment and Promotion** — the same "one shared validation helper reused across every write path" pattern `assertClassEnrollable` and `assertSectionEnrollable` already establish. It calls Academic Year Management's own Stable Public Service Interface (`getAcademicYearById(schoolId, academicYearId)`) — never a direct query against the `academic_years` table — and rejects when the Academic Year does not exist, does not belong to this school, or is Archived. Because a school with zero Academic Years simply has no valid `academicYearId` to supply, this same helper naturally collapses Business Rule #22's "reject if the school has none" into the same failure path as an invalid reference — no separate check is needed.
- **(ACR-004) Promotion's Academic Year default (Business Rule #23) is a plain pre-fill, not a validation shortcut.** When the caller does not explicitly supply an `academicYearId`, the service calls Academic Year Management's `getCurrentAcademicYear(schoolId)` and uses its `id` as the default. The chosen value — whether defaulted or explicitly supplied — always passes through the same `assertAcademicYearEnrollable` check before the new Enrollment is created, so the suggestion can never bypass validation the way an explicit choice wouldn't either.

# Database Impact

Conceptual data shape only — field-level schema is a separate Database Design exercise if the Product Owner wants one produced.

- A Student entity capturing: identifying information, parent contact information, an owning-school reference (required — every Student belongs to exactly one school, per Multi-Tenancy.md), a lifecycle status (`StudentStatus` enum: `ACTIVE` / `ELIGIBLE_FOR_GRADUATION` / `TRANSFERRED` / `WITHDRAWN` / `GRADUATED`, PascalCase enum name and UPPER_SNAKE_CASE values per Naming-Conventions.md's Enums section, matching `UserRole`'s existing pattern), a reference to the Student's own Account (Authentication & Authorization's entity, one-to-one), and standard `createdAt` / `updatedAt` timestamps per Database-Standards.md.
- A separate Enrollment entity capturing: a reference to the Student, an academic year, a reference to a Class (Class Management's entity), and timestamps. One Enrollment record exists per academic year per Student; Promotion creates a new Enrollment record rather than mutating the prior one, per Business Rule #5 and Database-Standards.md's "protect historical data" principle. The Student's *current* Class is derived by querying the most recent Enrollment, not duplicated onto the Student record itself.
- **(ACR-002) `sectionId` — nullable foreign key to Class Management's Section entity, added to Enrollment.** Additive migration; every pre-existing Enrollment row has `sectionId: NULL`, unaffected. No application-level uniqueness or index constraint ties `sectionId` to `classId` at the database layer (Section's own `classId` is already the source of truth for that relationship) — the "must belong to the same Class" rule (Business Rule #18) is enforced in the service layer via `assertSectionEnrollable`, the same layer (not the database) that already enforces the analogous "Class must belong to this school" check for `classId`.
- **(ACR-004) `academicYearId` — nullable foreign key to Academic Year Management's `AcademicYear` entity, added to Enrollment.** Additive migration, exactly mirroring the `sectionId` precedent above: every pre-existing Enrollment row has `academicYearId: NULL`, unaffected, and its original free-text `academicYear` column is left in place, permanently, as the historical value for those rows. Going forward, the service layer requires `academicYearId` for every new Enrollment/Promotion (Business Rules #21–#22) and stops writing to the free-text `academicYear` column entirely for new rows — the column itself is not dropped, since old rows still use it. "Must belong to this school and not be Archived" (Business Rule #21) is enforced in the service layer via `assertAcademicYearEnrollable`, never a database constraint, the same division of responsibility `sectionId` already established.
- Transfer's summary fields (prior Class, academic summary) are carried on the outgoing Enrollment record at the point of Transfer, per the Architecture section above.
- The transition to `ELIGIBLE_FOR_GRADUATION` is a one-time write to the Student's `status` field, triggered when a Promotion enrolls the Student into the school's then-current final Class. It is never re-derived or overwritten by a later change to Class Management's final-Class designation — per the Architecture section above, this is a deliberate, explicit exception to computing state live.
- Withdrawal and Graduation do not add data beyond the lifecycle status change and archival — per Business Rules #7 and #12, records are archived (preserved, inactive), never hard-deleted, per Database-Standards.md's Soft Delete Policy and the Archive Before Delete principle.
- Withdrawal Restoration is a plain status write (`WITHDRAWN` → `ACTIVE`) plus a call to Authentication & Authorization's account-reactivation service; it does not touch the Enrollment table, per Business Rule #14.
- Class Correction is the one place this feature ever mutates an existing Enrollment row's `classId` after creation — every other write path (Enrollment, Promotion) creates a new row instead. The audit record for a Class Correction carries the previous and new `classId` plus an optional reason in its `metadata` field, per Business Rule #17 and the standard audit record's existing `metadata` column (Multi-Tenancy.md).
- Class Correction reuses the same `assertNotAlreadyTerminal` guard Transfer and Withdrawal already use (checking for `TRANSFERRED`/`WITHDRAWN`/`GRADUATED`), so it is only reachable while a Student's status is `ACTIVE` or `ELIGIBLE_FOR_GRADUATION`, per Business Rule #16 (v1.5). This was added after an independent code review found that correcting a finalized Student's Class could leave a Transfer summary or Graduation record referring to a Class the Enrollment no longer points to.
- Relationship: Student → School is many-to-one, required (not nullable, unlike Account's Super-Admin exception) — every Student belongs to a school, with no platform-level Student. Student → Account is one-to-one. Student → Enrollment is one-to-many (history preserved).
- Student lifecycle audit events are written to the platform's shared audit log mechanism (owned by the Audit Logs feature), consistent with the standard audit record (Tenant, User, Action, Timestamp) defined in Multi-Tenancy.md — the same mechanism Authentication & Authorization's and School & Platform Management's designs already use.
- Indexing: `schoolId` (every roster/listing query is scoped to one school) and `status` (filtering active vs. transferred/withdrawn/graduated) should be indexed together, per Database-Standards.md's indexing guidance.

# API Design

High-level shape only — exact routes, payloads, and per-case status codes belong in a separate API Specification if requested.

- REST, versioned under `/api/v1`, per API-Standards.md. Resource name is plural: `/students`, consistent with Naming-Conventions.md's API Endpoints section.
- Conceptual endpoints: admit a Student (`POST /students`, School-Admin-only; internally invokes Authentication & Authorization's account-creation), enroll a Student (`POST /students/{id}/enrollments`, School-Admin-only), update Student profile (`PATCH /students/{id}`, School-Admin-only), promote (`PATCH /students/{id}/promote`), correct a Student's current Class (`PATCH /students/{id}/correct-class`, distinct from promote per Business Rule #16), transfer (`PATCH /students/{id}/transfer`), withdraw (`PATCH /students/{id}/withdraw`), restore a withdrawn Student (`PATCH /students/{id}/restore-withdrawal` — Withdrawal only; no equivalent endpoint exists for Transfer or Graduation, per Business Rule #15), graduate (`PATCH /students/{id}/graduate`) — the promote/transfer/withdraw/graduate lifecycle-action pattern mirrors School & Platform Management's existing `suspend`/`reactivate`/`close`/`reopen` endpoints, an already-established precedent in this codebase for state-transition actions. A Student roster/list endpoint (`GET /students`, School-Admin-only, paginated per API-Standards.md) and a Student's own record endpoint (`GET /students/me`, Student-only) round out the surface.
- **(ACR-002) `POST /students/{id}/enrollments`, `PATCH /students/{id}/promote`, and `PATCH /students/{id}/correct-class` each accept an additional optional `sectionId` field.** No new endpoint and no new route — this is an additive field on three existing request bodies, per Business Rules #18–#20.
- **(ACR-002) `GET /students` accepts an additional optional `sectionId` query parameter**, narrowing the roster to Students whose *current* Enrollment matches that Section specifically — the same "current Enrollment only, never historical" semantics the existing `classId` filter already has. May be combined with `classId` or used alone (a Section already implies its own Class). Added so the Web roster filter can offer Section-level granularity (e.g. "F1A" specifically, not just "F1"), consistent with Class Management's combined-name convention.
- **(ACR-004) `POST /students/{id}/enrollments` and `PATCH /students/{id}/promote` each accept an `academicYearId` field, required going forward for both.** No new endpoint — an additive field on two existing request bodies, per Business Rules #21–#23. Unlike `sectionId` (optional, conditionally required depending on the target Class), `academicYearId` is unconditionally required for Enrollment; Promotion alone allows it to be omitted, in which case the service defaults it to the school's Current Academic Year (Business Rule #23) before validating it the same way an explicit value would be.
- Every endpoint requires a valid JWT and passes through the same Authentication/Authorization middleware chain designed in Authentication & Authorization's Technical Design; no separate authentication mechanism is introduced.
- `GET /students/me` resolves the Student from the authenticated user's own token — never from a client-supplied `studentId` — so a Student can never view another Student's record by manipulating a request, per Multi-Tenancy.md's API Rules and Business Rule #11.

# Backend Design

- New feature module `backend/src/features/students/`, structured per Folder-Structure.md (controller, service, repository, validation, routes, dto, types, utils, tests).
- `StudentController`, `StudentService`, `StudentRepository`, per Naming-Conventions.md's Services/Repositories/Controllers sections.
- The service layer enforces: a Student cannot be enrolled before Admission (Business Rule pending Enrollment), Promotion always creates a new Enrollment record rather than mutating the existing one, Class Correction always mutates the current Enrollment in place and never creates a new one or touches Graduation eligibility, Transfer/Withdrawal/Graduation are mutually distinct terminal actions that also deactivate the Student's Account (via a call into Authentication & Authorization's deactivation service), only Withdrawal has a restoration path (reactivating the Account via the same service), and the transition to `ELIGIBLE_FOR_GRADUATION` is written once at Promotion time and never re-evaluated afterward (see Architecture).
- Admission's call into Authentication & Authorization's account-creation service, and Transfer/Withdrawal/Graduation's call into its deactivation service, are the feature's only cross-feature dependencies — direct in-process service calls, consistent with System-Architecture.md's Modular Monolith style, not network calls. **(ACR-002) `classesService.listActiveSectionsForClass(schoolId, classId)` is now also called** from `assertSectionEnrollable`, for the same reason and in the same style as the pre-existing `classesService.getClassById`/`getSuggestedNextClass`/`getFinalClass` calls — a direct in-process call into Class Management's own narrow public interface, never a query against its `sections` table. **(ACR-004) `academicYearsService.getAcademicYearById(schoolId, academicYearId)` and `academicYearsService.getCurrentAcademicYear(schoolId)` are now also called**, from `assertAcademicYearEnrollable` and Promotion's default-selection step respectively — direct in-process calls into Academic Year Management's own narrow public interface, never a query against its `academic_years` table.
- Repository layer is the only code touching Prisma, per Coding-Standards.md.

# Validation Strategy

- All validation happens server-side, in the feature's `validation/` layer, before reaching the service layer — never trust client input, per Coding-Standards.md and API-Standards.md.
- Enforces the Business Specification's Validation Rules directly: a Student cannot be enrolled without first being admitted, a Student cannot be admitted without an owning school, a defined lifecycle status is always present, Transfer requires generating the summary fields while Withdrawal must not, and Graduation's manual-confirmation step cannot be skipped even when eligibility is flagged.
- **(ACR-002) `sectionId`, when present in a request body, is shape-validated only** (a non-empty string) **in the `validation/` layer** — exactly like `classId` today. Whether it's *required* (the target Class has active Sections), whether it *belongs* to the target Class, and whether it's *archived* are all role-dependent, data-dependent checks that require a repository/cross-feature lookup, so — consistent with `assertClassEnrollable`'s existing split — they stay in the service layer's `assertSectionEnrollable`, never in `validation/`.
- **(ACR-004) `academicYearId`, when present, is shape-validated only** (a non-empty string) **in the `validation/` layer**, the same split as `classId`/`sectionId`. Enrollment's `validation/` layer requires the field to be present at all (unconditionally, unlike `sectionId`); Promotion's does not, since its absence is a valid "use the default" signal handled entirely in the service layer. Whether the value actually resolves to a real, same-school, non-Archived Academic Year is a cross-feature lookup, so it stays in `assertAcademicYearEnrollable`, never in `validation/`.

# Security Considerations

- Every endpoint requires authentication, role permission, and tenant (school) ownership checks, in that order, per Security-Standards.md's Authorization Security section — identical middleware chain to every other feature, no new mechanism introduced.
- `GET /students/me` derives the Student's identity strictly from the authenticated token, never a client-supplied identifier, per Security-Standards.md's Authorization Security section and Multi-Tenancy.md's API Rules — this is the specific control preventing one Student from viewing another's record (an IDOR-class risk if implemented naively).
- Student and parent contact information is personally identifiable information; it is handled only within this feature's own module and is never duplicated into another feature's data, per Security-Standards.md's Sensitive Data Protection section and Decision-Making-Principles' Feature Ownership.
- Every Student lifecycle event (Admission, Enrollment, profile update, Promotion, Class Correction, Transfer, Withdrawal, Withdrawal Restoration, Graduation) produces an audit record, per this feature's own Audit Requirements and Security-Standards.md's Auditability section. A Class Correction's audit record additionally carries the previous Class, the new Class, and an optional reason, per Business Rule #17.
- Account deactivation triggered by Transfer, Withdrawal, or Graduation immediately revokes the Student's refresh token, per Authentication & Authorization's and Security-Standards.md's Session and Token Management section — no new revocation mechanism is introduced here; this feature only triggers the existing one. Withdrawal Restoration calls the corresponding account-reactivation service, per Business Rule #14.

# Performance Considerations

- The Student roster endpoint must be paginated, per API-Standards.md's Pagination rule — a school-wide unfiltered Student list is not an acceptable query shape at scale.
- `schoolId` + `status` should be indexed together, since every roster and dashboard query filters on both, per Database-Standards.md's indexing guidance.
- Enrollment history grows by one record per Student per academic year — bounded, predictable growth; no special performance design is needed at current expected scale.

# Error Handling

- Consistent with API-Standards.md's status codes: 403 when a non-School-Admin role attempts a management action or a Student attempts to access another Student's record, 409 for an invalid lifecycle transition, 422 for validation errors.
- **(ACR-002) `assertSectionEnrollable` failures are 422s, not 404/409** — both "a `sectionId` was required but omitted" and "a provided `sectionId` isn't a valid, active Section of the target Class" (wrong Class, archived, or nonexistent — collapsed into one check via `listActiveSectionsForClass`) are treated as a single request-validation concern on the `sectionId` field, the same way `PATCH /teachers/{id}`'s guard-by-construction fields are 422s in Teacher Management, rather than splitting them into a 404-vs-409 distinction the way `assertClassEnrollable` does for `classId`. This is a deliberate simplification: unlike a Class (which is meaningfully either "not found" or "found but archived" as two distinct realities worth telling the caller apart), an invalid `sectionId` here is always fundamentally "this value doesn't resolve to a valid choice for this Class" — one message, one status code.
- **(ACR-004) `assertAcademicYearEnrollable` failures are 422s, for the same reason `assertSectionEnrollable`'s are.** A missing `academicYearId` (Enrollment only), a nonexistent one, one belonging to another school, or one that is Archived, are all collapsed into one request-validation concern on the `academicYearId` field — one message, one status code, never a 404/409 split. A school with zero Academic Years produces the identical 422 as any other invalid `academicYearId`, since there is no valid value that school could have supplied (Business Rule #22) — no separate error path or status code is introduced for that case.
- **Graduation is a controlled transition, resolved by Product Owner decision: `ELIGIBLE_FOR_GRADUATION` → `GRADUATED` only.** School Admin cannot graduate a Student directly from `ACTIVE` (or any other status) — attempting to confirm Graduation for a Student who has not already reached `ELIGIBLE_FOR_GRADUATION` is rejected with 409 Conflict, makes no change to the Student, and is recorded in the audit log as an attempted action, per this feature's Audit Requirements. There is no direct `ACTIVE` → `GRADUATED` path. An exceptional/early-graduation workflow, if ever needed, is a separate business process requiring its own design and permissions — not a bypass of this guard.
- Errors never expose internal implementation details, per Coding-Standards.md.

- **School & Platform Management** — Approved, with a completed Technical Design. Every Student belongs to a school this feature creates and keeps active. No blocker.
- **Class Management — hard implementation dependency, now resolved.** Enrollment (Business Workflow #2), Promotion (#3), and Graduation-eligibility (#6) all require a Class entity and a "final Class" designation that Class Management owns. Per Product Owner decision, `Development-Roadmap.md` was re-sequenced so Class Management (now #3) was implemented before Student Management (now #4) — it is now built and available at `backend/src/features/classes/classes.service.js`, exposing exactly the narrow read-only interface this feature needs: `getClassById`, `getSuggestedNextClass`, `getFinalClass`, and **(ACR-002)** `listActiveSectionsForClass`. No placeholder or temporary Class model was ever introduced; only the timing of Implementation was affected.
- **(ACR-004) Academic Year Management** — Accepted, with a completed, Approved Technical Design (`docs/06-technical-design/Academic-Year-Management.md`). Enrollment and Promotion require a real Academic Year reference, consumed exclusively through its Stable Public Service Interface: `getAcademicYearById`, `getCurrentAcademicYear`, `listActiveAcademicYears` (`backend/src/features/academic-years/academic-years.service.js`). No blocker — the feature is already built and Accepted; this is purely a new consumer of its existing interface, no change to Academic Year Management's own code is required.
- **Security Standards** — already authored; no gap.
- **Audit Logs** — this feature produces audit events from day one; the Audit Logs feature's own review/search capability is scheduled later in the Roadmap but does not block this feature's own Implementation, consistent with how Authentication & Authorization's design already treats this.

# Risks

- **Class Management sequencing dependency** — resolved; see Dependencies above. Kept here as a record that this was a real, hands-on-discovered gap in the original Roadmap ordering, resolved by re-sequencing rather than a design compromise.
- **Transfer summary scope creep** — keeping the Transfer summary as a few fields rather than a full entity is the simplest fit for what's approved today (Business Rule #9's "prior Class and an academic summary"); if the Product Owner later wants a richer transfer record (e.g., attachments, multi-section summaries), this is a schema migration, not a redesign, per "Avoid Premature Abstraction."
- **Parent contact data growth** — currently a small set of profile fields per the Business Specification's explicit "not a system actor" scoping (no Parent role, no portal). If a future Parent Portal is ever approved, this data model is a starting point, not a constraint — revisit only then, per YAGNI.
- **Known limitation — no correction path for a mistaken Transfer or Graduation.** This implementation is correct: Transfer and Graduation are permanent lifecycle events, exactly per Business Rules #6 and #15, and `assertNotAlreadyTerminal` correctly blocks further action once a Student reaches either status. But those same Business Rules anticipate "a separate, controlled administrative correction process" for genuine mistakes (a mis-clicked Transfer or Graduation), and that process has not been designed or built. A generic "Restore to Active" action was explicitly considered and rejected as a substitute — it would undermine the permanence these events are meant to have. Until it exists, a mistaken Transfer or Graduation has no in-application recovery path; a manual database edit is not a supported workaround. Tracked as its own backlog feature, **Administrative Corrections** (`docs/03-business/Administrative-Corrections.md`, `docs/00-governance/Development-Roadmap.md`'s Backlog section) — a cross-cutting feature, not an extension of Student Management.
- **(ACR-004) New hard dependency: a school with zero Academic Years cannot enroll or promote any Student.** This is the deliberate, Product-Owner-chosen trade-off recorded in ACR-004's own Consequences section (reject clearly rather than silently degrade to the legacy free-text field), not an oversight — but it is a genuine new coupling between two previously independent features, worth flagging here as a real operational risk: a School Admin who admits Students before ever visiting Academic Year Management will hit a wall at the Enrollment step with no prior warning from Admission itself. Mitigation (a hint on the Admission/Enrollment screen pointing to Academic Year Management) is a Frontend Design / Implementation Planning concern, not a business-rule change.

# Change History

- v1.0–v1.2 — Initial design through the Withdrawal Restoration and Class Correction additions; the "Eligible for Graduation" note was corrected from "computed live" to "stored, one-way lifecycle state" per Product Owner decision.
- v1.3 — Documented Transfer's explicit no-cross-school-link design.
- v1.4 — Recorded the known implementation gap (no correction path for mistaken Transfer/Graduation) and its tracking as the separate Administrative Corrections backlog feature. Phase 7 Validation passed; no design changes required. See `docs/08-validation/Student-Management.md`.
- v1.5 — Independent code review (Phase 9) found and fixed two defects: `enrollStudent` had no guard against re-enrolling an already-Transferred/Withdrawn/Graduated Student (bypassing their permanence), and Class Correction had no status guard at all (refined into Business Rule #16, v1.5 — restricted to `ACTIVE`/`ELIGIBLE_FOR_GRADUATION`). Both are now covered by automated tests. See `docs/00-governance/Code-Review-Report.md`.
- v1.6 — ACR-002 (`docs/01-architecture/Architecture-Decision-Records/ACR-002-Enrollment-Section-Reference.md`): added a nullable `sectionId` to Enrollment, threaded through Enrollment/Promotion/Class Correction (Business Rules #18–#20), validated by one shared `assertSectionEnrollable` helper calling Class Management's new `listActiveSectionsForClass`. Promotion additionally attempts a same-name Section match in the destination Class when the current Enrollment has one (Business Rule #19). Additive and backward-compatible — no change to any pre-existing behavior when a Class has no Sections.
- v1.7 — Product Owner feedback: the Web roster filter could only narrow by Class, not by Section, even though Enrollment could now carry one (v1.6). `GET /students` gained an optional `sectionId` query parameter, matched against each Student's current Enrollment the same way `classId` already is; `listStudents` extended to accept it alongside or instead of `classId`. The Web filter dropdown now lists one flat, combined-name option per Section (plus each sectionless Class by its own name), replacing the previous Class-only list. Covered by new unit and integration tests.
- v1.8 — ACR-004 (`docs/01-architecture/Architecture-Decision-Records/ACR-004-Enrollment-Academic-Year-Reference.md`): added a nullable `academicYearId` to Enrollment, threaded through Enrollment (required) and Promotion (defaults to the school's Current Academic Year, per Business Rule #23) — Business Rules #21–#24 — validated by one shared `assertAcademicYearEnrollable` helper calling Academic Year Management's Stable Public Service Interface, mirroring `assertSectionEnrollable`'s existing pattern exactly. The pre-existing free-text `academicYear` column is untouched and remains the historical value for every pre-existing Enrollment row; new rows stop writing to it entirely. A school with zero Academic Years is a new hard dependency, flagged in Risks. Additive and backward-compatible for all existing data.
